## Блок 3. Каретка (находка №1) — механизм в отчёте назван неверно, но фикс-кандидат правильный; сам эффект — скорее артефакт автоматизации, при этом код объективно хрупок

Код (`TemplateEditorPanel.tsx:44-53`):

```ts
const { text, caret } = edit(draft, el.selectionStart, el.selectionEnd)
onDraftChange(text)
requestAnimationFrame(() => { el.focus(); el.setSelectionRange(caret, caret) })
```

Разбор по шагам реального клика (React 19, discrete event):

1. `mousedown` по кнопке тулбара/палитры → **textarea теряет фокус** (у кнопок нет
   `onMouseDown={e => e.preventDefault()}`). Selection-значения при blur в Chrome сохраняются —
   поэтому вставка ложится в правильную позицию (что приёмка и видела).
2. `click` → `applyEdit` → `onDraftChange` → React 19 флашит состояние **синхронно в конце
   discrete-события**, до отрисовки кадра. Замена `value` у **несфокусированного** textarea
   ставит каретку в конец (нативный сеттер; собственное selection-restore React'а работает только
   для сфокусированного элемента — textarea им в этот момент не является).
3. rAF-колбэк, поставленный на шаге 2, выполняется **после** коммита → restore должен победить.

Отсюда два вывода:

- **Гипотеза отчёта «rAF срабатывает ДО re-render'а controlled textarea» механически неправдоподобна**:
  апдейт из discrete-события коммитится синхронно до возврата в браузер, rAF физически позже.
- **Реальная причина наблюдения `selectionStart == value.length` в ночном прогоне почти наверняка
  другая**: Chrome **приостанавливает requestAnimationFrame у скрытых/перекрытых/свёрнутых окон**
  (occlusion tracking на Windows). Ночной автономный прогон = окно не на переднем плане → rAF-колбэк
  не выполнился к моменту замера → каретка так и осталась в конце после шага 2. Это согласуется и с
  «клики/Ctrl+Home каретку не двигают» из самого отчёта — окружение без реального фокуса.

**Вердикт: артефакт автоматизации с вероятностью ~90% (при живом клике в фокусном окне restore
победит), НО код объективно хрупок** — восстановление каретки привязано к кадру отрисовки, который
не гарантирован (скрытая вкладка, свёрнутое окно, throttling). Плюс косметика: один кадр каретка/скролл
реально прыгают в конец и обратно.

**Минимальный фикс (правильный, и он же предложен в отчёте):** restore на коммите, а не на кадре —

```ts
const pendingCaret = useRef<number | null>(null)
// в applyEdit: pendingCaret.current = caret; onDraftChange(text)
useLayoutEffect(() => {
  if (pendingCaret.current === null) return
  const el = textareaRef.current
  if (el) { el.focus(); el.setSelectionRange(pendingCaret.current, pendingCaret.current) }
  pendingCaret.current = null
}, [draft])
```

Дополнительно (1 строка, стандартный паттерн editor-тулбаров): `onMouseDown={e => e.preventDefault()}`
на кнопках `TemplateToolbar`/`VariablePalette` — textarea вообще не теряет фокус, тогда React сам
сохраняет selection при коммите и исчезает фокус-мигание. Живой клик (10 сек) всё равно стоит сделать —
но фикс дешевле спора и полезен независимо от исхода.

## Блок 4. Английский текст ошибки (находка №3) — подтверждено, локализация тривиальна

- Источник: **`n8n/templates/render-document.js:224`** — `` throw new Error(`Unclosed {{#if}} opened at line ${t.line}`) ``;
  там же :249 (`{{#each}}`), :258 (общий), плюс ещё ~5 английских паттернов: `Unterminated string literal…`,

- Обёртка: **`apps/client/src/admin/lib/templateGate.ts:23`** — `` `Помилка в шаблоні: ${msg}` ``.
- Локализация делается **целиком в UI-слое** (движок — SSoT, не трогаем, инвариант §3.4): таблица
  regex→украинский шаблон в `runParseGate` (сообщений конечное число, номер строки извлекается группой),
  fallback — сырое сообщение. Полдня работы с тестами; риска ноль, т.к. gate живёт только в админке.

## Блок 5. Методология приёмки — честная, но синтетическая; границы применимости

Приём «native setter + dispatchEvent('input')» корректно проходит через React onChange — для
**value-level** утверждений это надёжно. `.click()` по кнопкам — надёжно для **обработчиков**, но не
для фокусного цикла.

**Покрыто убедительно:**
- П.1-4 (вставка директив/переменных в правильные позиции) — суть чистые функции `insertAtCursor.ts` +
  подтверждение в DOM-value; плюс юнит-тесты на них есть.
- П.6 (публикация) — сильнейший блок: эффект проверен в живой БД и мной независимо подтверждён до хеша.
- П.7 (негатив) — disabled-состояние, укр. обёртка ошибки, сохранение кривого черновика — всё
  value/state-level, синтетика тут адекватна.
- П.5 (чипы) — DOM-проверяемо, ок.

**Покрыто частично:**
- Каретка/фокус/blur (см. блок 3) — синтетика принципиально не воспроизводит mousedown→blur→click и rAF.
- Toast: не пойман; отчёт пишет «живёт < ~2 с» — **фактически в коде 4000 мс**
  (`ServiceEditPage.tsx:78`, `setTimeout(..., 4000)`). Мелкая, но фактическая ошибка отчёта; невидимость
  toast — того же происхождения, что и rAF (окно без отрисовки).
- «Розкладка» — проверена по DOM-тексту страниц, но без визуальной валидации A4 (скриншоты localhost не работали).

## Блок 6. Прод-безопасность трюка «оригинал + {{! коммент}}» — ✅ подтверждено кодом и экспериментом

- `render-document.js:62` — `content.startsWith('!')` → `'comment'`; `:211` — `if (kind === 'comment') continue;`
  (узел вообще не попадает в AST).
- `applyStandalone` (`:77-95`) — тег, стоящий отдельной строкой, съедает свою строку целиком
  (и хвост `\n`), «output стаётся byte-exact» — заявлено в шапке движка (:28-29).
- **Эмпирика (мой прогон)**: `renderDocumentWithStyles` на паре «текст» vs «текст + строка `{{! demo-comment }}`»
  → `text` идентичен и `styleHints` идентичны. Рендер-нейтральность **доказана**, публикация №1 не могла
  изменить генерируемые документы.
- Плюс: `publishTemplate` трогает `generation_mode` только если он NULL (:58) — у divorce он `'template'`,
  не тронут. Порядок snapshot→update защищает от «сломали и не заметили».

## Сводная оценка приёмки

**Фактология — безупречна.** Всё, что отчёт утверждает как факт (тесты, хеши, длины, ревизии,
байт-идентичность прода, нейтральность коммента), подтвердилось независимой проверкой на 100%.
Отдельный плюс — честные оговорки самого отчёта («не подтверждённый баг», «нужен живой клик») и
аккуратная схема публикации без риска для прода.

**Слабые места:**
1. Пункт validation.md «lint чистый» молча пропущен (падает, хоть и pre-existing).
2. Пункт «мобильная ширина read-only» не проверялся вообще и в отчёте не упомянут как пропуск.
3. Гипотеза по каретке названа неверно (rAF-vs-commit гонки нет; реальный механизм — blur textarea +
   пауза rAF в скрытом окне), хотя фикс-кандидат случайно правильный.
4. Мелкая фактическая ошибка: toast живёт 4 с, не «< ~2 с».
5. Не замечен риск в собственном совете «запусти e2e с env»: e2e публикует в живую БД без отката.
6. RLS и конкурентное редактирование — вне поля зрения приёмки (и вне синтетики в принципе).

**Итог: вердикт «приёмка пройдена» по 7 пунктам чеклиста поддерживаю** — с поправкой, что пункты
1-4 доказаны на уровне значений, а не живого ввода, и один пункт чеклиста сессии 1 (мобильный режим)
остался непокрыт.
