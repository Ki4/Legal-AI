> **Навіщо.** «Лікуєш наслідок, а не причину» — коли пійману причину помилки не записати в
> автозавантажуваний файл, та сама граблина повторюється в новому чаті. Сюди падають **повторювані**
> технічні пастки — коротко, правилом. Файл «росте від болю» і регулярно чиститься: застаріле —
> прибирати. Не дублювати сюди архітектуру (це `DECISIONS.md`) чи беклог (`IMPROVEMENTS.md`).
>
> Формат запису: **🪤 Симптом → Причина → Правило.** Нове додавати в кінець відповідної секції.

## Середовище / тулінг

### 🪤 PowerShell псує кирилицю у файлах і workflow JSON
- **Причина:** Windows PowerShell 5.1 пише UTF-16 LE + ламає кирилицю в native-exe pipeline.
- **Правило:** редагувати/генерувати файли з кирилицею через **Node.js або Bash-tool (UTF-8)**, не
  через PowerShell. n8n workflow оновлювати лише скриптами (`scripts/deploy-workflow.mjs`,
  `build-*.mjs`). Memory: `feedback_n8n_api_updates`.

### 🪤 WebStorm-термінал (JediTerm) не скролить Claude Code TUI
- **Причина:** `Mouse reporting` JediTerm — ні Shift, ні PgUp/PgDn, ні зняття галки не помогли.
- **Правило:** великі звіти писати у `.md`-файл репо (Сергій відкриє в редакторі), а в терміналі —
  стисло. Memory: `feedback_reports_to_file`.

### 🪤 Session-limit тарифу вбиває субагентів молча → частковий результат ≠ повний
- **Симптом:** під час Workflow-ревью частина verify-агентів падає на «You've hit your session limit»,
  а workflow повертає `confirmed: []` / «0 знахідок» — зовні НЕвідрізнимо від чистого дифу (s73: усі 3
  агенти впали → «0», після перезапуску 12 знахідок + blocker; s74: 6/18 verify впали).
- **Причина:** ліміт тарифу — акаунт-рівневий, вбиває агентів посеред прогону; упалий прогін виглядає
  як чистий → хибний висновок «перевірено/готово».
- **Правило (як вести довгі задачі під бюджетом):** (1) **чекпойнтити кожну перевірену одиницю в git
  ОДРАЗУ** — робота переживе смерть сесії, не копити багатокроковий результат у діалозі; (2) мірити
  fan-out під бюджет ДО запуску (агентів × ~40–60k токенів), тісно → менше/легше агентів або фази з
  читанням між ними; (3) після parallel/workflow дивитись `agents_error`/`<failures>`/`unverified` —
  НЕ ставити ✅ на упалому прогоні, workflow має ПОВЕРТАТИ `unverified`-список; (4) відновлення:
  ліміт скидається за годинником → перезапуск; **resume-з-кешу лише якщо код не мінявся**, після
  правок — свіже ревью по новому HEAD (старі знахідки про неіснуючий код); (5) падати гучно — казати
  Сергію, коли результат частковий. Memory: `feedback_long_tasks_token_budget`, `feedback_workflow_session_limits`.

## n8n / workflow

### 🪤 Паралельні гілки в n8n v1 не виконуються (`Node hasn't been executed`)
- **Причина:** n8n v1 execution depth-first **не чекає** fan-out — паралельні фетчі повертають
  «не виконано», workflow падає на порожній черзі/графі (session 51, `law-change-digest`).
- **Правило:** робити **лінійний ланцюг** фетчів (Fetch A → Fetch B → Fetch C), а не fan-out;
  `executeOnce` + `alwaysOutputData` щоб ланцюг переживав порожній результат.

### 🪤 Дві гілки fan-out пишуть ту саму колонку → пізніша затирає
- **Симптом:** одна гілка ставить `cases.status='preview_ready'`, інша (sibling того ж fan-out)
  пише `status='generating'` — у БД лишається `generating`, хоча обидва апдейти «спрацювали»
  (preview-module G3, session 54).
- **Причина:** n8n v1 depth-first проганяє ПЕРШУ гілку fan-out до кінця (включно з довгим хвостом),
  і лише потім — sibling-ноду; та виконується ОСТАННЬОЮ і затирає значення.
- **Правило:** колонку зі станом має писати РІВНО один вузол на кожен перехід (тут: Insert
  `generating` → Set Preview Ready `preview_ready`); sibling-апдейти НЕ чіпають спільну колонку.
  Перевіряти порядок наживо (читати рядок БД після прогону), не лише по тестах графа.

### 🪤 Секрети у workflow JSON
- **Причина:** закомічений workflow з реальними ключами = витік.
- **Правило:** у комічених JSON — лише `YOUR_*`/плейсхолдери; реальні ключі інжектить
  `deploy-workflow.mjs` у памʼяті через Global Config-expression (`Bearer {{GROQ_API_KEY}}`).
  Memory: `feedback_security_secrets`. Після API-апдейту workflow — `deploy-workflow.mjs` сам
  відновлює live credential-IDs (ручний Global Config-фіксап більше не потрібен).

### 🪤 CRON `schedule:` у `law-monitor.yml` тримається OFF
- **Причина:** увімкнення авто-флипне залежні послуги (divorce+alimony) у `needs_review` доти, доки
  2 виявлені зміни законів не розрулені.
- **Правило:** не вмикати `schedule:` до розрулення + sign-off Олі (#33, ~після 1 липня).

## Юридична логіка / документи

### 🪤 «ч.7» ст.175 ≠ «п.7 ч.3» ст.175
- **Причина:** легко сплутати **частину 7** статті з **пунктом 7 частини 3** (session 51, #87).
- **Правило:** при роботі зі статтями ЦПК/СК звіряти **частину vs пункт** дослівно з джерелом; не
  вгадувати нумерацію (це теж кейс anti-hallucination — стаття закону не підставляється з памʼяті).

### 🪤 Parity divorce/alimony = engine===legacy-builder, не лише голдени
- **Причина:** `*-template-parity.test.js` порівнює рендер шаблону (`services/*.document.txt`) з
  legacy JS-білдером (`*-document.js`) **байт-у-байт** (+ голдени). Нова юр-логіка лише в шаблоні
  ламає 117 parity-тестів (session 52, #87).
- **Правило:** будь-який новий блок/умову вносити в **ОБИДВА** файли синхронно (шаблон + legacy-білдер),
  матчити конвенції движка: порожнє поле → `________` (FALLBACK, через `val()`), standalone if/else-теги.
  Потім регенерувати голдени (engine===builder, тож рендер достовірний). Legacy-білдер живий як оракул до #52.

### 🪤 Хибний відкат коректного склоніння ПІБ псує якість
- **Причина:** надто строгий deterм. guard над AI-склоненням відкочував валідні форми у називний.
- **Правило:** stem-guard тримати **LENIENT** — відхиляти лише явний mismatch (підмінене слово /
  інша к-сть слів). Будь-яка зміна склоніння → прогнати parity-тести (263 байт-у-байт).

## Процес / верифікація

### 🪤 «Вже зроблено» на одному evidence виявляється завищенням
- **Причина:** claim з доку/памʼяті/власного висновку — це гіпотеза, не факт (двічі ловили за сесію).
- **Правило:** статус ✅ live потребує **≥2 згоджених evidence**, одне з яких — **invocation**, не
  лише definition; будь-яке протиріччя блокує ✅. Протокол: `docs/architecture/VERIFICATION-PROTOCOL.md`.

### 🪤 Зелений smoke ≠ робочий прод, якщо smoke обходить живу форму (issue #86)
- **Причина:** `test-webhook.mjs` слав вебхуку ключі **нової** конвенції (`defendant_*`) — усі smoke
  зелені, а жива TWA-форма (`form_config` з БД) збирала **стару** (`respondent_*`). Реальний сабміт
  давав документ з 16 дірами «________» (без відповідача взагалі) — місяцями непомітно. Здоровʼя-панель
  чесно горіла червоним, але її списали на «хибну тривогу» (двічі: демо s62 + Explore-агент вивів
  режим із міграцій замість живої БД).
- **Правило:** (1) smoke-ключі мають походити з **живого `form_config`**, не з sampleAnswers/фікстур;
  (2) `form_config` і `document_template` — одна одиниця деплою: заливати разом
  (`upload-form-config.mjs` + `upload-document-template.mjs`), інваріант «0 unmatched» на реальних
  конфігах у тестах; (3) `generation_mode`/стан прод-рядка звіряти по **живій БД**, не по міграціях;
  (4) червоний health на «робочій» послузі = розслідувати до кінця, не списувати на анализатор.

## Supabase / БД

### 🪤 `services.id` — INTEGER, не UUID (таблиця старіша за каталог міграцій)
- **Причина:** `services` створювалась через Dashboard до появи `supabase/migrations/`, з
  auto-increment `integer` id. Міграція 031 (`service_revisions`) впала на
  `FK … uuid and integer are incompatible` — новий код природно припускає UUID, як у решті таблиць.
  Показово: міграція 025 (`service_notes`) не випадково посилається на `services(slug)`, а не id.
- **Правило:** (1) FK на `services` — `INTEGER` (або на `slug`, якщо потрібна людська стабільність);
  (2) тип колонки чужої таблиці перевіряти по **живій БД** (`information_schema.columns`), не за
  аналогією з іншими таблицями; (3) клієнтський код не страждає — PostgREST приводить рядковий id.

### 🪤 Дві паралельні сесії беруть один номер міграції
- **Причина:** web-сесія і локальна сесія одночасно створили «наступну» `030_…` (template_editor і
  service_categories). Обидві застосовані в БД; у репо файл web-сесії перейменовано в `031_…`.
- **Правило:** перед створенням міграції — `git fetch origin main` і перевірити останній номер НА
  main, не лише локально; при колізії перейменувати ДО мержа (сама міграція idempotent — безпечно).

## React / UI (admin)

### 🪤 AnimatePresence-модалка лишає невидимий оверлей, що блокує всі кліки
- **Причина:** `<AnimatePresence>{open && <motion.div className="fixed inset-0 z-50">…}` іноді **не
  демонтує** оверлей після `open→false` — вузол лишається в DOM з `opacity:0` але
  `pointer-events:auto`, невидимо перехоплюючи **всі кліки на сторінці** (весь екран замерзає після
  першого закриття). Логіка (resolve/onClose) працює, але exit-анімація не завершує unmount; додавання
  `key` НЕ рятує (session 63, ConfirmModal). `opacity:0` **не** знімає pointer-events (на відміну від
  `display:none`/`visibility:hidden`).
- **Правило:** для оверлей-модалок з imperative-закриттям — `if (!open) return null` (лише
  enter-анімація через `motion` initial/animate; миттєве закриття для confirm-діалогу — норм). Якщо
  exit-анімація потрібна — верифікувати наживо, що вузол зникає з DOM (`overlays:0`), а не лише
  візуально. Перевірка: після закриття `document.querySelectorAll('.fixed.inset-0.z-50').length === 0`.

## Дані / контракт форма↔шаблон

### 🪤 Флип `generation_mode` js→template поза UI робить бойовим шаблон, що не проходив гейт
- **Причина:** publish/restore/form-save гейтяться dead-ref-предикатом (#88, s72), але зміна
  `generation_mode` робиться SQL-ом/dashboard-ом (в UI перемикача нема) — спляча чернетка стає
  бойовою без жодної перевірки. Саме цей клас відвантажив #86 (16 дір «________» у проді).
- **Правило:** перед будь-яким флипом js→template/hybrid — відкрити health-панель послуги
  (`ServiceViewPage`) і дочекатися 🟢 по dead refs (`collectDeadRefs` === 0 проти ЖИВОГО
  form_config). Довгостроково — render-time hard-fail (IMPROVEMENTS #104).
