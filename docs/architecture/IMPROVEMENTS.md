### 87. ЦПК ст.175 ч.7 — реквізити рахунку позивача
- **Звідки:** session 50 (2026-06-27) — верифікація law-monitor + детермінований diff редакцій ЦПК `2025-07-17 → 2026-04-24`. Знайдено реальною зміною закону, не вгадано.
- **Що змінилось:** ст.175 ЦПК доповнено **частиною 7** (Закон № 4833-IX від 07.04.2026): у позові **про стягнення грошових коштів** позовна заява має містити **реквізити рахунку позивача** (банк / небанківський надавач платіжних послуг). Для фізособи/ФОП — реквізити рахунку **АБО інформацію про його відсутність** + бажаний спосіб отримання коштів у разі задоволення позову.
- **Чому материально для нас:** аліменти = стягнення грошових коштів. Зачіпає **alimony** (завжди) і **divorce** із `alimony_claim=true`. Поточні форма+шаблон НЕ збирають і НЕ друкують реквізити рахунку → згенерований аліментний позов формально неповний за оновленим ЦПК.
- **Що зробити:** (1) додати у форму alimony (і гілку divorce+alimony) поле «рахунок позивача (IBAN)» з опцією «рахунку немає → бажаний спосіб отримання»; (2) друкувати блок у шаблоні в розділі реквізитів/прохальній частині; (3) citations: ст.175 ЦПК вже цитується (golden не дрейфує — змінилась лише редакція, не номер).
- **СК (2026-03-04 → 2026-05-25) — НЕ материально:** змінились ст.65/177/287, жодної нашої (105/110/112/141/150/157/180-184). Зафіксовано для повноти.
- **Пріоритет:** 🟡 важливо (юр-коректність аліментів). На підпис Олі 1 липня (формулювання блоку + чи треба IBAN обов'язково). Не блокує демо (документ генерується, питання формальної повноти).

- **Що ми будуємо послугу за послугою:**
  - `divorce` → [СК ст.105, 110, 183, ЦПК ст.175]
  - `alimony` → [СК ст.180, 181, 182, 232]

- **Зараз:** наявний `services.needs_law_review BOOLEAN` (міграція 007) і нова `services.status` (`active|needs_review|disabled`) описують частково те саме. `status` зроблено авторитетним джерелом правди для «чи обслуговувати послугу», а boolean лишено недоторканим — два сигнали замість одного.

- **Як краще:** після того як ніщо не читає `needs_law_review` — окремою міграцією видалити колонку (або перетворити на згенерований `status='needs_review'`).

- **Актуальність:** до того, як зʼявиться automated law-monitoring чи admin-UI ревʼю.

### 42. `law_deps` лишається в `watched_laws` JSONB (без нормалізованої таблиці)
- **Зараз:** звʼязок «закон → послуги» виводиться запитом по `services.watched_laws` (JSONB), окремої таблиці `law_deps`/`law_relations` немає.
- **Чому компроміс:** нормалізована таблиця = дублювання даних + синхронізація; на 2-3 послугах JSONB-запит достатній. Узгоджено з master-context («law_deps = розширення watched_laws»).
- **Як краще:** проміжний крок вже зроблено (G4) — канонічний реєстр-файл `scripts/law-registry.mjs` (ідентичність закону по URL) + `validate`/`normalize` тримають `watched_laws` у каноні. Далі при GraphRAG (#23) — нормалізована `law_relations`/`laws` з HITL-наповненням; тоді ж мігрувати зворотний індекс (див. #46).
- **Пріоритет:** 🔵 стратегічно (разом з #23 GraphRAG)
- **Актуальність:** коли послуг стане багато або JOIN-запити «закон→послуги» почнуть гальмувати.

### 43. Read-path kill-switch у боті неповний (меню частково захардкоджене)
- **Зараз:** меню послуг у `main-bot.json` будується Switch-нодою (захардкоджені пункти). Kill-switch на read-path лише НЕ віддає кнопку TWA для неактивної послуги; динамічного каталогу за `status` немає. Авторитетний guard — на write-path (`form-submit`), тож генерація все одно блокується.
- **✅ Зроблено частково (issue #61, session 38, 2026-06-19):** статичний чесний копірайт — 4 тексти (Welcome/Show Menu/Send Help/Service Unavailable) більше НЕ рекламують недоступні послуги як доступні: active = Розлучення+Аліменти, решта під «🔜 Скоро», ТЦК окремо «разом із юристом». Прибрано найгострішу UX-нечесність. Патчер `scripts/sync-main-bot-honest-catalog.mjs`. **Динамічна частина (нижче) лишається відкритою.**
- **Чому компроміс:** динамічний каталог = переробка бот-меню + Supabase-запит на КОЖНЕ повідомлення (зайва латентність). Статичний копірайт закриває UX-біль без цього. Безпека й так на сервері (write-path блокує генерацію).
- **Як краще:** будувати меню бота з `services WHERE status='active'` (динамічний каталог), щоб флип послуги авто-оновлював бот без правки тексту — **краще як admin-editable bot-copy** (юрист редагує тексти меню/категорій з адмінки), природно лягає в майбутній Service Builder (#18/#20). Рішення Сергія (session 38): зараз статика, динаміку/адмінку зробимо пізніше за потреби.
- **Пріоритет:** 🟡 важливо (UX: користувач не має бачити пункт, який потім скаже «недоступно») — гострий біль знято, лишилось auto-sync.
- **Актуальність:** до публічного запуску з 3+ послугами / коли послуги почнуть часто флипатись.

### 46. Реєстр законів = файл; нормалізована таблиця `laws` (v2)
- **Зараз (G4):** канонічна ідентичність закону живе у файлі `scripts/law-registry.mjs` (один `{slug,title,url}` на закон). Зв'язок «закон→послуги» — у `services.watched_laws` JSONB; зіставлення по **URL** (не по slug). `validate` ловить дрейф, `normalize` приводить до канону.
- **Чому компроміс:** n8n у рантаймі `watched_laws` не читає (статті вшиті в JS-шаблон), тож файла достатньо як SSoT для ідентичності + валідації. Повноцінна таблиця = міграція + бекфіл + синхронізація без реальної потреби зараз.
- **Як краще:** у v2/GraphRAG (#23, #42) винести закони в таблицю `laws` (PK = rada-id/URL), а `watched_laws` → FK-зв'язки; реєстр-файл стане сідом міграції. Заодно прибрати ризик розсинхрону файл↔БД.
- **Ризик зараз:** новий закон, доданий у `watched_laws` повз реєстр, не матчиться — мітигується командою `validate` (запускати після додавання послуги/закону).
- **Пріоритет:** 🔵 стратегічно (разом з #23/#42)
- **Актуальність:** коли зʼявляться вузли законів GraphRAG або багато послуг ділять закони.

### 47. `law_change_log` RLS — blanket authenticated, без per-tenant scoping
- **Зараз (migration 013):** панель ревʼю читає/оновлює `law_change_log` через політики `SELECT`+`UPDATE` для ролі `authenticated` (`USING (true)`). Будь-який залогінений юрист бачить усі рядки й може писати в будь-яку колонку рядка. `INSERT`/`DELETE` лишаються service_role-only (append-only з UI).
- **Чому компроміс:** зміни законів = глобальні законодавчі факти (СК/ЦПК зачіпають усіх), не per-tenant дані; юрист зараз фактично один (Ольга). Scoping/обмеження колонок = більший scope без реальної потреби.
- **Як краще:** (а) коли стане кілька юристів і журнал треба ділити — додати tenant-фільтр (напр. через `affected_services` → `services.lawyer_id`) або gate на `admin_users`/JWT-claim замість голого `authenticated`; (б) щоб юрист не міг переписати будь-яку колонку чи підмінити `reviewed_by` — замінити пряму `UPDATE`-політику на security-definer RPC `review_law_change(log_id, action, notes)`, що сам штампує `reviewed_by = auth.email()` + `reviewed_at = now()` і ігнорує решту колонок (або BEFORE UPDATE-тригер, що перезаписує ці поля з JWT).
- **Security-review (2026-06-11) — підтверджено, не блокує:** автоматичний скан позначив 3 знахідки на migration 013 (broad `USING(true)` UPDATE; bare-`authenticated` gate; client-stamped `reviewed_by` у `LawChangeLogPage.tsx`). **Головна мітигація:** публічна реєстрація вимкнена (`auth.settings.disable_signup=true`, invite-only) → роль `authenticated` = лише запрошена команда (зараз **1** акаунт). Тож «будь-який authenticated» = довірена особа, а не інтернет. Спуфінг `reviewed_by` у цій моделі — low-risk audit-nit. Усе вище («Як краще») — план хардингу до пункту-тригера нижче.
- **Пріоритет:** 🟢 nice-to-have, поки signup вимкнено + один юрист.
- **Актуальність (тригер хардингу):** ПЕРЕД увімкненням self-signup АБО онбордингом 2-го юриста — тоді обовʼязково RPC/тригер для штампу + role-gate (не голий `authenticated`).

### 48. CRON-моніторинг: умовні запити (If-Modified-Since/ETag) при рості реєстру
- **Зараз (фіча `cron-law-monitor`):** `scripts/check-law-updates.mjs` ітерує реєстр (унікальні закони по URL, дедуп спільних), на кожен — GET сторінки rada + парс «Редакція від». Є retry з backoff + jitter + повага до `Retry-After` (`scripts/lib/rada.mjs`), пауза між запитами. При 3 законах раз на тиждень навантаження мізерне.
- **Чому компроміс:** повний GET кожної сторінки масштабується лінійно з числом законів. При десятках-сотнях законів (ріст каталогу послуг) це і трафік, і ризик throttling.
- **Як краще:** умовні запити — зберігати `ETag`/`Last-Modified` сторінки per-law і слати `If-None-Match`/`If-Modified-Since` → незмінні закони повертають `304 Not Modified` (майже нульовий трафік + миттєва відповідь «не змінилось»). Потребує сховища ETag на закон (колонка/JSONB у `watched_laws` або майбутня таблиця `laws` #46) → окрема ітерація.
- **Пріоритет:** 🔵 стратегічно (разом із ростом каталогу / #46 нормалізованою таблицею `laws`).
- **Актуальність:** коли реєстр законів перевалить за ~кілька десятків.

### 49. Doc-engine: конвенція полів declension захардкоджена в Prepare Declension
- **Зараз (doc-engine #34):** шаблон сервіс-агностичний, але нода Prepare Declension досі збирає запит на склонення з фіксованих імен полів (`last_name`/`first_name`/`middle_name`, `defendant_*`, `marriage_place`, `children_details`). Нова послуга мусить використовувати ту саму конвенцію імен, інакше склонення не запрацюють (fallback — несклонене ПІБ, документ валідний, але стилістично гірший).
- **Чому компроміс:** divorce+alimony вже уніфіковані на цій конвенції; конфігурованість полів declension = окремий шар метаданих без реальної потреби при 2 послугах.
- **Як краще:** при 3-й+ послузі — декларація declension-полів у `services` (напр. JSONB `declension_fields: {plaintiff: [...], defendant: [...]}`), Prepare Declension читає її; разом з цим задокументувати конвенцію в гайді створення послуги.
- **Пріоритет:** 🟡 важливо (перший крок наступної послуги після divorce-порту)
- **Актуальність:** коли зʼявиться послуга, чия форма не вписується в поточну конвенцію імен.

### 50. Doc-engine фаза 2: типографіка Google Docs з `{{!style:}}` директив
- **Зараз (doc-engine #34):** движок ІГНОРУЄ зарезервовані директиви `{{!style: right|center|bold|indent|keep-with-next|keep-together|page-break-before}}` — документ іде в Google Docs одним plain-text `replaceAllText`, вся типографіка плоска (скарга Сергія: «відступи слабкі, далеко від ТОПу»).
- **Як краще:** рендерер фази 2 — движок повертає структуровані блоки (абзац + стиль з директив), нода доставки замість одного replaceAllText шле `documents.batchUpdate` з `insertText` + `updateParagraphStyle` (`alignment`, `indentFirstLine`, `keepWithNext`, `keepLinesTogether`, `pageBreakBefore`) + `updateTextStyle` (bold). Розриви сторінок — ПРАВИЛА, не позиції (DECISIONS). Шаблони вже містять директиви — переписувати їх не треба; голдени перегенеруються свідомо (вихід зміниться, це НЕ регресія).
- **Кроки:** (1) `renderBlocks()` поряд з `renderDocument()` + тести; (2) нода Build Replace Request → Build Batch Update; (3) шапка праворуч / заголовки по центру жирним / абзацний відступ / keep-правила; (4) ревʼю юристом еталонного документа → нові голдени.
- **Пріоритет:** 🟡 важливо (якість документа = конкурентна перевага; прямий запит користувача)
- **Актуальність:** наступна-через-одну сесія (після divorce-порту) або раніше, якщо якість стане блокером продажів.

### 72. Multi-template: кілька шаблонів на одну послугу
- **Зараз:** `services.document_template` — одна колонка TEXT на послугу. Dispatch у Build Document вибирає єдиний шаблон.
- **Навіщо кілька:** варіант для суду загальної юрисдикції vs апеляційний суд; «спрощена» і «повна» версія позову; A/B-тест формулювань; сезонні зміни (новий ПМ щорічно без правки коду).

Умова вибору — поле `conditions`: `{"court_type": "appeal"}` або `{"direction": "increase"}` — dispatches в Build Document читає `answers` і вибирає найточніший варіант, fallback — `is_default=true`. - **Пріоритет:** 🔵 при нагоді (потрібно лише коли кількість варіантів стає реальною потребою)
- **Тригер:** юрист просить два варіанти тексту для однієї послуги або виникає потреба в A/B-тесті.

### 17. Шаблони документів: від JS builder до Google Docs плейсхолдерів
- **✅ Здебільшого вирішено інакше (doc-engine #34, 2026-06-11):** обрано НЕ Google-Docs-плейсхолдери, а декларативний шаблон-DSL у БД + спільний движок (див. DECISIONS «Doc-engine»). - **Зараз (історичний стан на момент запису):** `divorce-document.js` генерує plain text → вставляється через один плейсхолдер `{{DOCUMENT_CONTENT}}` в Google Docs
- **Проблема:** Юрист не може редагувати шаблон (потрібно правити JS-код). Форматування базове.
- **Три підходи:**
  - **A) JS builder** (поточний) — для складних документів з умовною логікою (6+ if/else блоків). Повний контроль, тестується локально, 0% галюцінацій.
  - **B) Google Docs template з плейсхолдерами** — для простих документів. Юрист створює красивий шаблон з `{{PLAINTIFF_NAME}}`, `{{MARRIAGE_DATE}}` тощо → n8n робить batch replace. Юрист контролює форматування.

- **Рекомендація:** Підхід C для нових послуг. JS builder генерує секції, Google Docs шаблон визначає розташування і форматування. Юрист редагує шаблон у Google Docs, розробник — логіку в JS.
- **Пріоритет:** 🟡 важливо (блокує Service Builder)
- **Актуальність:** Потрібно до підключення другої послуги

### 18. Service Builder — конструктор послуг для юристів
- **Ідея:** Юрист самостійно додає нову послугу без розробника:
  1. Створює Google Docs шаблон з плейсхолдерами
  2. Налаштовує форму в адмін-панелі (поля, таби, умови)
  3. Система автоматично маппить плейсхолдери на поля форми
  4. n8n workflow заповнює шаблон і доставляє клієнту
- **Необхідні кроки:**
  1. Адмін-панель: конструктор форм (вже є базово)
  2. Google Docs API: парсинг плейсхолдерів з шаблону
  3. UI маппінгу: плейсхолдер ↔ поле форми
  4. n8n generic workflow: роутинг по service_slug → відповідний шаблон
- **Пріоритет:** 🟡 важливо (ключова фіча для масштабування)
- **Актуальність:** Після стабілізації 2-3 послуг вручну

### 26. Голосове заповнення форми через Telegram
- **Ідея:** Користувач у стресі — говорити простіше ніж друкувати 30+ полів. Відправляє голосове повідомлення боту → Whisper транскрибує → AI заповнює поля форми.
- **Поток:**
  ```
  Telegram voice message → n8n отримує audio_file_id
  → Whisper API ($0.006/хв) → текст
  → AI (той самий асистент форми з #25) → agent.setState(fields)
  → Користувач бачить заповнені поля → підтверджує
  ```
- **Чому Telegram, не Web Speech API:** органічно для нашої аудиторії, працює на iOS, якість вища.
- **Комбінується з:** #25 (AI-асистент форми) — голос це просто ще один спосіб дати контекст асистенту.
- **Вартість:** ~$0.006 за хвилину Whisper API, середня форма = 2-3 хв = ~$0.02 на кейс.
- **Пріоритет:** 🟡 важливо (після реалізації #25 AI-асистента)

### 23. GraphRAG — граф зв'язків між законами (поетапно)
- **Ідея:** Складні документи (розлучення + аліменти + поділ майна) вимагають розуміння зв'язків між законами, а не просто пошуку схожого тексту. Граф дозволяє агенту traversal-запитами знаходити ланцюжки: Ст. 109 СК → вимагає → Ст. 57 ЦПК → уточнюється → Постанова Пленуму №11.
- **Етап 1 (Supabase):** Додати таблицю `law_relations (from_chunk_id, to_chunk_id, relation_type)` — без нової інфраструктури, валідуємо концепцію.
- **Етап 2 (Neo4j):** Мігрувати якщо `law_relations` > 1000 записів або Supabase JOIN-запити стають громіздкими.
- **Наповнення:** AI витягує зв'язки автоматично → Ольга (юрист) перевіряє через інтерфейс HITL.
- **Пріоритет:** 🔵 стратегічно (після стабілізації 2-3 послуг)

### 24. Інтерфейс для Ольги (HITL — Human-in-the-Loop)
- **Ідея:** Юрист верифікує зв'язки які AI витягнув із законів. Жоден факт не потрапляє в граф без перевірки.
- **Поток:**
  ```
  AI читає закон → витягує зв'язки → pending_review
  Ольга бачить картку: "Ст. 109 СК → вимагає → Ст. 57 ЦПК. Джерело: [фрагмент]"
  → Підтвердити / Відхилити / Виправити → law_relations
  ```
- **Технологія:** CopilotKit Shared State (L6 з курсу Generative UI) — Ольга і AI в одному потоці, без окремої сторінки рецензування.
- **Frontend Tool:** `highlightInDocument` — AI підсвічує фрагмент тексту з якого витягнув зв'язок.
- **Пріоритет:** 🔵 стратегічно (після Етапу 1 пункту #23)

### 25. AI-асистент для заповнення форми (Shared State)
- **Ідея:** Замість того щоб заповнювати 20+ полів вручну — користувач описує ситуацію в чаті, AI заповнює поля форми в реальному часі. Користувач перевіряє і підтверджує.
- **Приклад:**
  ```
  Користувач: "Ми одружені 7 років, двоє дітей 5 і 8 років, я хочу опіку"
  AI заповнює: years_married=7, children_count=2, children_ages=[5,8], custody="plaintiff"
  ```
- **Технологія:** CopilotKit Shared State — agent.setState() пише в state форми, React компоненти читають.
- **Frontend Tools:** navigateToSection (переключати таби), highlightField (підсвічувати поле).
- **Конкурентна перевага:** Жоден український юридичний сервіс так не робить. Люди в стресі — вони розповідають ситуацію, а не заповнюють анкету.
- **Пріоритет:** 🟡 важливо (після стабілізації поточних форм)

### 54. Eval-набір для LLM-склонення (ground truth + поріг у CI)
- **Контекст:** 95% документа — детермінований JS-шаблон (тестується юніт-тестами, #19). Єдиний LLM-крок — відмінювання ПІБ/установ (`n8n/prompts/divorce-declension-prompt.txt`). Саме тут питання «скільки прогонів, щоб впевнитись, що генерація ОК».
- **Ключ:** у склонення є **об'єктивно правильна відповідь** (граматика укр. мови) → це не нечіткий eval, а closed-form: набір `вхід → правильні відмінки`, score = % точних збігів. «Скільки прогонів» = **покриття патернів** (~20–40 різних ПІБ: ч/ж, -ко/-енко/-ський, по батькові, подвійні, іноземні невідмінювані, назви установ у місцевому), а не повтори одного входу. temp=0.
- **Що зробити:** фікстура `scripts/evals/declension.golden.json` (Ольга/лінгвіст звіряє один раз) + ранер, що рахує % і падає нижче порога (старт: 100% на core-наборі). Завести в CI (#53). Ганяти весь набір при кожній зміні промпта/моделі.
- **Як краще (прибрати LLM зовсім):** оцінити `shevchenko-js` — детерміноване відмінювання укр. антропонімів з визначенням роду. Якщо покриє ПІБ → склонення переїде в шаблон (0 LLM, 0 токенів, 100% тестовано); установи в місцевому, можливо, лишаться LLM або хардкодом. Рівно той випадок, де LLM не потрібен.
- **Пріоритет:** 🔴 критично (це і є відповідь на «як перевіряти генерацію»; доповнює #30 Control Debt і #38 Faithfulness Gate)
- **Актуальність:** разом з #53.

### 53. CI-пайплайн (GitHub Actions): lint + test + test:docs + eval на кожен PR
- **Зараз:** `.github/` немає взагалі — тести (`vitest`, 32 шт.), `eslint` і golden-тест документа (`test:docs`) існують, але **ніщо не ганяє їх автоматично**. Жодного «зелено/червоно» на PR. Зливати з телефона наосліп — небезпечно.
- **Чому це фундамент:** CI = той самий «зелений чек», який дозволяє керувати мерджами з телефона (#56) і ловить регресії шаблону/склонення (#54). Без нього вся ідея «роботи з телефона» не тримається.
- **Що зробити:** `.github/workflows/ci.yml` — на `pull_request` і `push`:
  1. `npm ci` в `apps/client`
  2. `npm run lint`
  3. `npm run test` (vitest — детермінований шаблон, тести вже є)
  4. `npm run test:docs` (golden-master документа) — **спершу полагодити wiring, #55**
  5. (далі) eval-склонення з #54
  - опційно secret-scan (gitleaks) — ловить хардкод ключів (перегукується з #13а, #31)
- **Пріоритет:** 🔴 критично (фундамент безпечної розробки з телефона + regression-захист якості)
- **Актуальність:** перше, що варто налаштувати — решта (eval, branch protection) спирається на це.

### 55. Полагодити wiring npm-скриптів (scripts → repo-root) + дубль test-data
- **Зараз:** після переходу на монорепо утиліти живуть у **repo-root** `scripts/` (правило CLAUDE.md #10), а `apps/client/package.json` досі кличе їх як локальні: `test:docs`/`check:laws`/`scaffold` → `node scripts/...`. Запуск з `apps/client/` шукає `apps/client/scripts/` (її **немає**) → `npm run test:docs` падає `Cannot find module`. Тобто golden-тест документа де-факто не запускається, хоч файл `scripts/test-document.mjs` існує.
- **Дубль:** є і `./test-data/` (root), і `./apps/client/test-data/` — ризик розсинхрону фікстур після міграції.
- **Як краще:** (а) виправити шляхи в `apps/client/package.json` на root (напр. `node ../../scripts/...`) **або** додати root `package.json` зі скриптами-обгортками й ганяти з кореня; (б) звести test-data до одного джерела правди. Без цього CI (#53) не зможе викликати `test:docs`.
- **Пріоритет:** 🟡 важливо (блокує крок 4 у #53)
- **Актуальність:** перед увімкненням CI.

### 56. Branch protection + PR-flow для розробки з телефона

### 71. 🟠 Model-Agnostic екосистема — уникнення vendor lock-in

**Контекст:** ШІ-моделі — це регульована державою технологія (інцидент з Fable 5 довів це наглядно).
Відноситись до них треба як до будь-якого іншого зовнішнього сервісу в інфраструктурі: він може
зникнути, подорожчати, потрапити під санкції або бути відключений регулятором у будь-яку хвилину.

**Чотири паттерни захисту:**

**1. Уніфікований API (роутер/абстракція)**
Замість прямих запитів до Anthropic/Groq — бібліотека або власний proxy-шар, що приховує
конкретного провайдера за стабільним інтерфейсом. Варіанти: **LiteLLM** (OpenAI-сумісний API для
100+ моделей), **OpenRouter** (hosted proxy), самописний n8n-роутер (HTTP Request → вибір URL за
конфігом). Код ніколи не знає, куди йде запит — тільки роутер знає.
```
Code / n8n → LiteLLM proxy → Claude Fable 5
                           ↘ GPT-4o (fallback)
                           ↘ Groq llama (fallback)
```

**2. Fallback-ланцюжок (динамічне переключення)**
У конфігурації системи прописується пріоритет. При 503/429/403 або недоступності моделі —
автоматичне переключення без участі людини:
```javascript
// Приклад конфігу Global Config (n8n)
{
  "model_primary": "claude-fable-5",
  "model_fallback_1": "gpt-4o",
  "model_fallback_2": "llama-3.3-70b-versatile"   // Groq (безкоштовний)
}
```
n8n Code-нода або LiteLLM обробляє retry/fallback прозоро для бізнес-логіки.

**3. Назва моделі — тільки в конфізі, ніколи в коді**
`model_generation: 'llama-3.3-70b-versatile'` вже живе в Global Config-ноді (DECISIONS.md:
«Model Debt → конфіг-нода»). Це правильно. Наступний крок — не дублювати назву ніде в:
`n8n/prompts/`, скриптах, тестових фікстурах. Якщо модель зникла — адмін змінює **один рядок**
у Global Config → 5 секунд, нульовий деплой.

**4. Open-source резерв (self-hosted)**
Для критично важливих завдань — open-source модель на власному сервері (Llama 3.3, Mistral,
Qwen), яку не можуть відключити зовні:
```
VPS (Hetzner CX52, ~€18/міс) + Ollama → llama3.3:70b-q4
← fallback для hybrid reasoning при недоступності Groq/Anthropic
```
Для нашого кейсу (1 запит / хвилину на пілоті) — достатньо Groq free-tier. Self-hosted
актуальний при > 1000 doc/місяць або якщо Groq потрапить під регуляторний удар по Україні.

**Що зробити в нашому проекті:**

| Крок | Пріоритет | Стан |
|------|-----------|------|
| `GROQ_MODEL` + `GROQ_MODEL_FALLBACK` в Global Config; `prepareReasoning(modelName)` | 🟠 → ✅ | **DONE** (#40, `2ceed5c`) |
| Перед VPS-деплоєм: додати `GROQ_API_KEY=gsk_...` в `.env.local` і в env VPS | 🟠 | Чекає VPS |
| Fallback Code node: L3 Reasoning із `fetch()` + retry на GROQ_MODEL_FALLBACK | 🟡 | Після перших реальних запитів |
| LiteLLM або OpenRouter замість прямих HTTP до Groq | 🟡 | Після пілоту (потребує зовн. акаунту) |
| Self-hosted Ollama як cold reserve | 🟢 | Пізніше (VPS CX52, ~€18/міс) |

**Поточна схема (після #40):**
```
Global Config → GROQ_MODEL → prepareReasoning() → _groq_body.model → L3 Reasoning HTTP
                                                                         ↑ credential: Groq HTTP Auth
```
Groq API key зберігається як n8n credential `Groq HTTP Auth` (той самий що AI Declension).
`GROQ_API_KEY` в Global Config — placeholder для майбутнього Code node fallback (поки не використовується).

**Перед VPS:** додати `GROQ_API_KEY=gsk_...` до:
1. `apps/client/.env.local` (локально — для `deploy-workflow.mjs`)
2. VPS env vars (`/etc/n8n/.env` або Docker env) — щоб Code node fallback міг читати ключ і не залежав від n8n credential store

- **Пріоритет:** 🟠 → частково виконано. Залишок (Code node fallback) = після перших клієнтів.
- **Файли:** `n8n/templates/prepare-reasoning.js`, `scripts/sync-hybrid-nodes.mjs`,
  `n8n/workflows/current/form-submit.json`, `scripts/deploy-workflow.mjs`

### 77. 🟡 Формати документа + стилістика (PDF/DOCX export, send-as-file)

- **Що зараз:** єдиний вихід — Google Doc (Word-подібний), посилання у фінальному повідомленні бота. Користувач сам зберігає як хоче (Файл → Завантажити → потрібний формат). Кнопки «📥 PDF» / реальної відправки файлу НЕМАЄ — свідоме рішення (session 39): поки документ лежить тільки як Google Doc, окремий PDF-експорт передчасний.
- **Коли братись:** разом із проходом по **стилістиці документа** (типографіка Google Docs — частково є, #50) і **збереженню в різних форматах**. Тоді ж:
  1. **Inline-кнопка «📥 Завантажити PDF»** у фінальній картці бота — дешевий варіант: url на `https://docs.google.com/document/d/<id>/export?format=pdf` (працює, поки документ shared «anyone with link»).
  2. **Ідеальний UX:** бот сам експортує (Google Drive `files.export?mimeType=application/pdf`) і шле **PDF-файлом** у чат (`sendDocument`) — ~2 ноди + binary. Позбавляє юзера ходити в меню Google Docs.
  3. Можливо DOCX-експорт так само, якщо знадобиться подавати у Word.
- **Лімітований предперегляд (preview) — ВАЖЛИВО (Сергій, session 44):** показати користувачу *гарний* предперегляд документа перед/після генерації — напр. перша сторінка або частковий вигляд (вітрина якості: «ось як виглядатиме твій позов»). Подвійна роль: (а) крок підтвердження «все вірно» до фіналу, (б) тизер/upsell цінності. Технічно: рендер у PDF → перша сторінка як зображення (`sendPhoto`) або обрізаний/водяний PDF; уточнити обсяг (1 стор. / watermark / повний).
- **Цілісність ключових блоків (page-integrity) — ВАЖЛИВО:** ключові смислові блоки НЕ повинні розриватися між сторінками — шапка суду/сторін, прохальна частина «ПРОШУ» (всі пункти разом), блок дати+підпису, перелік додатків. Реалізується директивами `{{!style: keep-together|keep-with-next|page-break-before}}` (див. #50 фаза 2) при PDF/DOCX-рендері; юрист звіряє еталонний документ.
- **Зв'язок:** #50 (типографіка Google Docs — keep-правила вже описані), issue #65 (bot UX polish — фінальна картка з кнопками вже є, місце під PDF-кнопку зарезервоване).
- **Пріоритет:** 🟡 коли візьмемось за стилістику + формати збереження (не для поточного UX-проходу). Предперегляд + page-integrity = частина «гарного виводу» разом з PDF/DOCX.
- **🔬 Дослідження + рішення (2026-06-25, walkthrough із Сергієм).** Глибокий ресёрч вёрстки/тулчейну. Повний матеріал (НЕ дублювати тут): `docs/research/document-typography-and-toolchain.md` + журнал `docs/architecture/document-generation-design-notes.md` (Q1–Q6). Ключові НОВІ рішення поверх цього пункту:
  - **Дві школи вёрстки** (OOXML/Word vs CSS Paged Media) → **один источник → багато рендерерів** (HTML preview / DOCX edit / PDF). Формат вибирається **за сценарієм** (атрибут послуги/тарифу): preview=HTML, редагування=DOCX, продаж/анти-переиспользування=PDF-only.
  - **Стратегічний рендерер — `docx` (dolanmiu) + self-hosted Gotenberg** (LibreOffice + укр. пакет `hyphen-uk`): єдиний шлях «editable DOCX + приватний PDF з одного джерела». Headless Chromium для серверного PDF **дисквалифіковано** (немає словників переносу на Linux → «річки» пробілів). Fallback-альтернативи: DocRaptor/Prince ($$$), WeasyPrint (PDF-only). Вартість: ~€5/міс контейнер, per-doc ≈ 0; Google Docs зараз ~безкоштовно, але це стеля + PII-теча.
  - **NBSP-пасс у `render-document.js`** — окремий **найвищий-ROI** крок, працює навіть на Google Docs (приклеїти 1–2-літерні прийменники, не рвати `ст. 110`/`10 000 грн`). Не плутати з авто-переносом (потребує движка зі словником + тег `uk`). Запобіжник: не чіпати URL/коди/AI-склонені імена → негативні голдени.
  - **`keep-block` DSL-директива** → компілюється в keepNext-цепочку (лагодить «осиротілий підпис»: зараз `keep-together` на одному рядку = `keepLines`, склеює лише рядок, а не блок). Зафіксувати DSL→primitive маппінг (OOXML↔Docs↔CSS) як контракт портативності + `widow-control` (export-only).
  - **ДСТУ-точність (шрифт/поля/інтервал) = тригер міграції** з Google Docs на `docx`. ДСТУ 4163 — традиція/полировка, НЕ закон (зміст позова диктує ст.175 ЦПК → залишення без руху; типографіка — ні).
  - **Тести/evals — first-class** (Definition of Done): golden NBSP (+ негативні), contract «директива→примітив» на рендерер, **edge-layout fixtures** що форсують розрив (підпис не розривається), visual-regression (PDF→image). Деталі — журнал, розділ «Принципи».
  - Кросс-зв'язки: предперегляд+watermark → **#86** (вже детально, наш аналіз збігся), PII приватна доставка → **#57**, типографіка-директиви → **#50**, авторська система (семантичні ролі для юриста) → **#51**, CI+eval → **#53/#54**.
  - **🚧 Реалізується як `preview-module` (issue #83, session 54+):** монетизаційний потік превʼю→оплата→документ. У ПЕРШІЙ ітерації превʼю = **HTML-витяг** безпечного фрагмента в TWA (нуль нової інфри, #86-захист = відсутність суті), оплата — заглушка, доставка — signed URL із приватного Storage після `paid=true`. Рішення — `DECISIONS.md` «Превью-модуль…», ТЗ — `specs/features/preview-module/`.
  - **➡️ Production «по-серйозному» (відкладено на цей пункт):** **image-превʼю реальної стр.1** через Gotenberg `/screenshot` — додається ПРИ міграції рендеру на `docx`+Gotenberg (вище в цьому ж #77). Тоді майже безкоштовно (рендерер уже в стеку), а HTML-витяг лишається мобільним/fallback-варіантом. НЕ будувати окрему PDF→image-інфру (Vercel pdfjs / poppler) до Gotenberg — це викидний шматок.

### 86. 🟡 Захист предперегляду від копіювання (screenshot + AI-видалення watermark)
- **Загроза (Сергій, session 44):** якщо предперегляд (#77) показує майже готовий документ із watermark, недобросовісний користувач робить скріншот → просить ШІ прибрати watermark і «дозаповнити» решту → отримує документ безкоштовно. CSS/overlay-watermark особливо вразливий — сучасні inpainting-моделі знімають його за секунди.
- **Чи можна «чорний екран при скріншоті» (як стрімінг-платформи)? Здебільшого НІ в нашому стеку:**
  - «Чорне на скріншоті» у Netflix/банків = **апаратний DRM** (Widevine L1 / FairPlay / PlayReady): декодований кадр живе в захищеному hardware-буфері, який OS-композитор зачорнює при захопленні. Працює лише для DRM-захищеного **медіа** в **нативному** застосунку.
  - **Android** нативно: `FLAG_SECURE` → вікно чорніє на скріншоті/у recents (банки, гаманці). **iOS** не має API заблокувати скріншот — лише **детект постфактум** (`userDidTakeScreenshot`), реакція запізніла.
  - **Web / PWA / Telegram Mini App** (наш випадок): **немає API** заблокувати скріншот. Веб-сторінка не може зачорнити екран при захопленні; Telegram не дає Mini App такого хука (скрін-нотифікації є лише в secret chats, не для TWA). Десктопні хаки (детект PrtScn) тривіально обходяться.
  - **Аналоговий отвір:** навіть ідеальний цифровий захист обходиться фото екрана іншим телефоном → «заборонити скріншот» недосяжно в принципі.
- **Правильний підхід — захист НЕ-показом, а не приховуванням показаного:**
  1. **Частковий предперегляд** — показувати лише перші абзаци/першу сторінку; операційна суть («ПРОШУ», цитати статей, прохальна частина) у превʼю **фізично відсутня** (рендериться лише на сервері після оплати). Немає що «дозаповнювати» — ШІ може хіба галюцинувати, а це вже не court-ready.
  2. **Watermark вшитий на сервері** в самі пікселі/текст (не CSS-оверлей) + **flatten у зображення** (`sendPhoto`), не selectable-текст → не скопіювати текст, лише пікселі (часткові + з watermark).
  3. **Деградований предперегляд** — знижена якість, ключові пункти забляковані/розмиті на сервері (вшито в зображення).
  4. **«2 артефакти» (ідея Сергія) = по суті правильна модель:** preview-grade (частковий, watermark, image) vs full-grade (повний, чистий, файл після оплати) — генеруються окремо; повний ніколи не йде на клієнт до виконання умови.
- **Висновок:** ставку робити на **(1) — відсутність суті в предперегляді**, а не на блокування скріншота. Це і є природний рів: цінність = коректний юридичний зміст, якого ми просто не віддаємо в превʼю.
- **Зв'язок:** #77 (предперегляд + формати), #57 (приватна доставка PDF, не публічний лінк), #50 (рендер блоків — частковий рендер спирається на той самий движок).
- **Пріоритет:** 🟡 коли зʼявиться монетизація/платний предперегляд (зараз документ і так віддається повністю — захист передчасний, але рішення приймати ДО введення платного превʼю).

### 78. 🟡 Off-topic guard + тепле уточнення (vague-legal vs off-topic)

### 102. 🟡 Модалка підтвердження дій над послугою (єдиний дизайн, замість browser `confirm`)

- **Проблема (демо session 62):** деструктивні / статусні дії використовують нативний `window.confirm`
  (`confirm('Видалити послугу?')` у `ServiceCard`, `confirm('Видалити таб…')` у `FormBuilder`). Випадає з
  дизайн-системи (виглядає чужорідно), немає єдиного патерну, не можна пояснити наслідки дії.
- **Рішення:** один компонент `ConfirmModal` у `admin/ui/` (в дизайн-токенах, як решта кіту) з варіантами
  `danger | warn | info`: заголовок, тіло-пояснення, підтвердити/скасувати. Покриває: **Вимкнути послугу**,
  **Видалити послугу**, **Поставити на паузу**, видалити таб/поле — і майбутні дії над категоріями (#103).
- **Як працюватимемо:** (1) `ConfirmModal` у `admin/ui/`; (2) замінити всі `window.confirm` на нього;
  (3) єдиний хук `useConfirm()` для виклику. Зв'язок: дизайн-кіт (`/design`) отримує зразок модалки.
