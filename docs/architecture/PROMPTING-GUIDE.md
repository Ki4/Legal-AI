# Junior → Senior Prompts — Гайд

> Патерни для написання якісних промптів на основі курсу SDD.
> Мета: давати агенту контекст якого у нього немає, а не пояснювати що таке TypeScript.

---

## Головний принцип

Агент знає **як** писати код. Він не знає **що** ти хочеш побудувати і **чому**.

```
Джун:   "Зроби кнопку"
Синьор: "Зроби кнопку Submit яка блокується під час відправки форми
         і показує spinner. Після успіху — редирект на /success.
         Стилі через Tailwind, без кастомного CSS."
```

---

## Патерн 1: Бізнес-контекст замість технічних деталей

Давай **бізнес-контекст** — агент сам виведе технічні рішення.

```
Джун:   "Використай SQLite"
Синьор: "Це швидкий прототип для демо інвесторам.
         Нам не потрібна масштабованість прямо зараз."
         → агент сам обере SQLite або in-memory рішення
```

```
Джун:   "Зроби responsive"
Синьор: "40% наших користувачів — мобільні (Telegram).
         Форма повинна зручно працювати на екрані 375px."
         → агент сам застосує правильні breakpoints
```

---

## Патерн 2: Вказуй область впливу

При будь-якій зміні — кажи що ще потрібно оновити.

```
Джун:   "Додай поле 'дата народження' у форму"

Синьор: "Додай поле 'дата народження' у форму розлучення.
         Оновіть також:
         - specs/features/divorce-form/requirements.md
         - Supabase міграцію (нова колонка)
         - n8n маппінг полів
         - тести"
```

Це запобігає **drift** — коли код змінився, а документація/схема залишилась стара.

---

## Патерн 3: Критерії успіху (Validation Scorecard)

Завжди кажи як перевіриш результат.

```
Джун:   "Зроби інтеграцію з n8n"

Синьор: "Зроби інтеграцію форми з n8n webhook.
         Вважай задачу виконаною якщо:
         - форма відправляє POST на /api/submit
         - n8n отримує всі поля у правильному форматі
         - при помилці n8n — користувач бачить повідомлення
         - при успіху — редирект на сторінку підтвердження"
```

---

## Патерн 4: Обмеження та заборони

Кажи що **не** треба робити — це не менш важливо.

```
Синьор: "Реалізуй збереження форми.
         Не використовуй localStorage — дані містять PII.
         Шифруй перед відправкою (AES-256-GCM як у нас вже є).
         Не змінюй існуючий n8n workflow — тільки клієнтський код."
```

---

## Патерн 5: Явно називай skills і ресурси

Якщо знаєш що потрібен конкретний skill або файл — назви його.

```
Погано:  "Почни новий фічер"
Добре:   "Використай skill feature-spec щоб розпочати фічер alimony-form.
          Прочитай спочатку specs/mission.md і specs/tech-stack.md."
```

Це економить "thinking tokens" агента — він не гадає, а діє.

---

## Патерн 6: Розмір задачі

Великі задачі → дели на групи.

```
Погано:  "Реалізуй всю форму аліментів"

Добре:   "Реалізуй тільки Group 1 з плану: структуру компонентів
          і базові поля без логіки умовних полів.
          Зупинись після Group 1, я перевірю."
```

Менші кроки = менший cognitive debt = легше ревью.

---

## Патерн 7: Deep Review через субагентів

Коли хочеш незалежну перевірку:

```
"Запусти кілька субагентів для глибокого ревью проекту
 з урахуванням цієї зміни. Знайди:
 - невідповідності між кодом і спеком
 - потенційні баги
 - порушення наших архітектурних рішень з DECISIONS.md"
```

Субагенти не забруднюють основний контекст агента.

---

## Патерн 8: Research без переривання роботи

Прийшла ідея під час фічера — не кидай гілку:

```
"Не чіпай поточний код. Просто дослідж питання:
 чи варто нам перейти з Google Docs API на PDFKit для генерації документів?
 Запиши висновки в docs/research/backlog/pdf-generation-options.md"
```

Потім можна додати в roadmap з посиланням на файл.

---

## Шаблон промпту для початку фічера

```
Прочитай specs/mission.md, specs/tech-stack.md, specs/roadmap.md.

Ми розробляємо: [назва фічера]
Контекст: [1-2 речення про бізнес-причину]

Проведи зі мною інтерв'ю і створи feature spec:
  specs/features/[name]/plan.md
  specs/features/[name]/requirements.md
  specs/features/[name]/validation.md

Питай про: поля форми, умовну логіку, n8n кроки, критерії успіху.
Не починай реалізацію — тільки планування.
```

---

## Шаблон промпту для реалізації

```
/clear

Прочитай specs/features/[name]/plan.md і requirements.md.
Реалізуй Group [N] з плану.

Обмеження:
- [список обмежень з нашого стеку]

Не змінюй: [що не чіпати]
```

---

## Шаблон промпту для валідації

```
Прочитай specs/features/[name]/validation.md.

Перевір чи реалізація відповідає всім пунктам scorecard.
Якщо ні — виправ і оновіть відповідний спек.

Потім запусти субагентів для deep review змін на цій гілці.
```

---

## Чого НЕ треба писати в промпті

| Не пиши | Чому |
|---------|------|
| Назви змінних | Агент сам знає конвенції |
| CSS класи | Агент знає Tailwind/PicoCSS |
| Які файли створити | Якщо є спек — агент сам розбереться |
| "Будь ласка", "дякую" | Не впливає на результат |
| Детальні технічні кроки | Це мікроменеджмент — агент краще знає як |

---

## Золоте правило

> Якщо агент буде писати код 20-30 хвилин — витрать 3-4 хвилини на чіткий спек.
> Контекст якого у нього немає = твій унікальний внесок.
