# Spec-Driven Development — Наставление для Legal-AI

> Базується на курсі DeepLearning.AI "Spec-Driven Development with Coding Agents"
> Адаптовано під наш стек: React/Vite/TS + n8n + Supabase + Vercel

---

## Чому SDD, а не Vibe Coding

Vibe coding дає швидкий результат для одного компонента, але не масштабується.
У нас складний продукт: форми → n8n workflow → Supabase → PDF. Без спеку агент заповнює прогалини сам — і ми отримуємо технічний борг і drift між частинами системи.

> "The agent is the muscle, but the SPEC is the brain."

---

## Структура SDD у Legal-AI

```
specs/
  mission.md          ← місія, аудиторія, scope
  tech-stack.md       ← стек, обмеження, деплой
  roadmap.md          ← фази: поточні + майбутні документи

  features/
    divorce-form/
      plan.md
      requirements.md
      validation.md
    alimony-form/
      plan.md
      requirements.md
      validation.md
    ...
```

**Статус:** `specs/` ще не створено. Перед наступним фічером — генеруємо конституцію (див. нижче).

---

## Крок 0: Генерація конституції (один раз)

Це brownfield проект. Даємо агенту наші артефакти:

```
Прочитай CLAUDE.md, docs/architecture/IMPROVEMENTS.md,
docs/architecture/ARCHITECTURE.md, docs/architecture/DECISIONS.md.
Згенеруй конституцію проекту у трьох файлах:
  specs/mission.md      — місія, аудиторія, scope
  specs/tech-stack.md   — стек, обмеження, деплой
  specs/roadmap.md      — поточний стан + майбутні фічери

Задавай уточнюючі питання якщо потрібно.
```

Після генерації — перевіряємо вручну, правимо через агента (не вручну), коммітимо.

## Feature Loop — для кожного нового документа

### 1. Планування (окрема гілка)

```bash
git checkout -b feature/alimony-form
```

Промпт агенту:
```
Прочитай specs/mission.md, specs/tech-stack.md, specs/roadmap.md.
Ми розробляємо фічер: [назва].
Проведи зі мною інтерв'ю про цей фічер і створи:
  specs/features/[name]/plan.md
  specs/features/[name]/requirements.md
  specs/features/[name]/validation.md

Задавай питання про:
- які поля у формі
- логіку умовних полів
- що відбувається в n8n після сабміту
- як виглядає успішний результат (PDF, Telegram повідомлення)
```

Перевіряємо три файли → правимо через агента → коммітимо спек.

### 2. Реалізація

```
/clear
Прочитай specs/features/[name]/plan.md та requirements.md.
Реалізуй всі групи задач з плану.
```

Якщо фічер великий — реалізуємо групами по одній.

### 3. Валідація

Перевірка у такому порядку:
1. Переглядаємо diff у commit view
2. Запускаємо додаток, перевіряємо golden path
3. Перевіряємо edge cases (умовні поля, помилки валідації)
4. Якщо є тести — запускаємо
5. Просимо агента зробити deep review через субагентів:

```
Запусти кілька субагентів для глибокого ревью всього проекту
з цією зміною. Знайди проблеми та невідповідності зі спеком.
```

Якщо щось не так → просимо агента виправити **і код, і спек** одночасно.

### 4. Merge + Replanning

- Відмічаємо фічер у `specs/roadmap.md`
- Оновлюємо `apps/client/.claude/changelog.md`
- Коммітимо, мержимо в main
- Переглядаємо roadmap: наступний фічер ще актуальний?

## Чеклист перед кожним новим фічером

```
□ Попередній бранч змержено в main
□ specs/roadmap.md оновлено (попередній пункт відмічено)
□ Контекст агента очищено (/clear)
□ Наступний roadmap item досі актуальний
□ Незавершених задач немає
```

## Типові спеки для Legal-AI

### requirements.md для нової форми документа

```markdown
## Поля форми
- [список полів з типами і валідацією]

## Умовна логіка
- [які поля з'являються/зникають залежно від відповідей]

## n8n workflow
- Тригер: webhook від форми
- Кроки: валідація → генерація PDF → доставка в Telegram

## Обмеження
- Всі PII-дані шифруються AES-256-GCM перед записом
- PDF генерується через [Google Docs API / шаблон]
- Мова документа: українська

## Залежності
- Supabase таблиці: [список]
- n8n workflow: [назва]
```

### validation.md scorecard

```markdown
## Функціональна перевірка
- [ ] Форма відкривається в Telegram Mini App
- [ ] Умовні поля показуються/ховаються коректно
- [ ] Сабміт відправляє дані в n8n
- [ ] PDF генерується і відповідає шаблону
- [ ] Telegram повідомлення доставляється

## Edge cases
- [ ] Обов'язкові поля валідуються
- [ ] Форма працює на мобільному (responsive)
- [ ] Помилка n8n обробляється gracefully
```

## Правила роботи з агентом

**Завжди вказуй область впливу при змінах:**
```
Додай X і оновіть: specs/features/.../requirements.md,
будь-який пов'язаний код, тести.
```

**Не правь спеки вручну** — тільки через агента, щоб уникнути drift.

**Маленькі кроки = менше cognitive debt:**
Краще 5 маленьких коммітів, ніж один великий.

**Якщо прийшла ідея під час роботи над фічером:**
Не кидай гілку. Попроси агента записати дослідження в `docs/research/backlog/[тема].md`, потім додаси в roadmap.

---

## Replanning (між фічерами)

Окрема гілка `replan/...` для змін у конституції.

Приводи для replanning:
- PM сказав щось нове про продукт
- Знайшли проблему в архітектурі
- Хочемо додати новий інструмент у стек
- Потрібно автоматизувати частину workflow (skill)

При великій зміні → додаємо в roadmap як окремий фічер, не реалізуємо одразу.
