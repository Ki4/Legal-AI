# Legal AI — Skills & Harness: план дій

> Практичний план: що оформити як **Agent Skill**, що — як **ops-автоматизацію**,
> і як має виглядати наш **harness** (вся обвязка навколо моделі).
> Йди по чеклісту згори вниз. Посилається на ID з `IMPROVEMENTS.md` — не дублює їх.

---

## 🧭 Простими словами: Skills, Harness і де вони в нас

- **RAG** — *що* модель знає (дістає факти з бази у контекст). У нас — тільки для секції «обґрунтування».
- **Skill** — *як* виконувати наш рутинний воркфлоу. Папка з `SKILL.md`, яку Claude Code підвантажує сам, коли задача підходить.
- **Harness** — *чи спрацює це взагалі*: інструменти + перевірки + памʼять + права + пісочниця + оркестрація. Skill — це **один компонент** harness, не заміна йому.

**Ключове:** Skills у нас — це **не для кінцевого користувача**, а для **нас самих**, коли ми
працюємо через Claude Code / підтримуємо систему. Ми один раз записуємо «як ми робимо X у цьому
репо» — і далі агент робить це сам. «Чистий ROI» = нова інфраструктура не потрібна (за Claude Code
вже платимо), продакшн не чіпаємо, ризик нульовий, економія часу — одразу.

**Що НЕ робимо:** не «агентифікуємо» генерацію документів для користувача. Детермінований
шаблон (`render-document.js`) — це і є правильний harness для юридично-критичної задачі.

## 🏗️ Частина 2. Harness: як зараз і як має бути

Harness = вся обвязка навколо моделі. Ось наші компоненти — **зараз** vs **ціль**.

| Компонент harness | Зараз | Має бути |
|-------------------|-------|----------|
| **Agent loop / оркестрація** | Лінійний n8n-флоу (детермінований) | ✅ Лишити. Агент-петля — тільки в ops-шарі, не в генерації |
| **Інструменти (tools)** | Groq, Google Docs API, Supabase | + RAG-retrieve (`search_law_chunks`) як інструмент для однієї секції |
| **Context delivery** | Форма дає всі дані (без retrieval) | + **вузький RAG** лише для «обґрунтування» (#2) |
| **Skills** | Немає формалізованих (тільки CLAUDE.md + session) | ✅ S1–S4 у репо (`skills/`) |
| **Verification / eval** | 263 parity-тести, citation golden (#36) — але **тільки build-time** | + **рантайм QA-нода** на згенерований документ → `quality_score` (#30) |
| **Critic / grounding** | Немає | + **агент-критик** після генерації: кожна `ст. X` має існувати в `law_chunks` (#2б) |
| **Sensors (датчики)** | Немає | + **моніторинг законів** (#2а) — «сенсор», що ставить `needs_review` |
| **Permissions / sandbox** | AES-256, status kill-switch, без виконання коду | ✅ Лишити. DSL без `eval` — вже безпечно |
| **Memory / state** | `cases`, для dev — `session-summary.md` | ✅ + `quality_score` тренд у `cases` |
| **Observability** | `cases.status` (мінімум) | + дашборд: тренд якості, citation-drift у CI |
| **Human-in-the-loop** | Заплановано, не живе | + панель ревʼю Olga для flagged-документів (#24) |

**Підсумок одним рядком:** ядро (детермінований шаблон) лишаємо як є — це сила. Додаємо навколо
нього три речі harness, яких бракує: **(1) сенсор законів**, **(2) рантайм-перевірку якості +
критик-grounding**, **(3) вузький RAG для обґрунтування**. Плюс формалізуємо **dev-скіли**.
