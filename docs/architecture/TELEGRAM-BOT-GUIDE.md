# Telegram-бот — мапа поточного стану + сценарії

> Знято з живого n8n (`active: true` обидва), не з файлу-снепшоту — `main-bot.json` на диску каже `active: false`, але це застаріла експорт-метадата, реальний стан інший (перевірено через `/api/v1/workflows`).
> Мета доку: зафіксувати ЩО Є зараз (тексти, гілки, баги), щоб від цього відштовхуватись при «доведенні до ума» взаємодії користувача в Telegram. Без code change — це аудит.

---

## 1. Два окремих workflow

```
Telegram (чат) ──→ main-bot.json   ("Legal AI Bot v2")     — диспетчер: розмова → визначення послуги → кнопка форми
TWA (форма)    ──→ form-submit.json ("...v6 Hybrid Template") — приймає відповіді форми → генерує документ → шле в Telegram
```

Це означає: коли юзер пише боту текстом — працює `main-bot`. Коли юзер натискає кнопку і заповнює форму в Mini App — `main-bot` вже не задіяний, форма постить прямо у webhook `form-submit`. Документ повертається назад у той самий Telegram-чат через `Notify User`/`Send Doc Link` ноди `form-submit`, **не** через `main-bot`.

## 2. main-bot.json — покроковий флоу

```
Telegram Trigger
   ↓
Wait (1s)                    ← призначення незрозуміле, немає debounce/групування після нього (TODO §4.1)
   ↓
Normalize                    ← message OR callback_query → єдиний {_chatId,_userId,_text,_firstName,_type}
   ↓
Check Identity (Supabase identities)
   ↓
User Exists? ──NO──→ Create Profile → Create Identity → Welcome New User  [ТУПИК — §4.2]
   │
  YES
   ↓
Pre-filter (regex: вітання/коротке/офтоп — без AI, економить токени)
   ↓
Skip AI? ──YES──→ Show Menu  [ТУПИК, це і є відповідь]
   │
   NO
   ↓
AI Agent (Groq llama-3.3-70b, system prompt нижче) → {service_id, confidence}
   ↓
Switch(confidence)
   ├─ ≥0.9 → Get Service(high) → Is Active? ──yes→ Send TWA Button (deep-link)
   │                                          └─no→ Service Unavailable (bot)
   ├─ ≥0.4 → Get Service(medium) → Is Active? ──yes→ Ask Confirm (кнопки Так/Ні)  [КНОПКИ НЕ ОБРОБЛЯЮТЬСЯ — §4.3]
   │                                            └─no→ Service Unavailable (bot)
   └─ <0.4 → Send Help (загальний фолбек)
```

### 2.1 Тексти повідомлень (verbatim, з живого workflow)

| Нода | Коли | Текст |
|---|---|---|
| **Welcome New User** | перший контакт нового юзера | «Вітаю, {ім'я}! ⚖️\n\nЯ твій персональний AI-юрист. Допоможу з:\n• Розлучення та аліменти\n• Спори з ТЦК/ВЛК\n• Реєстрація ФОП\n• Пошук суду\n\nПросто напиши своє питання або опиши ситуацію ✍️» |
| **Show Menu** | вітання / `/start` / `/help` / `/menu` від існуючого юзера | «🏛️ *Юридична допомога*\n\n...\n📋 _Розлучення та поділ майна_\n💰 _Аліменти_\n🪖 _Спори з ТЦК/ВЛК_\n💼 _Реєстрація ФОП_\n🔍 _Пошук суду за адресою_\n...» |
| **Send TWA Button** | confidence ≥0.9, послуга активна | «⚖️ *{title}*\n\n{description}\n\nНатисніть кнопку нижче...» + inline-кнопка `webAppUrl` |
| **Ask Confirm** | confidence 0.4–0.9, послуга активна | «🤔 Схоже, ваш запит стосується: *{title}*\n\nЯ правильно зрозумів?» + кнопки `✅ Так` / `❌ Ні` |
| **Send Help** | confidence <0.4 | «🏛️ *Не зовсім зрозумів ваше питання*\n\n...Спробуйте переформулювати...» |
| **Service Unavailable (bot)** | послуга `status≠active` | «🛠️ На жаль, послуга *{title}* зараз тимчасово недоступна.\n\nМи оновлюємо її відповідно до змін у законодавстві. Спробуйте, будь ласка, пізніше.» |

### 2.2 AI Agent — system prompt (інтент-класифікатор)

Захардкоджений список послуг прямо в промпті:
```
ID 1: divorce       (розлучення, поділ майна, шлюб)
ID 2: alimony        (аліменти, утримання дітей)
ID 3: military        (спори з ТЦК, ВЛК, мобілізація, відстрочка)
ID 4: business        (бізнес, ФОП, реєстрація, договори)
ID 5: court_search    (пошук суду, підсудність)
```
Повертає `{service_id, confidence}`. **Не знає** про `alimony-change`, `divorce-with-children` (це не окремий `service_id`, тож не проблема) — §4.5.

Перевірено живі дані Supabase `services` (на момент аудиту):

| id | slug | title | status |
|---|---|---|---|
| 1 | divorce | Розірвання шлюбу | **active** |
| 2 | alimony | Стягнення аліментів | **active** |
| 3 | military | Спори з ТЦК | disabled |
| 4 | business | Бізнес / ФОП | disabled |
| 5 | court_search | Пошук суду | disabled |

→ 3 з 5 «послуг», які бот активно рекламує у Welcome/Show Menu, **не існують** як реальна пропозиція.

## 3. form-submit.json — релевантна для UX частина

```
TWA POST → Webhook → Validate → Get Service → Is Service Active? → Get Profile (guard) → Encrypt → Insert Case
   ↓
Notify User: "✅ Дякуємо! Дані отримано.\n\n📋 Послуга: {title}\n🔢 Кейс №: {id}\n\nДокумент готується... ⏳"
   ↓
Respond OK (200 до TWA — форма закривається)
   ↓
[АСИНХРОННО] Copy Template → Replace Placeholder → (Hybrid: L2→L3→L4 critics) → Apply Typography → Share Document
   ↓
Send Doc Link: "📄 Ваша позовна заява готова!\n\n👇 Відкрийте...\n{url}"
```

**Помилка в асинхронній частині (Copy Template, Replace Placeholder, ...) НЕ доходить до клієнта.** Є тільки:
```
Error Trigger → Format Error → Send Admin Alert (chatId="236581343", тобто ТІЛЬКИ адмін)
```
Клієнт назавжди залишається на «Документ готується... ⏳» без жодного фідбеку. **Це точно те, що сталось з кейсом `56e84825`** (Google OAuth впав на `Copy Template`, юзер не отримав ні документа, ні пояснення).

## 4. Знайдені сценарії/проблеми

### 4.1 `Wait` (1с) перед Normalize — призначення незрозуміле
Немає жодної групувальної/debounce-логіки після нього (просто йде в Normalize). Можливо, залишок від відлагодження race condition з Telegram (дублікати update), можливо — нічого не робить. **Потребує рішення: прибрати або задокументувати навмисну причину.**

### 4.2 Перше повідомлення нового юзера «проковтується»
`Welcome New User` — тупикова нода (`"main": [[]]` у connections). Тобто коли юзер пише БОТУ ВПЕРШЕ («Привіт, допоможіть з розлученням») — створюється профіль, надсилається вітання, а сам текст повідомлення **ніколи не йде в Pre-filter/AI Agent**. Юзер має написати ВДРУГЕ, щоб бот відповів по суті. Перше враження = бот ігнорує питання.

### 4.3 Кнопки `Ask Confirm` не обробляються — реальний баг
`Ask Confirm` шле кнопки з `callback_data`: `confirm_service_{id}` / `show_menu`. Коли юзер тапає кнопку → приходить `callback_query` → `Normalize` ставить `_text = "confirm_service_2"` (або `"show_menu"`) **як звичайний текст**. Далі: існуючий юзер → `Pre-filter` (рядок не вітання/не офтоп, ≥3 символи) → `_skip_ai=false` → летить **в AI Agent як юридичний запит**. Класифікатор намагається зрозуміти «confirm_service_2» як юридичне питання — найвірогідніше, low confidence → `Send Help` замість очікуваної дії (підтвердити послугу / показати меню). **Кнопки в `Ask Confirm` зараз імовірно не виконують те, що написано на них.** Потребує перевірки живим тестом + окремої гілки обробки `_type === 'callback_query'` до Pre-filter.

### 4.4 Реклама послуг, яких немає (IMPROVEMENTS #43, вже у бэклозі)
Welcome/Show Menu обіцяють ТЦК/ФОП/пошук суду — усі `disabled`. Військові спори — за стратегією прямо **blocked** (потрібен юрист-партнер), не просто «тимчасово». Поточний текст «тимчасово недоступна... спробуйте пізніше» звучить як збій, а не «це не наш scope (ще)».

### 4.5 AI-диспетчер не знає про `alimony-change`
Коли цей сервіс розблокується (~після Ольги), запит «хочу зменшити аліменти» все ще буде класифікований як `service_id=2` (звичайний alimony) — диспетчер не запропонує саме hybrid-сервіс зміни розміру. Не критично зараз (сервіс `disabled`), але стане проблемою одразу після флипу.

### 4.6 Немає live-статусу генерації (вже в roadmap v3.2, не баг — майбутня фіча)
Юзер бачить «готується ⏳» один раз і потім або документ, або тишу (якщо помилка — §3). Стрімінг статусу ("аналізую закони → формую документ → готово") — заплановано, не зроблено.

### 4.7 Старі посилання на форму (IMPROVEMENTS #4a, вже в бэклозі)
Кнопка `Send TWA Button` містить deep-link з `service` slug, зафіксованим у МОМЕНТ повідомлення. Якщо `form_config` оновився після відправки повідомлення — старе посилання все ще клікабельне, веде на форму зі старим контекстом.

## 7. ⛔ ПІДТВЕРДЖЕНИЙ інцидент (session 35) — німа тиша на «Алименти»

Відтворено живцем: існуючий юзер пише «Алименты» → **жодної відповіді**. Знято з n8n executions API (не з файлу):

- **Exec 54, `status=error`.** Весь pipeline відпрацював правильно: Normalize → Pre-filter → AI Agent (класифікував alimony, висока впевненість) → Get Service → Is Active? (active) → **`Send TWA Button` впав**.
- **Помилка Telegram:** `400 Bad Request: can't parse inline keyboard button: Text buttons are unallowed in the inline keyboard`. Означає: кнопка пішла **без дії** (лише `text`, без `web_app`).
- **Корінь — НЕ конфіг:** живе визначення ноди МАЄ `webAppUrl` (вираз валідний, резолвиться в `legal-twa.vercel.app?service=alimony&uid=...`). **n8n Telegram-нода (typeVersion 1.2, n8n 2.20.6) не серіалізує `web_app`-кнопку в inline-клавіатурі.** Обхід: слати кнопку через raw HTTP до Telegram API (`TELEGRAM_BOT_TOKEN` є в `.env.local` → Global Config).
- **Чому німо:** у `main-bot` **немає Error Trigger** (на відміну від `form-submit`). Будь-який збій після відповіді = тиша і для юзера, і для адміна.
- **repo ↔ live drift:** живий workflow (`updatedAt 2026-06-09`) відрізняється від `n8n/workflows/current/main-bot.json` (інші credential-id). Бекап живого знято: `n8n/workflows/.backups/main-bot.live-*.json`. **Не передеплоювати файл наосліп** — зб'є креди.

## 8. Рішення — запуск TWA (відповідь на §6 та концерн «initData»)

Як TWA читає контекст (`apps/client/src/App.tsx:225,271,283`): `service` ← `?service=`; `userId` ← `initDataUnsafe.user.id` АБО `?uid=` (fallback); `first_name` ← `initData`.

**Обраний формат кнопки — `web_app` на звичайний vercel-URL** (НЕ Direct-Link `t.me/bot/app`). Причини:
- Форма лишається звичайною веб-сторінкою → відкривається і поза Telegram (на майбутнє), і автономно тестується через Playwright (Claude може клікати сам; фінальний тап у Telegram — за Сергієм).
- Запуск через web_app-кнопку всередині Telegram → сторінка отримує підписаний `initData`.
- TWA вже підтримує обидва режими — клієнт майже не змінюється.

**#6 (безпека) закриває НЕ кнопка, а сервер:** TWA читає `initDataUnsafe` (непідписане) і приймає голий `?uid=` (підробляється). Справжній фікс — `form-submit` верифікує HMAC-підпис `initData` ботовим токеном і не довіряє `uid` без валідного підпису. Окремий security-кусок у write-path.

## 9. План робіт (хірургічно, по сесії на групу)

- **Issue (main-bot):** G1 Error Trigger → G2 робоча web_app-кнопка (raw HTTP) → G3 онбординг (фікс тупика нового юзера §4.2 + обробка callback_query §4.3 + привітання-префікс `_is_new` + 🔄 Інша послуга). Спільний контекст = `main-bot.json`.
- **Issue (#6 security):** серверна верифікація `initData` у `form-submit`, прибрати довіру до `?uid=`.
- **Беклог (IMPROVEMENTS):** динамічний каталог за `status` (#43), застарілі form-посилання (#4a), loading-індикатор у чаті, чесний список послуг (active/coming-soon/paused).
