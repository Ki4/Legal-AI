Автозаполнение договоров — PoC

Что сделали, почему так, альтернативы и как работает флоу · 09.07.2026

Коротко. Юрист готовит шаблон в обычном Word с плейсхолдерами {{поле}}, система собирает данные в JSON (форма/бот) и отдаёт готовый .docx + PDF + HTML-превью. Ядро — Word, движок подстановки — docxtpl (Python). Всё локально, без облака, за доли секунды.

Как работает флоу

1Подготовкаtemplate.docx + data.json
2Заполнениеdocxtpl подставляет данные
3output.docxготовый Word-файл
4PDFчерез Word, для печати
5ПревьюHTML через mammoth

Шаги 4 и 5 — параллельные выходы из одного output.docx. Всё вместе делает run_pipeline.py.

Синтаксис в шаблоне: {{ поле }} — простые поля; {%tr for … %}…{%tr endfor %} — строки таблицы (цикл по этапам); {% if … %}…{% endif %} — условные блоки (например, аванс).

Почему Word — ядро

АргументСуть
Юрист не меняет привычкиОн и так пишет договоры в Word — просто расставляет {{переменные}}. Учиться нечему.
Контроль вёрсткиШрифты, поля, разрывы страниц, неразрывные блоки. Для юрдоков критично (пример — подпись).
КонфиденциальностьДанные клиента не уходят в облако — обработка локально. Для юрфирмы часто обязательное требование.
Скорость и автономностьДоли секунды, без сетевых запросов и внешних API.
.docx → PDF тривиальноИз Word в PDF — один-в-один. Обратно (Google Docs → точный PDF) сложнее.

Почему не Google Docs

Не «плохо», а не подходит на роль ядра:

  • Работает через API — медленнее, нужен OAuth / сервис-аккаунты.
  • Данные уходят в облако Google — против конфиденциальности.
  • Хуже с динамикой — циклы и таблицы сложнее.
  • Меньше контроля над печатной вёрсткой.
  • Плюс: облачный шаринг → берём как «бонус/потом».

Границы PoC (что ещё не сделано)

  • PDF требует установленного Word (иначе LibreOffice-fallback).
  • Нет валидации обязательных полей JSON.
  • Нет пакетной обработки (один договор за прогон).
  • Приём данных от бота/формы пока имитируется — JSON кладём вручную.
  • Интеграция с Google Docs не реализована.
