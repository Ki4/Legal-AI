Playbook вариаций документа

Как реально используются 9 типов вариаций · стек: docx-источник + docxtpl + правила + форма · 10.07.2026

Модель. .docx — источник правды (вёрстка живёт в нём). Переменные и лёгкие условия — инлайн в docx (docxtpl). Тяжёлые правила/ветвления — в variations.json. Форма даёт сырые ответы → buildContext достраивает вычисляемое → docxtpl заполняет. Это гибрид Contract Express (разметка в Word) × docassemble (правила отдельно).
Форма (сырые ответы) → buildContext (ПІБ, рід, дати, дроби) → docxtpl заповнює → .docx / PDF / HTML │ │ │ variations.json computed layer вёрстка з самого docx (правила «що коли») (відступи, стилі збережені)

9 типов вариаций — детально

1Подстановка✓ у тебя есть
Чтовставить значение в место
КогдаПІБ, адреса, сума, дата, номер
Синтаксис{{ plaintiff_name }}, {{ total_amount }} {{ currency }}
ПримерПозивач: {{ plaintiff_name }}
Хранитьпрямо в docx
Граблитекст в Word бьётся на runs — при замене склеивай их; имя бывает во втором абзаце ячейки
2Условное включение✓ у тебя есть
Чтоблок появляется, только если условие истинно
Когдаemail, фактична адреса, аванс, додатки «за наявності»
Синтаксис{% if plaintiff_email %}…{{ plaintiff_email }}{% endif %}
Примерблок аванса {% if template_has_advance %}…{% endif %}
Хранитьпростое — инлайн в docx; сложное — правило в variations.json, в docx флаг
Граблипустое поле рендерится пустотой (не падает), но останется «висячий» разделитель — оборачивай весь фрагмент с меткой
3Взаимоисключающие альтернативы✓ у тебя есть
Чторовно один из N вариантов текста
Когдавыбор по полю формы — marital_status, спосіб аліментів
Синтаксис
{% if marital_status == 'never_married' %}Від наших стосунків у нас{% else %}У шлюбі у нас{% endif %} народилася дитина…
Примерветка alimony_type (частка / тверда сума)
Хранитьправило — variations.json (kind: variant), текст вариантов — в docx
Граблипорядок важен (первый истинный побеждает); всегда клади {% else %} как дефолт
4Повторение / циклы✓ у тебя есть
Чтодинамическое число строк/абзацев по списку
Когдаетапи робіт, кілька дітей, оснащення, перелік додатків
Синтаксистри строки-контроллера в таблице:
рядок 1:  {%tr for s in stages %}
рядок 2:  {{ s.num }} | {{ s.title }} | {{ s.deadline }}
рядок 3:  {%tr endfor %}
⚠️ Главная грабля (проверено): {%tr%} заменяет всю строку; жадный regex хватает последний тег → нельзя класть for и endfor в одну строку. Держи их в отдельных строках-контроллерах вокруг контентной.
Связьпри N>1 нужно согласование «дитина проживає» → «діти проживають» (см. #7)
5Вычисляемые / derived✓ у тебя есть
Чтозначение НЕ вводится, а вычисляется из полей формы
Когдасклейка ПІБ, дріб від кількості дітей, укр. дати, ініціали
Синтаксисне в docx, а в buildContext → готовый ключ, docx просто {{ plaintiff_name }}
Примерalimony_context.py: plaintiff_name, marriage_verb, alimony_fraction
Best practiceDRY: повторяющееся условие → одна именованная derived-переменная, не копия теста в 10 местах (LSC HotDocs)
6Кросс-ссылки и авто-нумерация✕ долг
Чтоссылка на пункт/додаток, автонумерация
Когда«згідно п. 3.2», «Додаток № N», нумерация, что «едет» при скрытых блоках
Как делатьнумерацию — стилями Word (нумерованный список), не руками; ссылки — Word REF-поля или derived-номер из buildContext
Статусу тебя пока ручная нумерация — технический долг
7Граммсогласование: рід / число / падеж⚠ частично · главный gap
Чтоправильная форма слова по роду/числу/падежу
Когда«уклав/уклала», «батько/мати», «дитина/діти», падежи ПІБ («Івановим Іваном»)
Рід/числокак именованная derived (best practice HotDocs): marriage_verb='уклала'. В docx — {{ marriage_verb }}
Падежи — главный gap: ни один open-source движок (docxtpl/Jinja) не умеет их нативно. Варианты: (а) AI-склонение с fallback в називний (ваш ai.* слой); (б) морфология pymorphy3 как Jinja-фильтр; (в) заранее просить форму у клиента.
Best practiceрод/число — явные именованные примитивы, не инлайн-{% if gender %} в каждом предложении
8Clause library / переиспользуемые блоки⚠ частично
Чтобиблиотека готовых клауз, вставляемых по условию, общих между шаблонами
Когдатиповые пункты (ЦПК ст.175 реквізити) — одинаковы в разных заявах
Как делатьвынести блоки в отдельные .docx-фрагменты/реестр; вставка {% include %}-подобно или INSERT IF из variations.json
Best practiceклауза = мини-шаблон со своими переменными; вставка всегда / по условию / выбор юзером (HotDocs)
Статусблоки внутри шаблона есть; общей библиотеки между услугами — нет
9Guided-interview ↔ разметка⚠ частично
Чточто и когда спрашивать (форма) и как связано с шаблоном
Две школыContract Express: опросник авто-генерится из разметки (один источник). docassemble: правила отдельно, движок сам решает что спросить.
У тебяформа и шаблон раздельно; связка намечена через anatomy_from_form.py + инвариант «zero unmatched». Цель — один источник: поле формы ↔ слот шаблона

Где хранить правило

Тип логикиКудаПочему
Подстановка, простое {% if поле %}инлайн в docx«на виду», просто
Вариант по одному полюправило в variations.json, текст в docxправило редактируемо, документ чистый
Сложное условие (много полей, И/ИЛИ)variations.jsonне мусорить docx нечитаемой логикой
Derived (склейка/рід/дроби)buildContextвычисление, не текст
Каскад (одно поле → много мест)одна derived-переменная, ссылка вездеDRY, single-point-of-change

Эвристика: лёгкое и локальное → в docx; тяжёлое, повторяемое или межшаблонное → в отдельный слой.

Тестирование шаблона

  1. Нет висячих тегов после заповнення ({{/{%) — есть в docpipe.lint
  2. Обязательные поля присутствуют (schema/anatomy) — есть
  3. Каждая ветка рендерится — прогон всех значений marital_status/alimony_type (как demo_variations.py)
  4. Целостность вёрстки — блок підпису не рвётся (verify_signature.py), відступи збережені
  5. Golden/parity — эталон на фикстуре, red не мёрджится

Чек-лист «как автору описать вариацию»

  1. Определи тип (1–9 выше).
  2. Реши где хранить (docx / variations.json / buildContext).
  3. Если derived — заведи именованную переменную (DRY).
  4. Если род/число/падеж — явный примитив, не инлайн в каждом предложении.
  5. Добавь тест ветки (прогон значений поля).
