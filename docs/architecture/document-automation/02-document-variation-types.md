# Playbook вариаций — как это используется на практике

_Прикладной справочник по 9 типам вариаций в нашем стеке: **docx — источник правды** +
`docxtpl` (инлайн-разметка) + `variations.json`/`buildContext` (правила/derived) + форма.
Каждый тип: что это · когда · синтаксис · реальный пример из нашей работы · где хранить · грабли._

---

## 0. Модель в одном абзаце

```
Форма (сырые ответы)  →  buildContext (derived: ПІБ, рід, дати, дроби)  →  docxtpl заповнює  →  .docx/PDF/HTML
        │                          │                                              │
   variations.json           computed layer                              вёрстка з самого docx
   (правила «що коли»)                                                    (відступи, стилі збережені)
```
Это гибрид: **Contract Express** (разметка в Word, вёрстка сохраняется) × **docassemble** (тяжёлые правила в отдельном слое). Лёгкие условия — инлайн в docx; тяжёлая логика/ветвление — в манифесте.

---

## 1. Подстановка (variable / merge field)

- **Что:** вставить значение в место.
- **Когда:** любое одиночное поле — ПІБ, адреса, сума, дата, номер.
- **Синтаксис (docxtpl):** `{{ plaintiff_name }}`, `{{ total_amount }} {{ currency }}`
- **Реальный пример:** `Позивач: {{ plaintiff_name }}` (в `make_alimony_docx.py`).
- **Где хранить:** прямо в docx.
- **Грабли:** текст в Word бьётся на *runs* — если менять значение вручную в коде, склей runs (мы это делали в `set_text`/`para_replace`). Имя лежит бывает во **втором** абзаце ячейки (ловили в подписи).

## 2. Условное включение (optional / conditional)

- **Что:** блок появляется, только если условие истинно.
- **Когда:** опциональные строки — email, фактична адреса, аванс, додатки «за наявності».
- **Синтаксис:** `{% if plaintiff_email %}адреса електронної пошти: {{ plaintiff_email }}{% endif %}`
- **Реальный пример:** блок аванса в договоре `{% if template_has_advance %}…{% endif %}`; email/ІПН в заяві.
- **Где хранить:** простое условие — инлайн в docx; сложное («якщо … і … або …») — правило в `variations.json`, а в docx только флаг.
- **Грабли:** пустое поле у docxtpl рендерится пустой строкой (не падает) — но останется «висячий» разделитель/пробел; оборачивай весь фрагмент, включая метку.

## 3. Взаимоисключающие альтернативы (variant / either-or)

- **Что:** ровно один из N вариантов текста.
- **Когда:** выбор по полю формы. Твой пример: `marital_status` → «Від наших стосунків…» vs «У шлюбі…»; спосіб аліментів `percent`/`fixed`.
- **Синтаксис:** `{% if marital_status == 'never_married' %}Від наших стосунків у нас{% else %}У шлюбі у нас{% endif %}`; для >2 — `{% elif %}`.
- **Реальный пример:** ветка `alimony_type` (частка/тверда сума) в `make_alimony_docx.py`; вступ про дитину.
- **Где хранить:** правило — в `variations.json` (kind: `variant`, cases[]), текст вариантов — в docx.
- **Грабли:** порядок веток важен (первый истинный побеждает — как HotDocs `ELSE IF`); всегда клади `{% else %}` как дефолт.
- **Best practice (индустрия):** сведи «включить/исключить/повторить» к одному конструкту где можно (урок Contract Express `[span]`).

## 4. Повторение / циклы (repeating sections, table rows)

- **Что:** динамическое число строк/абзацев по списку.
- **Когда:** етапи робіт, кілька дітей, оснащення, перелік додатків.
- **Синтаксис (таблица):** три строки-контроллера —
  ```
  рядок1: {%tr for s in stages %}
  рядок2 (контент): {{ s.num }} | {{ s.title }} | {{ s.deadline }}
  рядок3: {%tr endfor %}
  ```
  для абзацев — `{%p for … %}…{%p endfor %}`.
- **Реальный пример:** таблиця «Етапи робіт» (договор) и таблиця приборів (мед-форма).
- **⚠️ ГЛАВНАЯ ГРАБЛЯ (проверено):** `{%tr%}` заменяет **всю строку**; жадный regex хватает последний тег → **нельзя** класть `for` и `endfor` в одну строку. Держи их в отдельных строках-контроллерах вокруг контентной.
- **Множина:** при N>1 нужно ещё и согласование «дитина проживає» → «діти проживають» (см. #7).

## 5. Вычисляемые / derived (computed)

- **Что:** значение НЕ вводится, а вычисляется из полей формы.
- **Когда:** склейка ПІБ (`last+first+middle`), дріб від кількості дітей, дати в укр.форматі, ініціали.
- **Синтаксис:** не в docx, а в `buildContext` (Python/JS) → отдаёт готовый ключ, docx просто `{{ plaintiff_name }}`.
- **Реальный пример:** `alimony_context.py`: `plaintiff_name`, `marriage_verb`, `alimony_fraction`, `fmt_date`.
- **Где хранить:** в `buildContext` (computed layer), помечено в `variations.json` (kind: `computed`, depends_on).
- **Best practice (DRY / LSC HotDocs):** повторяющееся условие → **одна именованная derived-переменная**, не копия теста в 10 местах. Поменяется формулировка — правишь в одном месте.

## 6. Кросс-ссылки и авто-нумерация (пока нет — как добавить)

- **Что:** ссылка на пункт/додаток, автонумерация пунктов.
- **Когда:** «згідно п. 3.2», «Додаток № N», нумерация, которая «едет» при скрытых блоках.
- **Как делать:** нумерацию — **стилями Word** (нумерованный список), не руками (иначе при скрытом блоке номера собьются — мы это отмечали в договоре). Ссылки — либо Word REF-поля, либо derived-номер из `buildContext`.
- **Статус:** у тебя пока ручная нумерация; это долг.

## 7. Граммсогласование: рід / число / **падеж** (славянский — главный gap)

- **Что:** правильная форма слова по роду/числу/падежу.
- **Когда:** «уклав/уклала», «батько/мати», «дитина/діти», и **падежи** ПІБ («Івановим Іваном», «у Шевченківському відділі»).
- **Как делать у нас:**
  - **Рід/число** — как **именованная derived-переменная** (best practice HotDocs `he/she/they-X`): `marriage_verb='уклала'`, `child_word='дитина'/'діти'`. В docx — просто `{{ marriage_verb }}`.
  - **Падежи** — ⚠️ **ни один open-source движок (docxtpl/Jinja) не умеет их нативно**. Варианты: (а) AI-склонение (как в вашем `ai.*` слое) с fallback в називний; (б) морфология-библиотека (`pymorphy2`/`pymorphy3`) как Jinja-фильтр; (в) для ПІБ — заранее просить у клиента форму или склонять через словарь.
- **Реальный пример:** `detect_gender` + `marriage_verb` в `alimony_context.py`; ваш `ai.defendant_instrumental` в проде.
- **Best practice:** делай род/число **явными именованными примитивами**, а не инлайн-`{% if gender %}` в каждом предложении.

## 8. Clause library / переиспользуемые блоки (как ввести)

- **Что:** библиотека готовых клауз-кусков, вставляемых по условию, переиспользуемых между шаблонами.
- **Когда:** типовые пункты (ЦПК ст.175 реквізити, «досудове врегулювання не проводилось») — одинаковы в разных заявах.
- **Как делать у нас:** вынести повторяющиеся блоки в отдельные `.docx`-фрагменты или в реестр клауз; вставка — `{% include %}`-подобно или `INSERT IF`-логикой из `variations.json`.
- **Best practice (HotDocs):** клауза = мини-шаблон (может содержать свои переменные); вставка `INSERT` (всегда) / `INSERT IF` (по условию) / выбор юзером.
- **Статус:** у тебя блоки есть внутри одного шаблона; общей библиотеки между услугами — нет.

## 9. Guided-interview ↔ разметка (свести к одному источнику)

- **Что:** что и в каком порядке спрашивать (форма) и как это связано с шаблоном.
- **Две школы:**
  - **Contract Express:** опросник **авто-генерится из разметки** документа (один источник).
  - **docassemble:** правила отдельно, движок сам решает что спросить (backward-chaining).
- **Как у тебя:** форма (`form_config`) и шаблон — раздельно; ты уже наметил связку через `anatomy_from_form.py` (форма → анатомия) и инвариант «zero unmatched». Двигаться к **одному источнику**: поле формы ↔ слот шаблона.

## Где хранить правило: docx inline vs variations.json

| Тип логики | Куда | Почему |
|---|---|---|
| Подстановка, простое `{% if поле %}` | **инлайн в docx** | «на виду», просто |
| Вариант по одному полю (`variant`) | правило в **variations.json**, текст в docx | правило редактируемо, документ чистый |
| Сложное условие (много полей, И/ИЛИ) | **variations.json** | не мусорить docx нечитаемой логикой |
| Derived (склейка/рід/дроби) | **buildContext** | вычисление, не текст |
| Каскад (одно поле → много мест) | **одна derived-переменная**, ссылка везде | DRY, single-point-of-change |

Правило-эвристика: **лёгкое и локальное — в docx; тяжёлое, повторяемое или межшаблонное — в отдельный слой.**

## Нейминг (из best practices)
- Derived-переменные — говорящие имена с ролью: `plaintiff_name`, `marriage_verb`, `alimony_fraction`.
- Повторяющийся тест → именованный флаг (`is_divorced`), а не копия условия.
- Комментарий рядом со сложным правилом (митигация «спрятанной логики»).

## Тестирование шаблона (закрываем пробел индустрии)
У тебя уже есть основа — доведи до правила:
1. **Нет висячих тегов** после заповнення (`{{`/`{%`) — есть в `docpipe.lint`.
2. **Обязательные поля** присутствуют (schema/anatomy) — есть.
3. **Каждая ветка рендерится** — прогон всех значений `marital_status`/`alimony_type` (как `demo_variations.py`).
4. **Целостность вёрстки** — блок підпису не рвётся (`verify_signature.py`), відступи збережені.
5. **Golden/parity** — эталонный вывод на фикстуре, red — не мёрджится (как ваши 263/117 фикстур).

## Итог: чек-лист «как автору описать вариацию»
1. Определи **тип** (1–9 выше).
2. Реши **где хранить** (docx inline / variations.json / buildContext).
3. Если derived — заведи **именованную переменную** (DRY).
4. Если род/число/падеж — **явный примитив**, не инлайн в каждом предложении.
5. Добавь **тест ветки** (прогон значений поля).
