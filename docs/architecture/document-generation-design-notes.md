## Принципы (standing) — 2026-06-25

### Тесты + evals — first-class, не «после»
Цель Сергея: **по возможности всё покрыть** проверками, чтобы процесс был **контролируемым**
(CI-гейт: красное не мёрджится). Каждая будущая задача из материалов идёт с тестами/evals в
Definition of Done. Founder отметил это И как приоритет, И как своё слабое место → я веду тесты/evals.

**Ключевое различие (Сергей изучает evals параллельно):**
- **Тесты** — для ДЕТЕРМИНИРОВАННОГО кода. Один вход → ровно один выход, бинарный pass/fail
  (golden / parity / unit / contract). Сюда: шаблонный движок, NBSP-пасс, рендереры, decision-tables.
- **Evals** — для НЕдетерминированного / LLM-выхода. Один вход → выход варьируется → меряешь на
  **наборе кейсов метрикой с порогом** (≥X% grounded, abstention-rate ≤ Y), а не бинарно за один
  прогон. Сюда: склонение, Tier-2 проза, критики. Инструменты: DeepEval / RAGAS / promptfoo.
- Ложится 1:1 на determinism-first: детерминированные ~95% → **тесты**, генеративный остаток → **evals**.
  Чем сложнее услуги (растёт генерация) — тем важнее evals → ввод evals = правильное направление.
- Реальность: «всё» нельзя покрыть одинаково — приоритет **по риску** (юридически критичные пути
  первыми). «Контролируемый процесс» = и тесты, и evals в CI на каждое изменение.

_(Детальная тест-стратегия по вёрстке/harness — в план-файле сессии; развернём в чек-листы при
формировании явных задач после walkthrough.)_

## Q1 (2026-06-25) — Мульти-формат вывода (HTML/DOCX/PDF) + как юрист описывает правила вёрстки

**Вопрос (Сергей):** Из HTML хорошо делается PDF, у Word тоже есть инструменты, а у Google Docs API
— не все. У нас задача, возможно, показывать preview даже в HTML, давать Word для дальнейшего
редактирования или PDF. Как покрыть все сценарии и выбирать нужный при необходимости? Как дать юристу
описывать эти правила максимально просто и интуитивно через интерфейс? И хотелось бы иметь гайд с
описанием «что за что отвечает и зачем» в том же интерфейсе.

**Предложение:**

### 1. Архитектура «один источник → много рендереров»
Не выбирать один формат, а зафиксировать **один абстрактный источник** и иметь **по адаптеру на
формат**. У нас это уже наполовину так: `render-document.js` выдаёт текст + `_style_hints`
(абстрактные намерения), `apply-typography.js` — адаптер под Google Docs. Добавляем ещё адаптеры за
теми же `_style_hints`:

```
   ОДИН ИСТОЧНИК (format-agnostic):
   template (текст + {{!style:}}) + answers + блок-библиотека
        │  render-document.js → text + _style_hints
        ▼
   HTML-рендерер      DOCX-рендерер     PDF                  Google Docs
   (preview)          (docx, edit)      (DOCX→Gotenberg)     (текущий)
   → CSS break-*      → keepNext/…      → LibreOffice        → updateParagraphStyle
```

- Источник правды один — директивы `{{!style:}}` («розеттская» таблица соответствия OOXML ↔ Docs ↔ CSS).
  Каждый рендерер переводит их в примитивы своего формата.
- Формат выбирается под сценарий в рантайме, не зашит:
  - **Preview → HTML** (мгновенный, `<iframe>` в админке/Mini App) — дёшево и отзывчиво при правке.
  - **Редактирование → DOCX** (`docx`-рендерер).
  - **Финал → PDF** (DOCX→Gotenberg: PDF и DOCX из одного источника + украинский перенос работает).
- ⚠️ Оговорка: HTML-preview и Gotenberg-PDF — разные движки → preview *похож*, но не пиксель-в-пиксель.
  Для черновой правки HTML отлично; для суд-точной сверки — кнопка «Точный PDF-preview» (медленнее).

Это паттерн **single source → multiple renderers** (intermediate representation): намерение пишется
один раз, форматов — сколько нужно.

### 2. Юрист описывает правила через «семантические роли», не через сырые директивы
Юрист не трогает `keep-with-next`/`break-inside`. Он работает с **именованными ролями** (как «стили»
в Word, а не прямое форматирование):

| Роль (выбирает юрист) | Что ставит система | Гайд в тултипе («зачем») |
|---|---|---|
| Заголовок розділу | center + bold + keep-with-next | щоб заголовок не повис унизу окремо від тексту |
| Блок підпису | keep-block (keepNext-цепочка) | щоб дата+підпис не лишились самі на новій сторінці |
| Новий розділ з нової сторінки | page-break-before | явний розрив сторінки |
| Звичайний абзац | indent + justify | стандартний вигляд |

- Юрист кликает роль — система сама ставит правильный механизм. Он думает в ролях, не в примитивах.
- **Гайд встроен в данные роли:** роль = `{label, primitives[], help_text, preview}`. `help_text` →
  тултип + боковая help-панель. Один источник кормит: (1) UI выбора, (2) встроенный гайд, (3) рендереры.
- Это **маленький registry ролей с метаданными** — интуиция «маленькие деревья со своими метаданными»,
  применённая к вёрстке.

### 3. Как покрываются все сценарии разом
Один источник + реестр семантических ролей → рендерер под формат выбирается автоматически по сценарию
(preview=HTML, edit=DOCX, final=PDF), юрист описывает только роли через интерфейс с тултипами-гайдом.

**Открытые подвопросы (на потом):** нужен ли «Точный PDF-preview» в MVP или хватит HTML; где живёт
реестр ролей (код vs БД vs per-service файл); порядок реализации рендереров.

## Q2 (2026-06-25) — Формат выхода = функция бизнес-сценария (и рычаг монетизации)

**Тезис (Сергей):** Нам нужны обе школы вёрстки — оба метода, а с учётом Q1 даже своего рода 3
формата. Потом определимся, в каких случаях какой. Например: для админки юриста и проверки — один;
для возможности дать пользователю самому дописать Word — DOCX; для предпросмотра — возможно HTML;
для некоторых продаж — **только PDF**, чтобы не переиспользовали, купив один документ.

**Предложение:**

Две школы (часть 2) = технология; 3 формата (HTML/DOCX/PDF) = выдача. Все из **одного источника**
(Q1 multi-renderer). «Какой формат» — рантайм-параметр сценария, не отдельная кодовая ветка.

| Сценарий | Формат | Почему |
|---|---|---|
| Черновой предпросмотр при правке | HTML | мгновенно, дёшево, в `<iframe>` |
| Юрист-ревью / суд-точная сверка | PDF (точный рендер) | то, что увидит суд; +HTML для скорости |
| Пользователь дописывает сам | DOCX | редактируемо в Word |
| Продажа «готовый документ», анти-переиспользование | **PDF-only** | нет редактируемого источника → труднее переиспользовать/перепродать |

**Формат как рычаг монетизации / анти-пиратства** (инсайт Сергея):
- PDF-only = базовый тариф: купил конкретный документ, а не шаблон.
- DOCX = выше тариф (редактируемо, можно переиспользовать под свой кейс) → дороже либо ограничено.
- ⚠️ Честно: PDF **не** делает переиспользование невозможным (текст копируется, печатается,
  переподаётся под другой кейс). Он убирает лёгкий путь «открыл .docx, заменил ПІБ, переподав» и
  «перепродав шаблон». Усиление: **watermark с ID/именем покупателя** (трассируемость), приватная
  генерация без публичной ссылки (стыкуется с PII-фиксом #57), при желании flatten/защита PDF.

**Решение-направление:** поддержать все 3 формата из одного источника; матрицу «сценарий → формат»
держать как **конфиг (атрибут услуги/тарифа)**, не хардкод. Формат становится частью tier/pricing-модели
и наследует kill-switch-паттерн (атрибут услуги).

**Открытый подвопрос:** точные пары «тариф → формат» и нужен ли watermark в MVP.

## Q3 (2026-06-25) — Переносы: NBSP-first (обязательно), авто-перенос — бонус

**Понимание (Сергей, подтверждено):**
- **NBSP (слой A)** — первый кандидат на внедрение: наивысший ROI, нулевой риск, работает везде вкл.
  Google Docs. Реализация — функция в `render-document.js`.
- **Авто-перенос (слой B)** — бонус; требует движка со словарём (docx+Gotenberg / WeasyPrint) +
  правильный языковой тег `uk-UA`. На Google Docs недостижим.
- Предохранитель NBSP-функции: НЕ трогать URL, email, коды, слоты со склонёнными AI-именами →
  в тесты как «негативные» голдены.

**Уточнение:** NBSP — обязательный **baseline независимо от движка** (держим даже на docx+Gotenberg,
т.к. авто-перенос на машине читателя в Word не гарантирован без укр. proofing-пакета). Авто-перенос —
полировка сверху. Это **два разных механизма**, не «или-или».

## Q4 (2026-06-25) — Тулчейн: стоимость, LibreOffice-риски, масштабирование, альтернативы

**Вопрос (Сергей):** Подробнее про краевые расхождения LibreOffice vs Word — какие риски? Сколько
стоит генерация? Google Docs сейчас ~бесплатно? Как распределять нагрузку при росте (помимо очереди)?
Google Docs делал для быстрой проверки результата — заменяемо; вопрос цены и выделенных потребностей.

**Ответ / предложение:**

**Стоимость:**
| | Google Docs (сейчас) | docx + Gotenberg |
|---|---|---|
| За документ | бесплатно (в квоте) | ≈ 0 (детерминированный код) |
| Инфра | $0 | ~€5/мес контейнер (можно ко-разместить с n8n) |
| Возможности | потолок + PII-течь | полный контроль + приватный PDF + editable DOCX |
- LLM в рендере не участвует → «стоимость генерации» = только фиксированный мелкий контейнер.
- Google Docs сейчас ~бесплатно (API в квоте) → был отличным прототипом (мгновенная проверка, 0 инфры).

**LibreOffice vs Word — риски + митигация:**
- Подмена шрифта (главный риск): нет шрифта в контейнере → др. метрики → сдвиг переносов/пагинации →
  может сломать keep-block. Митигация: установить точные шрифты (TNR / Liberation Serif) в образ.
- Мелкие отличия интервалов/переносов; сложные Word-фичи. У нас документы простые → риск низкий.
- DOCX (Word) и PDF (LibreOffice) могут чуть по-разному пагинироваться. Митигация: visual-regression
  (PDF→image diff); канонический артефакт — PDF.

**Утечка памяти:** Gotenberg сам управляет LibreOffice — встроенная опция «рестарт после N конверсий»
+ Docker restart-policy/health-check. Стандартно решаемо.

**Распределение нагрузки (помимо очереди):** Gotenberg stateless → (а) горизонтальные реплики за
round-robin LB (nginx/traefik); (б) job-queue (BullMQ/Redis) с N воркерами на свои Gotenberg.
Генерация не латенси-критична (секунды) → очередь с ретраями естественна. На 3 услугах хватит 1 инстанса.

**Альтернативы (дороже, на будущее, fallback):** DocRaptor / PrinceXML (hosted, коммерческий, turnkey
высокая верность, $$$); WeasyPrint (если когда-нибудь PDF-only достаточно).

**Решение-направление:** `docx`+Gotenberg — победитель по цена/качество под выделенные потребности
(приватный PDF + editable DOCX + контроль). Google Docs — быстрый заменяемый прототип. PII-течь (#57)
чинится отдельно и срочно через Drive `files.export` (без миграции).

## Q5 (2026-06-25) — ДСТУ vs содержание: приоритеты разработки + триггер миграции

**Важные выводы (часть 6 walkthrough):**
- **Содержание ≠ оформление — не смешивать.** Содержание позова диктует **ст. 175 ЦПК** (найменування
  суду, сторони/реквізити, вимоги, ціна позову, обставини, докази, додатки, підпис, дата) → нарушение
  = **залишення без руху (ст. 185)**. Оформление (ДСТУ 4163:2020: TNR ~14, інтервал 1–1.5, поля
  ~30/10–15/20 мм, по ширині, абзац ~1.25 см) — **традиция/полировка, НЕ основание вернуть позов**.
- **ДСТУ 4163:2020** — стандарт організаційно-розпорядчої документації; обязательность для приватного
  позивача **ограничена**. ⚠️ Клиенту НЕ подавать «закон требує саме такий шрифт».
- **Приоритет разработки:** harness **содержания** (критики / abstention / чек-лист ст. 175) — слой 1,
  критический; **типографика** — слой 2, полировка. Кривой абзац позов не вернёт; пропущенный
  реквизит — вернёт.
- **ДСТУ-точность = триггер миграции на `docx`.** Google Docs не управляет шрифтом/полями/интервалом →
  как только нужен ДСТУ-точный вид, переходим на `docx`+Gotenberg. Пока хватает «прилично» (+ NBSP) —
  Google Docs ок.

## Q6 (2026-06-25) — Монетизация: preview → оплата (value-first) + где держать гейт

**Вопрос (Сергей):** Человек видит частичный preview, потом платит (не платит вслепую). Как
отображать? Учли ли мы preview? Как делают подобное, какие практики?

**Ответ / предложение:**
- Модель **value-first** («сначала вижу результат, потом плачу») — верная, повышает конверсию
  (FastDoc / LegalZoom / Rocket Lawyer).
- Учтено **частично**: HTML-рендерер (Q1) — механизм показа. **Монетизационный** preview — НОВОЕ измерение.
- Практики «preview → оплата»: (1) **watermark «ЗРАЗОК»** поверх полного; (2) **частичный** (шапка +
  начало, дальше гейт «розблокувати за X грн»); (3) **redacted** (операт. части размыты/скрыты).
- ⚠️ **SECURITY:** НЕ рендерить полный чистый текст на клиенте и прятать CSS-ом (видно в DevTools).
  **Сервер ПРИДЕРЖИВАЕТ** чистую версию до подтверждения оплаты. Preview = watermarked/обрезанный
  серверный артефакт (картинка или HTML без операт. частей); delivered (после оплаты) = чистый
  PDF/DOCX (+ опц. watermark с ID покупателя — стыкуется с Q2 анти-переиспользованием).
- Расширяет матрицу Q2 осью **preview (до оплаты) vs delivered (после оплаты)** + платёжный гейт.

**Открытые подвопросы:** степень preview (сколько показывать), формат preview (image vs watermarked
HTML), интеграция платежа (Telegram Payments?), где хранится confirmed-флаг и как сервер его проверяет
перед выдачей чистого артефакта.
