## 3. Критика: GDPR / мед-данные — тонкости, которые надо добавить

> Претензия «основне GDPR зроблено» (#16) верна для семейных услуг. Для медицины — нет: данные о здоровье =
> **особая категория**, у неё отдельный правовой режим и в украинском законе, и в GDPR. Ниже — что именно
> меняется. Это ТЗ для T1; финальные ответы даёт ресёрч, не этот документ.

### 3.1. Правовая рамка — три слоя, не один
- **ЗУ «Про захист персональних даних» №2297-VI, ст. 7:** данные о здоровье = чувствительные, обработка
  запрещена по умолчанию; главное легальное основание для нас — **однозначное задокументированное согласие**.
- **Ст. 9 + порядок Уполномоченного ВР:** обработка данных «особого риска» (здоровье!) требует
  **уведомления Омбудсмана** (в течение 30 дней с начала обработки) и **ответственного лица** за защиту
  данных (ст. 24). Для семейных услуг этого не требовалось — для мед станет обязанностью. Проверить в T1
  актуальную процедуру (закон движется к GDPR-гармонизации, проект 8153).
- **Врачебная тайна** (Основы законодательства о здравоохранении ст. 39-1/40, ЦК ст. 286): мы не медучреждение,
  но факт «человек X лечился в учреждении Y» уже раскрывает состояние здоровья.
- **GDPR напрямую:** Украина не ЕС, но (а) аудитория в Telegram включает украинцев **в ЕС** (беженцы —
  Польша/Германия); если сервис им таргетируется — GDPR ст. 3(2) применим, для здоровья это ст. 9
  (explicit consent) + **обязательный DPIA** (ст. 35 — special category); (б) EU-legalization = будущая
  ставка стратегии → строить сразу по GDPR-планке дешевле, чем переделывать. **Решение по гео-скоупу
  волны 1 — явно зафиксировать в T1** (вариант: волна 1 = только UA, ЕС отложен — тогда DPIA-lite добровольно).

### 3.2. Минимизация — сильнейший инструмент, и он в нашем дизайне форм
- **M1 (запрос медкарты) можно спроектировать почти без медданных:** ФИО, учреждение, период, тип документа.
  Диагнозы для заявления на выдачу копии карты **не нужны**. Это делает M1 идеальным первым кандидатом
  ещё и по приватности — форсировать этот принцип на этапе form_config, а не после.
- **M3/M4 (жалобы) — настоящая специальная категория:** свободный текст «что случилось» будет содержать
  диагнозы и лечение. Правило: free-text поля мед-услуг = помечены sensitive → шифруются (как `cases.data`,
  миграция 008), **не отправляются во внешние LLM** без явного решения (см. 3.4).
- **Данные третьих лиц:** медкарта ребёнка/родственника/умершего — согласие даёт не субъект данных.
  В T1: чьё согласие нужно и какую галочку/текст показывать (законный представитель и т.п.).

### 3.3. Согласие — сейчас его нет как артефакта
Для чувствительных данных согласие должно быть **однозначным, отдельным и доказуемым**. Добавить:
- отдельный consent-экран в TWA **до** мед-формы (не строчка в общем дисклеймере);
- хранение факта: таблица `consents` (user UUID, версия текста, timestamp, услуга) — иначе согласие
  недоказуемо;
- версионирование текста согласия (юр-текст пишет/подтверждает Оля).

### 3.4. Инвентарь процессоров — у каждого канала своя дыра
| Канал | Проблема для медданных | Митигация |
|---|---|---|
| **Telegram** | Bot API не E2E; документ в чате лежит на серверах TG, DPA не получить | для мед-категории **дефолт = только защищённая ссылка** (разводка доставки #89/#90 уже есть — задать per-category политику, opt-in в чат для мед либо убрать, либо с отдельным предупреждением) |
| **Supabase** | регион проекта, PDF в Storage, signed URL 24ч = доступ по ссылке без auth | зафиксировать EU-регион + DPA; для мед — короче TTL ссылки и/или повторная выдача только через TWA |
| **Groq / LLM** | склонение ФИО шлёт только имена (ок), но hybrid-генерация фактов дела = медданные к US-процессору | правило: мед-услуги волны 1 = только `template` (нуль LLM-вызовов с payload); для будущей генерации — DPA/zero-retention или Anthropic с ZDR; решить в T1 |
| **n8n** | execution-логи хранят payload'ы форм → медданные в истории выполнений | для мед-workflow отключить/укоротить сохранение executions; на VPS (Hetzner = EU) — ок, ngrok-туннель в dev с реальными медданными — нельзя (только тест-данные) |
| **Vercel/TWA** | фронт не хранит, но webhook-payload транзитом | проверить логи функций (не логировать тела) |

### 3.5. Доступ и аудит
- RLS уже включён (005), но для мед добавить **audit-log доступа юриста** к делу (кто/когда открыл) —
  стандарт для health-data, дёшево на insert-триггере.
- Роли: медкейсы видит только юрист, закреплённый за категорией (связка с #103-категориями).

### 3.6. Retention и удаление — из nice-to-have в обязательное
- Ретеншн есть (009), но для мед решить срок отдельно (короче? юр-требования к хранению обращений?).
- **IMPROVEMENTS #64 (удаление по запросу + deletion-log) медтрек поднимает в блокирующие**: право на
  удаление чувствительных данных без работающего механизма = формальное нарушение с первого клиента.
  Не забыть Storage: SQL DELETE не чистит PDF (гочас s77) — удаление = Storage DELETE + SQL.

### 3.7. Прочее, что всплывёт в T1
- **Публичная privacy policy в TWA** (укр., с разделом про здоровье) — сейчас, судя по всему, нет.
- **Breach-план:** кому и в какой срок сообщаем при утечке (Омбудсман/субъекты) — одна страница в runbooks.
- **Военный контекст:** ВЛК/МСЭК-документы = здоровье + призывной статус; чувствительность выше медианной,
  учесть при решении «волна 1 — только M1 или M1+M3/M4».
- **DPIA-lite** (оценка воздействия) даже без формальной обязанности — полезный артефакт для разговора
  с Олей и будущими партнёрами/инвесторами.

### 3.8. Резюме критики
Стратегия «медицина = шаблонные позиции в том же движке» выдерживает проверку, **если** волна 1:
(1) стартует с M1, спроектированного без диагнозов; (2) только `generation_mode='template'` (нуль LLM
на медданных); (3) доставка = ссылка, не чат; (4) согласие как артефакт + уведомление Омбудсмана +
ответственное лицо; (5) #64 сделан до первого мед-клиента. Главный риск не «GDPR-штраф», а украинский
режим ст. 7/9 + репутация: одна утечка «жалобы на врача» убивает доверие вертикали целиком.
