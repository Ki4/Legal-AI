## 1. Главный вопрос: можно ли написать расширение, которое удобно добавляет услугу с ветвлениями?

**Да.** Пять необходимых способностей; четыре подтверждены документацией Microsoft (context7, 2026-07-15):

| Способность | API | Статус |
|---|---|---|
| Знать выделение | `context.document.getSelection()` | ✅ |
| Заменить выделение на `{{field}}` | `range.insertText(txt, Word.InsertLocation.replace)` | ✅ |
| Якорь на поле/блок | `range.insertContentControl()` + `.tag`/`.title`/`.appearance` | ✅ |
| Обернуть блок отдельными абзацами | `paragraph.insertParagraph(txt, "Before"\|"After")` | 📋 **T5** |
| Метаданные внутри файла | `Office.context.document.customXmlParts.addAsync` / `getByNamespaceAsync` | ✅ |

Последнее — подарок: `getByNamespaceAsync` ищет part **по namespace**, а `docx_meta.py:31` уже пишет и
опознаёт блоб по `urn:legal-ai:service-meta:1`. Python-сторона и надстройка уже говорят на одном языке.

**Но вопрос «можно ли» — не тот вопрос.** Механика есть. Настоящий вопрос — **что именно** надстройка
должна произвести, чтобы из этого родилась MCP-услуга. Ответ ниже, и он меняет форму задачи.

## 2. Из чего состоит услуга (факты, не догадки)

Инвентарь Explore-агента по репо. Это **не** «шаблон + форма» — это восемь вещей:

| Часть услуги | Где живёт сейчас | Несёт ли `.docx` |
|---|---|---|
| Текст документа | `n8n/templates/services/<slug>.document.txt` (SSoT в git) → копия в `services.document_template` | ✅ он и есть .docx |
| Поля: id/тип/лейбл/подсказки/опции | `services.form_config` JSONB ← `upload-form-config.mjs` | ✅ customXml |
| Ветвление документа | `{{#if}}` в тексте (движок A) / `{%p if %}` (движок B) | ✅ |
| Логика формы `show_if` | `form_config` (один уровень, без вложенности — `form.ts:28-31`) | ✅ |
| Валидация формата | библиотека на 6 правил: `email`/`phone`/**`inn` (контрольная сумма РНОКПП)**/`name`/`passport`/`iban` (`validators.ts`) | ✅ выпадашка |
| **Табы и порядок вопросов** | `form_config.tabs` — **выбрасывается из JSON-схемы** (`form-schema.ts`) | ⚠️ **канала нет** |
| **Привязка к законам** (`watched_laws`) | JSONB, **SQL-сид руками** на каждую услугу | ✅ **из цитат в тексте** |
| Дерево интервью, отказы, юр-guidance | скилл, **~150 строк прозы руками на услугу** | ⚠️ см. §4 |
| Вычисляемый слой (склонение, даты прописью) | соглашение об именах + код движка (`extract.py:36-60`) | ❌ никогда |
| Юр-константы | **хардкод в коде**: `REGISTRY` прожминимумы 2026, `alimonyFraction` ст.183 (`render-document.js:548-552`) | ❌ и это болячка |

### 2.1 🔴 Настоящая дыра — не в Word, а в ширине канала

Схема, которую видит LLM (`formConfigToJsonSchema`), **теряет**:
- **`tab`** — порядок и группировку вопросов. В схеме его нет **вообще**.
- **`validation`** — превращается в прозу `FORMAT_NOTES`, а привязка правила к полю сегодня **эвристика
  по регулярке над id поля** (`resolveValidationRule`: `/tax_number|ipn|inn|rnokpp/` → inn).
- **условную обязательность** — `required` попадает в схему, только если `required===true && !show_if`.

**Скилл существует ровно затем, чтобы компенсировать потерянное.** Отсюда 150 строк прозы на услугу —
их пишем **мы**, руками, и Word тут ни при чём. Пока канал узкий, любой Word-билдер упирается в потолок:
данные он даст, а услугу — нет.

### 2.2 ✅ Подарок: law-monitor подключается сам

Юрист **уже пишет** «ст. 180 СК України» в тексте. В репо есть регулярка цитат
(`serviceAnatomy.ts`), голдены `<slug>.citations.json` и `scripts/extract-citations.mjs`.
`watched_laws` матчится **по канонической ссылке** (`law-change.mjs:34-37`), не по slug.

Значит компилятор способен собрать `watched_laws` **из самого текста**, а law-monitor — живой и
доказанный (s79: реальный CRON-флип по СК 4824-IX) — начинает охранять услугу, рождённую в Word,
**с первой секунды и без единого SQL-сида**.

## 3. Что это значит: новый билдер — это компилятор, а не редактор форм

```
        ┌─────────────────────────────────────────┐
        │  ОДИН .docx  = единственный источник     │
        │  ├── текст документа + {%p if %}         │
        │  └── customXml: поля, табы, валидация,   │
        │      guidance, отказы, цитаты            │
        └───────────────────┬─────────────────────┘
                            │
                   КОМПИЛЯТОР (сервер)
                            │
        ┌───────────────────┼───────────────────┬──────────────────┐
        ▼                   ▼                   ▼                  ▼
  services-строка     JSON-схема тула     watched_laws        checklist
  (производная)       (широкий канал)     (из цитат)          (fail-closed)
```

Три следствия, каждое — смена модели:

1. **`services`-строка перестаёт быть источником и становится проекцией.** Её можно снести и пересобрать
   из `.docx`. Это и есть причина, почему «веб = зеркало» (решение №2) когерентно: редактировать
   проекцию бессмысленно — перезатрётся.
2. **Надстройка — не билдер, а редактор контракта.** Билдер = компилятор. Из этого следует порядок
   работ (§5): **компилятор доказывается вообще без Word**.
3. **Per-service скилл — это баг, а не фича.** См. §4.

## 4. Куда девается скилл (~150 строк прозы на услугу)

Разложил построчно то, что сегодня написано руками в `alimony-claim/SKILL.md`:

| Что в скилле | Куда уходит | Кто автор |
|---|---|---|
| Порядок табов (`:56-61`) | данные блоба → **расширенный канал схемы** | юрист (панель) |
| Дерево routing: divorce vs alimony vs оба (`legal-intake:22-28`) | поле контракта `applies_when` / `not_applies_when` | **юрист, прозой в панели** |
| Отказы: имущество/опека — не эта услуга (`:27-28`) | там же | **юрист** |
| Юр-основания, номера статей (`:23-29`) | цитаты **из текста** → §2.2 | выводится |
| Документы к подготовке (`:31-39`) | `required_checklist` (уже data-driven) | юрист |
| Формат-лор: `children_details` = ДД.ММ.РРРР, не ISO (`:47-54`) | `hint` поля (уже есть в контракте!) | юрист |
| Протокол интервью: по одному вопросу, сводка, подтверждение (`:31-41`) | **общий роутер, один на всех** | мы, один раз |
| Обработка `service_unavailable` (`:38`) | общий роутер | мы, один раз |

**Вывод: ни одна строка не обязана быть per-service кодом.** Всё либо данные, которые авторит юрист,
либо generic-протокол, который пишется один раз. Цель «ноль прозы на услугу №10» — достижима, и это
не лозунг, а разбор по строкам.

Ключевой сдвиг: **отказы и границы услуги — это юридическое суждение, а значит авторская работа
юриста, а не наш код.** Сегодня их пишем мы. Это и есть та самая исходная боль, просто в неочевидном месте.

## 5. Что структурно НЕ придёт из Word — назвать и заморозить

Честный список. Если это не назвать, «ноль кода» станет ложью на третьей услуге.

1. **Вычисляемый слой** (склонение, даты прописью). Это код движка B + соглашение об именах
   (`extract.py:36-60`: `<party>_<case>`, `<date>_words`). Панель обязана **показывать** доступные
   вычисляемые ключи (она может — `derived_sources` уже их считает), но не определять их.
2. **Юр-константы.** Сегодня прожминимумы 2026 и дробь ст.183 захардкожены в `render-document.js`
   (движок A). Для новых услуг движка B это **нельзя повторять**: константа в коде = ежегодный
   тихий дрейф в суде. Предложение: таблица `legal_constants` (значение + период действия + источник),
   и law-monitor охраняет её так же, как статьи. **Вне скоупа этого трека — но записать сейчас.**
3. **Технический потолок Office Add-in.** Он не VBA: нет события «юрист правит текст», нельзя
   заблокировать сохранение. Поэтому испорченный шаблон **ловится компилятором при публикации**, а не
   предотвращается в Word. Это архитектурная данность и второй аргумент за гейты на сервере.

## 6. Развилка представления ветвления (решается фактом в T5)

Сегодня (`build_alimony_poc.py:74-82`) control-абзац `{%p if defendant_employed == 'yes' %}` **виден
юристу** в тексте иска. Так вышло потому, что шаблон собирал скрипт — служебная строка никому не мешала.
В целевом потоке файл открывает юрист.

- **A — литеральные jinja-абзацы.** Ноль работы на сервере (`extract.py`, гейты работают as-is), но мусор
  виден и юрист может сломать парность.
- **B — Content Control как маркер блока, jinja впрыскивается компилятором.** ⭐ В документе юриста jinja
  нет **вообще**: сломать синтаксис невозможно, потому что синтаксиса в файле нет. Content Control
  переживает правку текста внутри себя. Цена — слой «чистый docx + карта блоков → docxtpl-шаблон».
- **C — гибрид** (CC вокруг видимых jinja-абзацев): мусор всё равно виден. Худшее из двух.

**Рекомендация: B.** С появлением компилятора (§3) цена B резко падает — серверный синтез шаблона
перестаёт быть «лишним слоем» и становится **обычной работой компилятора**. Но выбор — фактом в T5.

## 10. Решения интервью (2026-07-15, medium)

1. **Скоуп** — полный цикл до публикации.
2. **Веб-панель** — зеркало, не билдер (для услуг движка B).
3. **Живые divorce/alimony** — движок A заморожен как legacy.
4. **Путь в БД** — свой эндпоинт + Supabase Auth; **гейты на сервере**.
5. **Хранилище `.docx`** — новый приватный Supabase Storage bucket.
6. **Среда** — Word Desktop (Windows), sideload только у Сергея.
7. **AI в панели** — нет; детерминированные подсказки. AI — фаза 2 поверх готового UI.
8. **Амбиция** — **услуга = один .docx, ноль кода**: схема расширяется, per-service скилл умирает.

**Открытые вопросы**
- A или B (§6) — фактом в T5.
- Какой Word у Оли (Windows/Mac, M365/коробочный, версия).
- Что хранится в Storage при варианте B: авторский `.docx`, синтезированный шаблон, или оба.
- Когда `doc-engine` + Gotenberg едут в прод (§8) — больше этого трека.
- `legal_constants` как данные (§5.2) — отдельный трек.

## 11. ⚠️ Спорный факт — не тащить в спеку

Explore-агент утверждает, что `divorce`/`alimony` до сих пор `generation_mode='js'` и потому **не имеют
MCP-тула** (ссылки `014:11`, `016:4-5`). Это **противоречит живому факту**: `generate_alimony_document`
отработал на демо D7 (`DEMO-FINDINGS-2026-07-11.md`), а s82 фиксирует 4 живых тула. Вероятно, прочитана
миграция, которая эти значения меняет, а не устанавливает.

На дизайн не влияет (обе услуги всё равно уходят в legacy — решение №3), но **проверить перед спекой**:
`select slug, generation_mode, status from services`.
