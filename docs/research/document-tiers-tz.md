## 1. Погляд збоку: як це закривали у світі (і що ми беремо)

Чотири еталони, кожен дає нам або підтвердження, або конкретне покращення.

### 1.1 Stanford RegLab (Magesh, Dahl, Ho et al., 2024/2025) — «RAG не лікує галюцинації»

Провідні **юридичні** AI-інструменти з RAG: **Lexis+ AI — 17%**, **Westlaw AI-Assisted Research — 33%** галюцинацій, попри маркетинг «hallucination-free». Висновок дослідників: заяви провайдерів **перебільшені**.

→ **Для нас:** пряме підтвердження нашого рішення «нуль галюцинацій конструкцією, не RAG-ом» (DECISIONS). Якщо навіть TR/LexisNexis на кураторських базах дають 17–33% — **генеративний текст не можна пускати у операбельну частину судового документа**. Наш висновок сильніший за їхній: ми не покладаємось на RAG як на ліки, ми **виносимо генерацію з довіреного шляху**.

### 1.2 DoNotPay / FTC (2024–2025) — «$193k за overpromise»

FTC оштрафувала «робота-юриста»: компанія **не тестувала**, чи працює AI на рівні юриста, **не залучала адвокатів** для перевірки якості, **не була навчена** на повній базі законів. Заборона надалі робити необґрунтовані заяви «AI = юрист».

→ **Для нас три уроки (нові, у репо не формалізовані):**
1. **Скромні заяви.** Позиціювання — «сервіс **самопредставництва**: готуємо документ для самостійної подачі», **не** «AI-юрист», **не** «заміна консультації». (mission це має у scope-out, але як **продуктовий/маркетинговий guardrail** + дисклеймери це окремий артефакт — додати.)
2. **Тестована якість = вимога, не бонус.** Потрібен **стендовий eval-харнесс** (див. §5).
3. **Юрист у петлі — це не лише «рів», це юридичний захист** від claims-ризику.

### 1.3 HotDocs / Docassemble / A2J Author / Suffolk LIT Lab — зрілий світ document automation

Ціла індустрія (HotDocs з 1990-х; Docassemble — open-source «золотий стандарт» guided-interview; A2J Author; Suffolk Assembly Line — суди 40+ штатів) **30 років** робить судові форми **детерміновано**: керована анкета → умовний шаблон → документ. **Без LLM.** Академічний висновок (arXiv 2312.09198): «гібрид **constrained drafting + human review** найкраще підходить для авторингу guided-interview».

→ **Для нас:** наш doc-engine (form_config + `{{#if}}`-шаблон + render-document.js) — це **Docassemble-клас**, перевинайдений добротно. Наслідки:
- **Tier 0/1 має лишатися без LLM** — це не компроміс, це state of the art. ~80% юридичних документів автоматизуються **без** генерації.
- Наша новизна — **не движок** (це commodity), а **Telegram-native UX + українська + кластер, валідований юристом + тонкий Tier-2 AI-шар**. Це і є диференціація; не плутати з «ми зробили AI-генератор документів».
- Варто запозичити їхні UX-патерни анкети (preview-as-you-go, тест умовної логіки, доступність для людини в стресі).

### 1.4 Harvey / CoCounsel (Thomson Reuters) — планка надійності

Лідери ринку юр-AI на найскладніших задачах тримають надійність так:
- **Юристи в петлі на всьому циклі** + **багатошаровий eval** (людські преференції + автоматичний LLM-eval) + власні бенчмарки.
- **Citation grounding:** структуровані метадані + embedding-пошук + **LLM-бінарне співставлення** «твердження ↔ джерело»; **runtime-Shepardization** (перевірка, що норма досі «good law»).
- Результат Harvey: **~0.2%** галюцинацій у внутрішніх вимірах (не нуль!).
- **Routing моделей** (драфтинг → reasoning-моделі).

→ **Для нас (конкретні покращення):**
- **Runtime good-law check.** У нас є CRON-моніторинг законів (`watched_laws`, `law_change_log`) — це **краще за багатьох**, але це моніторинг *послуги*, не *документа в момент генерації*. Додати: на генерації жоден citation не вказує на застарілу редакцію (звʼязати `law_version_date` з критиком). Це наша мікро-Shepardization.
- **Citation grounding до користувача, не лише в код.** mission обіцяє «користувач розуміє, на основі яких законів». Показувати статті користувачу → довіра + диференціація.
- **Багатошаровий eval як stand-up артефакт** (зараз у нас він описаний у validation.md, але не стендовий і не gate-ить релізи).
- **0.2% у Harvey з повним стеком** = чесний орієнтир: нуль недосяжний → тому **abstention обовʼязковий**, а операбельний текст — детермінований.

## 2. Канонічні рівні Tier 0 / 1 / 2 (/3)

Принцип монотонності: **вищий Tier = більше довіри потрібно віддати машині = товстіший харнесс**. Межі — не тема послуги, а два якісні тести нижче.

```
Tier 0 ──[тест A]──► Tier 1 ──[тест B: ПОЯВА ГЕНЕРОВАНОЇ ПРОЗИ]──► Tier 2 ──[тест C]──► Tier 3
детермінований      детермінований,        гібридний:                      не документ:
документ            але комбінаторний/      детерм. кістяк +                 триаж + ескалація
(forma→шаблон)      retrieval-вибір блоків  генерована case-проза + харнесс  (живий юрист)
```

**Тест A (0→1):** щоб зібрати правильний документ, треба **класифікація / retrieval / вибух комбінаторики** при виборі блоків? (Але самі блоки — наперед написані юристом.) Так → Tier 1.

**Тест B (1→2):** документ містить **згенеровану case-specific прозу**, яку **неможливо** замінити наперед написаним блоком (обґрунтування під конкретні факти)? Так → Tier 2. **Це перша поява галюцинаційної поверхні.**

**Тест C (2→3):** головна цінність — **кваліфікація ситуації / стратегія**, а документ вторинний або відсутній? Так → Tier 3.

| | Tier 0 | Tier 1 | Tier 2 | Tier 3 |
|---|---|---|---|---|
| **Що це** | детерм. документ | детерм. документ, складна збірка | гібридний документ | триаж/ескалація |
| **Генерована проза** | ні | ні | **так, 1 секція** | н/д |
| **Роль AI** | лише склонения ПІБ | склонения + (можливо) вибір блоку з verified-набору | склонения + обґрунтування під enum-констрейнтом | intent/основание-detection |
| **Галюцинації** | 0% конструкцією | 0% (вибрано не той блок ≠ вигадано) | можливі → харнесс ловить/abstain | вивід не віддається юзеру |
| **Людина** | юрист тільки при зміні закону | + юрист авторить дерево рішень | + юрист на ярус-3 графі і ревʼю 🟡 | **живий юрист обовʼязково** |
| **Приклади** | стягнення аліментів, розлучення без дітей | розлучення з дітьми+майном, поділ майна, вибір суду | **зміна розміру аліментів** | військові спори (ТЦК/ВЛК) |
| **Модель грошей** | продаж документа | продаж документа | документ (+ платне ревʼю юриста) | referral/комісія |
| **SDD-Tier спеки** | 1 | 2 | 2 | 2 |

> Tier 1 у нас поки порожній на практиці (live — два Tier 0). Перша Tier 1-послуга — «розлучення з дітьми + майно» (багато умовних блоків, але без генерації). Перша Tier 2 — нижче §4.

## 3. Tier 0 — приклад «Стягнення аліментів»: як це вирішується ЗАРАЗ

Жива послуга (`generation_mode='template'`, `status='active'`). Документ — позовна заява про стягнення аліментів. Нижче — **повний поточний алгоритм** і **нюанси** (зокрема — де навіть на Tier 0 ховається складність).

### 3.1 Алгоритм (end-to-end, як у проді)

```
[Клієнт у Telegram]
  1. TWA: DynamicLegalFormBuilder рендерить форму з services.form_config
     (alimony: ~44 поля / 16 умовних show_if; 4 таби). Валідація: required, формати.
     Чернетка → localStorage. Згода (PII/retention) перед сабмітом.
        │ POST { user_id, service_slug:'alimony', answers, consented_at }
        ▼
[n8n form-submit.json]
  2. Validate (Code)        — user_id/service_slug/answers присутні? інакше 4xx.
  3. Get Service (Supabase) — за slug.
  4. Check Status (Code)    — status==='active'? інакше 503 (kill-switch).
  5. Get Profile (Supabase).
  6. Encrypt (Code)         — AES-256-GCM → 'v1:<iv>:<tag>:<ciphertext>'.
  7. Insert Case (Supabase) — encrypted_data, status='submitted'.
  8. AI Declension (HTTP→Groq llama-3.3-70b, temp=0, ~200 tok)   ◄── ЄДИНИЙ виклик AI
        вхід:  ПІБ позивача/відповідача, місце реєстрації, children_details
        вихід: JSON { plaintiff_genitive, defendant_instrumental,
                      defendant_genitive, marriage_place_locative, children_genitive }
  9. Build Document (Code)  — dispatch generation_mode='template':
        renderDocument(alimony.document.txt, context)
        context = answers ⊕ ai(з fallback) ⊕ computed
        render-document.js — ЧИСТИЙ парсер DSL (без eval).
 10. Create Google Doc (HTTP) + batchUpdate (вставка тексту).
 11. Respond — { document_url, case_id }.
```

**Розкладка тексту (з alimony.document.txt):** ~95% — статичний шаблон зі вшитими нормами (ст.180,150,141,182–184 СК; п.6–10 ч.3 ст.175 ЦПК; п.3 ч.1 ст.5 ЗСЗ); підстановки `{{plaintiff_name}}`, `{{formatDate ...}}`; одна AI-залежність — `{{ai.defendant_instrumental}}` тощо (склонения).

### 3.2 Нюанси — де навіть тут складно (щоб «прочувствовать»)

1. **Стать з по-батькові.** `-івна/-ївна/-овна → female` → дієслова (`{{gender plaintiff_gender 'уклав' 'уклала'}}`, `звільнений/звільнена`). 🔻 Крихкість: іноземні імена, відсутнє по-батькові, нестандартні форми → хелпер може помилитись. Зараз — евристика без fallback на «спитати».
2. **Дати.** ISO → «20 червня 2015 року» (`formatDate`, місяці в родовому відмінку зашиті). Локаль-специфічно, але детерміновано.
3. **ІПН vs паспорт.** `has_no_ipn` → рядок з паспортом замість ІПН (×2: позивач/відповідач). Чисте ветвлення.
4. **Парсинг дітей із вільного тексту.** `children_details` = багаторядковий «ПІБ, дата р.н., свідоцтво № … від …» → `[{name, birthDate, certInfo, certInstrumental, gender}]`. 🔻 **Найкрихкіше місце Tier 0:** користувач має дотриматись формату; кома-розділення; склонения свідоцтва (`certInstrumental`) йде через AI. Помилка формату → кривий блок дітей. (Кандидат на структуровану під-форму замість textarea.)
5. **Частка аліментів.** `alimonyFraction(n_children)`: 1→¼, 2→⅓, 3+→½ (ст.183 СК). Детерміновано.
6. **Множина.** `plural(n_children, 'дитина','діти','дітей')` — 3 форми укр. множини.
7. **Fallback склонения.** `(ai && ai.x) || зібране_ПІБ` — поле ніколи не порожнє, навіть якщо Groq впав.
8. **Гарантія коректності — byte-parity.** 117 тестів alimony (шаблон === старий JS-білдер байт-у-байт) + 3 golden. Зміна тексту = зміна даних (шаблон у git), не коду.
9. **Операційні запобіжники.** `status` kill-switch; citation-страж (цитати шаблону ⊆ `watched_laws`, інакше CI падає); CRON zakon.rada → флип у `needs_review`.
10. **PII-нюанс (недооцінений).** ПІБ і місце все ж **їдуть у Groq** на склонения. Це PII за межу системи. 🔻 Варто зафіксувати в runbook/DPA-нотатці (провайдер, retention, no-train). Решта `answers` шифрується і LLM не бачить.

### 3.3 Чому це працює надійно

Бо **немає генерації**: усе або поле, або словник, або детермінований хелпер. Найгірша помилка — **склонения ПІБ** (обмежений, видимий, з fallback клас). Це і є «нуль галюцинацій конструкцією». Залишкові ризики — **не текстові, а вхідні**: крихкий парсинг дітей, вибір суду користувачем, коректність склонения рідкісних прізвищ.

## 4. Tier 2 — схожа послуга «Зміна розміру аліментів»: складнощі → варіанти → ціль

Та сама правова область, той самий клієнт — але **модифікація вже присудженого** розміру (ст.192 СК). Один крок угору по Tier-драбині оголює всі труднощі Tier 2 у мінімальному обсязі. (Повний контракт — `specs/features/alimony-change/`; тут — критичний фокус «складнощі / опції / ціль».)

### 4.1 Що саме ламається при переході Tier 0 → Tier 2

| # | Складність | Чому Tier 0-підхід не працює |
|---|---|---|
| C1 | **Обґрунтування зміни обставин** (ст.192/182) — case-specific проза | її **не можна** зашаблонити: аргумент залежить від конкретної зміни (дохід↑, потреби↑, здоровʼя↓). Перша генеративна поверхня → перша поверхня галюцинацій (Stanford: навіть RAG 17–33%) |
| C2 | **Асиметрія судового збору** ↑/↓ | ↑ (одержувач) — звільнення (п.3 ч.1 ст.5 ЗСЗ); ↓ (платник) — **платить** 1% ціни позову (ст.176 ЦПК), не менше 0.4 ПМ. Одна умова перемикає всю фінансову+правову частину — `exception_if`, ярус-3 ревʼю |
| C3 | **Плаваюча величина** — прожитковий мінімум (50% підлога, 0.4 ПМ для збору) | змінюється щороку → не можна в текст/модель, лише `registry` |
| C4 | **Вхід = попередній юр-акт** (рішення суду: суд, №, дата, поточний розмір) | новий клас входу; документ **посилається** на нього і будує дельту |
| C5 | **Момент дії нового розміру** (ст.191 vs практика) | правова неоднозначність → впливає на «ПРОШУ»; не вирішується кодом |
| C6 | **Поріг «істотності» зміни** (ст.192) | юридичне судження, чи зміни достатньо → це **не** задача моделі |

> C1 — єдина *технічно нова* складність (генерація). C2–C4 — детерміновані (розрахунок/словник/registry). C5–C6 — **юридичні**, не технічні: харнесс їх не «вирішує», а **явно виносить юристу**.

| **B. Lawyer-assisted (augment first)** ⭐ | детерм. кістяк + **юрист пише обґрунтування** (HITL з 1-го дня), монетизація через revenue-share | висока якість; **збирає gold-датасет** з юристових текстів; juридичний захист (DoNotPay-урок) | не повна автоматизація; впирається в пропускну здатність юриста | **v0 — старт** |
| **C. Constrained AI + критики + abstention + ревʼю** | AI драфтить під enum-констрейнтом (цитати лише з verified-набору) → детерм. critic-1 + LLM critic-2 → abstention → юрист дивиться лише 🟡 | масштабованість; кінцевий стан; ніколи не гірше за A (abstention) | важкий; потрібен **eval-харнесс** + юрист у петлі; не вмикати до зелених eval | **v1/v2 — після eval** |
| **D. Повна AI-генерація** | LLM пише весь документ | — | відхилено: Stanford 17–33%, DoNotPay $193k | ніколи |

**Рекомендована траєкторія (покращення I4):**

```
v0  Опція B  — детерм. кістяк + юрист пише обґрунтування (платна послуга, revenue-share)
              паралельно: будуємо eval-харнесс (I1) на текстах юриста як gold
v1  Опція C  — AI-драфт + критики + abstention; юрист РЕВʼЮЄ (а не пише);
              реліз тільки коли eval-gate зелений (ungrounded-rate < поріг)
v2  Опція C+ — abstention авто-відвантаження для high-confidence; юрист лише на 🟡/борд-лайн
завжди: Опція A як підлога — abstention НІКОЛИ не дає гірше за чистий валідний документ
```

Це і є світовий патерн «**augment → automate**» (HotDocs/Docassemble + Harvey HITL): спершу людина в петлі скрізь, автоматизуємо лише те, що eval довів.

### 4.3 Харнесс для Опції C (де критик, де детермінізм, де abstention)

(Стислий; повна 6-слойна схема — `service-tiers-and-ai-harness.md` §4, контракт — `specs/features/alimony-change/requirements.md`.)

- **Детермінуємо максимум:** напрямок ↑/↓, судовий збір (C2), ціна позову, ПМ (C3), частки, нумерація. LLM до цього не торкається.
- **L2 GraphRAG = обогащення, не генерація:** seed ст.192 → обхід `law_relations` (verified) → набір норм + **enum-список дозволених цитат**. AI фізично не вигадає номер статті (strict structured output).
- **L4 критики:**
  - **critic-1 (детерм., без LLM) — первинний (I7):** кожне число/дата/№/ПІБ у прозі ⊆ входу; кожна цитата ⊆ L2 → інакше 🔴.
  - **critic-2 (LLM) — лише дорадчий:** groundedness per-sentence → 🟡 (не довіряємо як єдиному гейту — Stanford).
  - **+ runtime good-law (I2):** жоден citation не на застарілу редакцію.
- **Abstention:** критики провалені → прозу викидаємо → документ = Опція A + алерт. **Найгірший випадок = валідний Tier-0-документ.**
- **L5 пакет юристу:** review-card (факти, розрахунок збору з нормою, набір норм, обґрунтування з 🟡-спанами + питання C5/C6). Юрист бачить **дельту ризику**, не весь документ.

### 4.4 Чого треба добитися (цілі / Definition of Done)

1. **v0 у проді швидко** (Опція B): детерм. кістяк + розрахунок збору за напрямком (C2) + посилання на попередній акт (C4) + юристове обґрунтування. → дохід + gold-датасет.
2. **Стендовий eval-харнесс (I1)** з гейтами: `ungrounded-claim-rate`, `abstention-rate`, retrieval-recall норм — у CI, як byte-parity на Tier 0.
3. **Перехід на Опцію C тільки за зеленим eval**; abstention гарантує «не гірше за A».
4. **Runtime good-law (I2) + citations користувачу (I3)**.
5. **Продуктовий guardrail (I5):** «самопредставництво, не консультація»; платне ревʼю юриста = окрема цінність, не прихований ризик.
6. **Outcome-петля (I6):** трекати приймання судом / залишення без руху (ст.185 ЦПК) як north-star — замикає eval реальністю.
7. **Послуга active лише після ярус-3 ревʼю юриста** (C2/C5/C6 verified).

**Стоп-сигнал (свідомий):** якщо на eval abstention-rate стабільно високий — Опція C не дотягує → лишаємось на B (юрист пише), reasoning у backlog. Не патчимо проміптом.
