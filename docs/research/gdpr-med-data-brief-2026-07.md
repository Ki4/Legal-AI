## 0. TL;DR — попередній вердикт

**Conditional GO для M1**, за умови виконання 5 умов (нижче §G5). Обґрунтування в одному абзаці:

M1 генерує **лист-запит від пацієнта до закладу на видачу власної медкартки** — реалізацію статутного права (ст.39 Основ законодавства про охорону здоров'я). Наш рушій обробляє **мінімум**: ПІБ, заклад, період, тип документа — **без діагнозів** (мінімізація by design, #93 G2). Проте сам факт «особа X запитує медичну документацію із закладу Y» — це **непрямі дані про здоров'я** (special-category, ст.7 ЗУ 2297-VI) → потрібні **згода + повідомлення Омбудсмана + retention-політика**. Усе це — керовані адмін-/дизайн-умови, не блокери-стопери. **GDPR наразі не застосовний** (укр-only), стане тригером при виході в ЄС (Польща CUKR). Ризик №1 не в M1, а в **ширшій медвертикалі** (скарги, де є діагнози/лікарські помилки) — її go/no-go тримаємо окремо.

⚠️ **Розрив, який треба закрити:** issues #91/#92/#93 посилаються на `docs/architecture/med-vertical-plan-2026-07.md` — **цей файл не існує**. Цей бриф покриває його §3 (GDPR). Решту плану (§1–2 інвентар/шкала, §4 retention) варто досписати окремо.

## G1 — Правова рамка

### 1.1 Україна (чинне право — застосовне ЗАРАЗ)

| Норма | Що каже | Наслідок для нас |
|---|---|---|
| **ЗУ 2297-VI ст.7** (Особливі вимоги) | Обробка даних про **здоров'я** — ЗАБОРОНЕНА, крім винятків: (а) **однозначна згода** суб'єкта; (б) мед-цілі (діагноз/лікування) — але лише медпрацівником/медзакладом. | Ми **не медзаклад** → наша єдина підстава = **однозначна поінформована згода**. ✅ верифіковано |
| **ЗУ 2297-VI ст.9** + **Наказ Омбудсмана №1/02-14 (08.01.2014)** | Обробка, що становить **«особливий ризик»** (здоров'я прямо в переліку), вимагає **повідомлення Уповноваженого ВРУ (Омбудсмана) впродовж 30 робочих днів** від початку + призначення відповідальної особи/підрозділу. | Одноразова адмін-дія перед стартом M1. Форма — на сайті Омбудсмана. ✅ верифіковано |
| **Основи законодавства про охорону здоров'я (2801-XII) ст.39** | Повнолітній пацієнт має право на **копію власної медичної документації**. | M1 = інструмент реалізації цього права. Легітимна мета. ✅ верифіковано |

### 1.2 Куди рухається право (будувати на виріст)

**Проєкт 8153 «Про захист персональних даних»** (GDPR-модель): пройшов 1-е читання 20.11.2024, **станом на 2026 НЕ ухвалений** (готується до 2-го читання). Вводить: незалежний DPA, розширені права суб'єкта, **штрафи до 150 млн грн або 8% річного обороту**. ✅ верифіковано.
→ **Висновок:** проектувати consent/retention **за GDPR-логікою вже зараз** — коли 8153 ухвалять, переробляти не доведеться.

### 1.3 GDPR — територіальна застосовність (Art.3)

Україна **не в ЄС/ЄЕЗ** → GDPR **не застосовний автоматично** до обробки даних резидентів України. Тригери (Art.3): (а) establishment у ЄС; (б) **пропозиція товарів/послуг особам у ЄС** або моніторинг їх поведінки. ✅ верифіковано.
→ **Сьогодні:** GDPR **не застосовний** (сервіс для юзерів в Україні через Telegram).
→ **Майбутній тригер:** план EU-легалізації (**Польща CUKR**, вікно 04.05.2026–04.03.2027) = надання послуг особам у ЄС → GDPR **увімкнеться**. Тому §1.2 (будувати за GDPR) — не перестраховка.

## Ключовий аналіз M1 — це взагалі special-category?

Це **центральне питання для Олі**. Дві інтерпретації:

- **Вузька (на нашу користь):** ми обробляємо лише ПІБ + заклад + період + тип документа. Діагнозів нема. Це «звичайні» персональні дані + факт звернення до закладу.
- **Широка (обережна, ймовірно правильна):** сам факт «особа запитує **медичну** документацію з **конкретного медзакладу**» — **непрямо розкриває дані про здоров'я** (що особа є/була пацієнтом). Регулятор радше трактує це як special-category.

**Робоче припущення брифу = широка інтерпретація** (безпечніше для court-ready юр-продукту): трактуємо M1 як обробку даних про здоров'я → повний комплаєнс (згода + повідомлення + retention). Якщо Оля підтвердить вузьку — частину вимог можна послабити, але «over-comply» тут дешевше за ризик.

**Мінімізація, яку тримаємо в будь-якому разі (#93 G2):** форма M1 **без полів діагнозу/стану**; лише реквізити запиту. LLM (Groq) — **нуль медданих** (склонення ПІБ ≠ медконтент).

## G3 — Consent-артефакт (дизайн + що потрібно від Олі)

**Потрібно ПЕРЕД мед-формою** — окремий екран згоди (артефакт #91 G3, споживається #93 G3).

**Технічна частина (Claude робить):**
- Екран згоди перед form_config M1 (чекбокс «Я даю згоду…», не pre-checked; блокує далі).
- Таблиця `consents` (міграція): `user_id`, `service_slug`, `consent_text_version`, `granted_at`, `ip/tg_id`, `withdrawn_at`. Append-only, версіонована (текст згоди може мінятися).
- Лог версії тексту → доказовість «на що саме погодився».

**Юридична частина (потрібен Оля — текст + обсяг):** див. питання нижче.

## G4 — Retention / видалення / breach

- **Retention:** визначити TTL для med-cases + PDF у Storage (IMPROVEMENTS #64 → з «колись» стає **блокуючим** для M1). Пропозиція: авто-видалення PDF + мінімізація рядка cases через N днів після доставки (N — узгодити з Олею; медзапит не потребує довгого зберігання).
- **Право на видалення:** механізм «видалити мої дані» (навіть якщо GDPR не застосовний — 8153 його введе; будуємо на виріст).
- **Privacy policy:** окремий документ (укр.) + посилання в consent-екрані. Текст — Оля/шаблон.
- **Breach-план:** короткий runbook (`docs/runbooks/`) — хто, що, кому повідомляє при витоку медданих. Для 8153 (штрафи 8% обороту) — не формальність.

## G5 — Попереднє go/no-go (НЕ фінал)

**Рекомендація: CONDITIONAL GO для M1** за виконання 5 умов ДО публікації:

1. ☐ **Згода** — consent-екран + таблиця `consents` + **текст від Олі** (обсяг обробки, мета, строк, права).
2. ☐ **Повідомлення Омбудсмана** — подати повідомлення про обробку особливого ризику (30-дн. вікно; форма з сайту) + призначити відповідальну особу (Сергій? Оля?).
3. ☐ **Retention** — TTL med-cases + Storage (IMPROVEMENTS #64) реалізовано; privacy policy + breach-runbook написані.
4. ☐ **Мінімізація** — форма M1 без діагнозів; доставка = signed-link-only; LLM = нуль медданих. (Дизайн — вже закладено.)
5. ☐ **Sign-off Олі** — юридична валідація трактування M1 (special-category?) + текстів згоди/політики + що M1 не заходить у «пораду/діагноз».

**Фінальний go/no-go → DECISIONS.md** після зустрічі, коли умови 1,2,5 отримають вхідні від Олі.

**No-go / hand-off (окремо від M1):** позиції зі **справжніми медданими** (скарги на лікарські помилки, оскарження МСЕК з діагнозами) — вищий ризик, тримати на hand-off юристу, **не** в 1-й хвилі автоматизації.

## 🎯 Питання для Олі — зустріч 07.07 14:00

Гострі, конкретні, з чесним «не знаю» де треба:

1. **Трактування M1:** запит на видачу **власної** медкартки (ПІБ + заклад + період, без діагнозу) — це обробка **даних про здоров'я** (ст.7 2297-VI) чи «звичайні» персональні дані? (Впливає на обсяг комплаєнсу.)
2. **Підстава обробки:** підтверджуєш, що для нас (не медзаклад) єдина підстава = **однозначна поінформована згода**? Чи є простіша (реалізація права за ст.39)?
3. **Повідомлення Омбудсмана:** чи справді потрібне для нашого сценарію, і **хто** відповідальна особа (ти / Сергій)? Ти подавала таке раніше?
4. **Текст згоди:** візьмеш на себе текст consent-екрана + privacy policy (укр.)? Які пункти обов'язкові (мета, обсяг, строк, треті сторони — Telegram/Supabase, права суб'єкта)?
5. **Строк зберігання:** скільки за законом/практикою тримати згенерований медзапит + чи є вимога видаляти?
6. **Червона лінія:** де межа, за якою M1 перетворюється з «оформлення документа» на «медичну/юридичну пораду», яку нам заборонено давати?
7. **Ширша медвертикаль:** які позиції з твого списку **точно НЕ** можна автоматизувати через special-category (→ hand-off)?
