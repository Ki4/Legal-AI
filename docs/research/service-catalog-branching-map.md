**Дата:** 2026-06-12 (session 22)
**Метод:** живой `services.watched_laws` + `form_config` (Supabase), regex-проход по шаблонам (`n8n/templates/services/*.document.txt`), `specs/roadmap.md`, research спроса (`service-demand/00-ukraine.md`, `01-candidate-military-disputes.md`), решение «GraphRAG-стек» (`graphrag-stack.md` + DECISIONS).

## 2. Правовая база live-услуг (что реально цитируется в документах)

### Розірвання шлюбу
- **СК:** ч.3 ст.105, ст.110, ст.112 (основание иска); ст.65 (общие долги, условный блок).
- **ЦПК:** ст.27 (подсудность); п.6–10 ч.3 ст.175 (процессуальные заявления); ст.187, 274 (финальная ссылка).
- **ЗСЗ:** пп.3 п.1 ч.2 ст.4 (сбор оплачен) / п.1, п.2, п.11 ч.1 ст.5 (льготы — словарь в шаблоне: инвалидность I-II, представитель ребёнка с инвалидностью, чернобылец 1–2 кат.).

### Стягнення аліментів
- **СК:** ст.141, 150, 180 (обязанности родителей); ч.2 ст.182, ст.182–184 (размер и критерии); ст.183 неявно — хелпер `alimonyFraction` (1/4–1/2 по числу детей).
- **ЦПК:** п.6–10 ч.3 ст.175; ст.174, 175 (финальная ссылка).
- **ЗСЗ:** п.3 ч.1 ст.5 — истец **автоматически** освобождён от сбора.

### Судебная практика — не используется
Ни один шаблон не цитирует постановления ВС. `law_chunks` (21 чанк) — мёртвые данные. Для GraphRAG это кандидат на ярус 2 (retrieval-обогащение), не на ярус 3.

## 3. Таксономия ветвлений

Извлечено из live `form_config` (divorce: 53 поля / 14 условных; alimony: 44 / 16) и `{{#if}}`-цепочек шаблонов. Два принципиально разных класса:

### A. Юридически-значимые факты — переключают нормы и структуру документа

| Факт-драйвер | Что переключает | Норма |
|---|---|---|
| `has_children` → `alimony_claim` → `alimony_amount` | блок детей + алиментный блок + динамическая нумерация «ПРОШУ» (5–8 пунктов) | ст.180, 183 СК |
| `marital_status` (married / divorced / never_married) | три разных вступа иска, разные документы-основания | ст.141 СК |
| `alimony_type` (percent / fixed) | способ взыскания; `alimonyFraction` | ст.182–184 СК |
| `has_joint_property`, `property_dispute`, долги | блок раздела имущества/долгов | ст.65 СК |
| `court_fee_exempt` + `court_fee_exempt_reason` | оплата vs льгота + конкретный пункт статьи (словарь EXEMPT_REASONS в шаблоне) | ст.4 vs п.1/2/11 ч.1 ст.5 ЗСЗ |
| досудебное урегулирование / обеспечение / оригиналы у ответчика / расходы / нет другого иска | варианты обязательных процессуальных заявлений | п.6–10 ч.3 ст.175 ЦПК |
| `surname_after_divorce` | пункт о возврате добрачной фамилии | ст.113 СК (**не цитируется — пробел**, см. §4) |

### B. Реквизитные ветвления — правовую логику не меняют
`has_no_ipn` → паспорт вместо ИПН (×истец/ответчик); `same_actual_address` / `defendant_actual_address_known`; `defendant_employed` → работодатель/должность/зарплата (усиливают мотивировку, статьи не меняют); `defendant_other_income`.

### Вывод для графа
Каждый драйвер класса A — готовое ребро `exception_if`/`requires` **3-го яруса** (всегда ревью юриста): «факт → требует норму → добавляет блок/пункт». Их ~10–15 на услугу, они **уже формализованы и протестированы** (380 parity-тестов двух услуг — фактически тесты этих рёбер). Факты-драйверы переиспользуются между услугами кластера: дети, имущество, статус брака, льгота по сбору, доход ответчика встретятся и в «поділ майна», и в «зміна аліментів».

## 5. Маппинг retrieval-техник на нашу архитектуру

Контекст: доклад (Лена, паттерны RAG-маршрутизации) описывает путь **от свободного чата к детерминизму** — «распознали интент → отдали точный SME-утверждённый ответ, минуя генерацию; RAG = fallback». Мы пришли в ту же точку с другой стороны: **ядро уже детерминировано** (интент = выбранная услуга, clarifying = форма, SME-ответ = шаблон, LLM только на склонениях).

| Техника | У нас сейчас | Где пригодится |
|---|---|---|
| Intent Detection | интент = выбор услуги кнопкой (`service_slug`) | вход свободным текстом → роутинг по каталогу; **военный триаж** = intent detection по основаниям отсрочки |
| Function calling как интент | `form_config` = строгая схема параметров generate_document | чат-ассистент v3.1: LLM заполняет поля формы из свободного текста (Shared State) |
| FAQ-индексация Q→A | нет | **GraphRAG шаг 0–1:** индексировать не сырой текст статей, а сгенерированные вопросы к каждой статье («Хто звільнений від судового збору?» → чанк ст.5 ЗСЗ). Дёшево (dev-сессия), точность retrieval ↑ |
| Query reframing / expansion | не нужен в ядре: запросы к графу строятся из ответов формы детерминированно (metadata-first, s21) | только свободный консультационный чат |
| Chat history (summary / RAG over history) | форма = state, диалога нет | v3 чат-ассистент |
| Stable vs fluctuating properties | stable есть: `profiles` (шифрованный) | fluctuating (страх/срочность) — сигнал к эскалации в военном триаже |
| Clarifying questions | **форма с `show_if` = детерминированный clarifying-loop, спроектированный юристом заранее** | LLM-версия — там, где комбинаторика взрывается (поділ майна); abstention-паттерн s21 |

**Уточнение терминов:** LightRAG-фреймворк отклонён в s21; описанные техники — не фреймворк, а паттерны маршрутизации + retrieval-гигиена, совместимые с решением «патерни замість фреймворків».

## 6. Следствия: трёхслойная архитектура + шаг 0

Три слоя, в которых живут техники:
- **(а) Детерминированное ядро** (форма → шаблон) — не трогаем; это лучшая из возможных реализаций «intent → точный SME-ответ».
- **(б) Retrieval-слой hybrid-услуг** («зміна аліментів») — FAQ-индексация + metadata-first + enum-констрейнт + abstention.
- **(в) Свободный вход / чат** (v3, военный триаж) — intent detection + clarifying + fluctuating properties.

**Шаг 0 GraphRAG = формализация уже существующего** (без Ольги, без API-затрат):
1. Regex-экстрактор цитат из шаблонов → нормализованный список (закон-URL + статья + часть/пункт).
2. Сверка с `watched_laws` → закрыть drift из §4.
3. Тест-страж: каждая цитата шаблона покрыта watched_laws (вечная защита от дрейфа).
4. Далее (шаг 1): досев `law_chunks` чанк=статья + migration `law_relations` + рёбра «факт-драйвер → норма» из §3 в pending на ревью Ольги (~2026-06-25).
