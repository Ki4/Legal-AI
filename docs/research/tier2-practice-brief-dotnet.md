# Практичне завдання: Tier 2 — гібридна генерація юридичного документа

> Цей документ самодостатній (доступ до основного репозиторію не потрібен). Основа — реальна задача
> юридичного SaaS (Україна): генерація позовних заяв. Усі формулювання норм закону нижче —
> **переказ для цілей вправи**, не юридична консультація і не цитата для продакшну. Посилання на
> повні тексти кодексів — у §2.

## 0. Ідея завдання

Є сервіс, який за структурованими фактами складає **позовну заяву про зміну розміру аліментів**.
Майже весь документ — детермінований шаблон з умовною логікою (якщо/то за вхідними полями). Але
**один абзац** — це «обґрунтування» причин зміни, яке має бути згенероване (LLM чи будь-яким іншим
способом) і при цьому:
- посилатись **тільки** на норми закону з невеликого наданого тобі набору (ніяких «стаття 256
  Цивільного кодексу» від себе);
- згадувати **тільки** факти/числа/дати, які є у вхідних даних (ніяких вигаданих сум).

Це і є «Tier 2» за нашою внутрішньою класифікацією:

- **Tier 0/1** — чиста комбінаторика шаблонів, без генерації взагалі.
- **Tier 2 = Tier 1 + рівно один генеративний фрагмент**, обв'язаний: маршрутизація → retrieval →
  constrained generation → grounding-перевірка → abstention-fallback.
- **Tier 3** — вільний діалог/тріаж (не в цьому завданні).

**Твоє завдання** — реалізувати весь конвеєр end-to-end на .NET. Модель, RAG-підхід, бібліотеки,
архітектура, стратегія промптів, як саме мірити «достатньо заземлений (grounded) текст» — усе
твій вибір. Цей документ описує **WHAT** (вхід, правила, очікуваний вихід, тест-кейси, критерії
успіху). **HOW** — повністю твоя зона, у цьому й сенс практики.

## 1. Вхідні дані (JSON)

```jsonc
{
  "change_direction": "increase" | "decrease",   // збільшити чи зменшити розмір аліментів

  "prior_alimony": {
    "type": "percent" | "fixed",                  // поточний спосіб: % від доходу чи тверда сума
    "value": number,                              // percent: 0-100; fixed: грн/міс
    "basis": "court_decision" | "agreement",      // поточний розмір встановлено судом чи договором
    "agreement_own_procedure": "yes" | "no" | "unknown" | null
    // ^ лише якщо basis == "agreement": сторони вже намагались змінити договір самостійно?
  },

  "requested_alimony": {
    "type": "percent" | "fixed",
    "value": number
  },

  "changed_facts": ["..."],   // підмножина 9-значного enum, див. таблицю нижче

  "children": [ { "age_years": number } ],   // 1..N дітей

  "existing_debt": "yes" | "no" | null,
  // ^ лише якщо change_direction == "decrease": чи є непогашена заборгованість за поточними алиментами?

  "evidence_list": ["..."]   // може бути порожнім []
}
```

### `monthly_delta` (похідне поле)

Потрібне для розрахунку ціни позову (§4). Обчислюється **тільки якщо** `prior_alimony.type ==
"fixed"` **і** `requested_alimony.type == "fixed"`:

```
monthly_delta = abs(requested_alimony.value - prior_alimony.value)
```

Якщо хоч одна сторона — `"percent"`, `monthly_delta = "unknown"` (неможливо обчислити частку від
невідомого доходу). Це **не помилка** — просто окрема гілка у виході (див. §8, TC4).

### `changed_facts` — enum (9 значень)

| Значення | Доступне при | Норми з бази знань (§2) | Маршрут (§3) |
|---|---|---|---|
| `payer_income_up` | `increase` | A1, A2 | `PROCEED` |
| `payer_income_down` | `decrease` | A1, A2 | `PROCEED` |
| `payer_new_dependents` | `decrease` | A1, A2 | `PROCEED` |
| `payer_health_down` | `decrease` | A1, A2 | `PROCEED` |
| `child_needs_up_general` | `increase` | A1, A2 | `PROCEED` |
| `child_needs_up_extraordinary` | `increase` | A5 | **`ABSTAIN_EXTRAORDINARY`** |
| `child_health_down` | `increase` | A1, A2 | `PROCEED` |
| `recipient_income_down` | `increase` | A1, A2 | `PROCEED` |
| `cost_of_living_up` | обидва напрямки | A1 (⚠️ слабка підстава) | `PROCEED`*, окрім одного випадку — див. R2 у §3 |

Валідний вхід містить **непорожню** і **несуперечливу** підмножину (не можна одночасно
`payer_income_up` і `payer_income_down` — це суперечність, див. R4 у §3).

## 2. База знань (L2) — фіксований набір «статей закону»

Це весь набір джерел, доступний генератору. **Будь-яке посилання на статтю закону у згенерованому
тексті має бути з цього списку** (за `id`), інакше це hallucination.

> 🔗 **Повні тексти кодексів** (для довідки, НЕ для копіювання формулювань у прод):
> - Сімейний кодекс України (СК) — https://zakon.rada.gov.ua/laws/show/2947-14
> - Цивільний процесуальний кодекс України (ЦПК) — https://zakon.rada.gov.ua/laws/show/1618-15
> - ЗУ «Про судовий збір» — https://zakon.rada.gov.ua/laws/show/3674-17
>
> Конкретну статтю шукай на сторінці закону за номером (зміст ліворуч або Ctrl+F «Стаття NNN») —
> прямі посилання-якорі на окремі статті змінюються між редакціями, тому не наводимо їх тут.

| id | Джерело (для контексту) | Переказ — що це означає (для grounding) |
|---|---|---|
| A1 | СК України, ст.192 | Підстава для зміни розміру аліментів — істотна зміна матеріального/сімейного стану однієї зі сторін або стану здоров'я |
| A2 | СК України, ст.182 ч.2 | Перелік обставин, які суд враховує при визначенні розміру: стан здоров'я і матеріальне становище дитини та платника, наявність у платника інших дітей/осіб на утриманні, доходи кожного з батьків тощо |
| A3 | СК України, ст.183 | Алименти можуть присуджуватись у частці від доходу платника |
| A4 | СК України, ст.184 | Алименти можуть присуджуватись у твердій грошовій сумі; така сума підлягає автоматичній індексації без окремого рішення суду |
| A5 | СК України, ст.181, ст.185 | Додаткові витрати на дитину з визначеною вартістю (лікування, навчання тощо) стягуються окремим позовом, відмінним від «зміни розміру аліментів» |
| A6 | СК України, ст.189 | Розмір аліментів за договором можна змінити за згодою сторін; до суду — якщо згоди не досягнуто |
| A7 | СК України, ст.191 / постанова ВСУ №3/2006 п.23 | Новий розмір аліментів застосовується з дня набрання рішенням суду законної сили |
| A8 | СК України, ст.197 | Заборгованість зі сплати аліментів стягується окремо і не погашається автоматично зміною розміру на майбутнє |
| A9 | ЦПК України, ст.27 | Загальне правило підсудності — за місцем проживання відповідача |
| A10 | ЦПК України, ст.28 ч.1 | Позови про стягнення аліментів можна подавати також за місцем проживання позивача |
| A11 | ЦПК України, ст.176 | Ціна позову за вимогами про стягнення періодичних платежів — сукупна сума платежів за один рік |
| A12 | ЗУ «Про судовий збір», ст.4 | Ставка судового збору — відсоток від ціни позову, але не менше встановленої частки прожиткового мінімуму |
| A13 | ЗУ «Про судовий збір», ст.5 ч.1 п.3 | Позивачі звільняються від сплати судового збору за позовами про стягнення аліментів |

## 3. Маршрутизація (L0.5) — детермінований гейт ДО будь-якої генерації

Чиста функція `route(changed_facts, prior_alimony.type)`, без LLM. Застосовується **першою**, до
шаблону і до retrieval.

| # | Умова | → Маршрут | Що на виході |
|---|---|---|---|
| R1 | `child_needs_up_extraordinary ∈ changed_facts` | `ABSTAIN_EXTRAORDINARY` | §6 — документ НЕ створюється |
| R2 | `prior_alimony.type == "fixed"` І `changed_facts == {cost_of_living_up}` (рівно один елемент) | `ABSTAIN_INDEXATION` | §6 — документ НЕ створюється |
| R3 | `prior_alimony.type == "percent"` І `changed_facts == {cost_of_living_up}` (рівно один елемент) | `PROCEED` | документ створюється, але critic має позначити абзац як слабко обґрунтований (AMBER) |
| R4 | `changed_facts` порожній або суперечливий (наприклад, містить і `payer_income_up`, і `payer_income_down`) | — | невалідний вхід — відхиляється до маршрутизації (валідація форми) |
| R5 | усе інше | `PROCEED` | звичний документ |

Порядок перевірки: **R4 → R1 → R2/R3 → R5**. R1 і R2 не можуть збігтись одночасно (R2 вимагає, щоб
`changed_facts` складався **рівно** з одного елемента `cost_of_living_up`).

> 🔑 **Важливе розрізнення на майбутнє (§5):** `ABSTAIN_EXTRAORDINARY` / `ABSTAIN_INDEXATION` — це
> рішення «взагалі не генерувати документ» (приймається **до** L1/L3). Це інша категорія, ніж
> `ABSTAIN_REASONING` з §5 — там документ генерується, просто без персоналізованого абзацу.

## 4. Детермінований скелет (L1) — має збігатись завжди, без LLM

| | `increase` (позивач = одержувач аліментів) | `decrease` (позивач = платник) |
|---|---|---|
| Підсудність (шапка документа) | за вибором позивача — місце позивача **або** відповідача (A10) | тільки місце проживання відповідача (A9) |
| Судовий збір | звільнення (A13), `court_fee.exempt = true` | розрахунок: ціна позову = `monthly_delta × 12` (A11); збір = `max(1% від ціни позову, 0.4 × 3328)` (A12) |
| «ПРОШУ» — дія | «Збільшити розмір аліментів ... з X до Y» | «Зменшити розмір аліментів ... з X до Y» |
| «ПРОШУ» — момент дії | «з дня набрання рішенням суду законної сили» (A7) — **однаково для обох напрямків** | те саме |
| 50%-floor (довідкове значення, не hard-валідація) | дивись нижче | те саме |

### Registry-значення (на 2026 рік, зашити як константи)

| Вік дитини | Прожитковий мінімум | 50% (floor) |
|---|---|---|
| < 6 років | 2817 грн | **1408.50 грн** |
| 6–18 років | 3512 грн | **1756 грн** |
| Прожитковий мінімум для працездатних (для збору, A12) | 3328 грн | floor збору = **1331.20 грн** (0.4 × 3328) |

Якщо `monthly_delta == "unknown"` (див. §1) — `court_fee` не розраховується, у виході ставиться
`"court_fee": "manual"`, а в `questions_for_lawyer` додається пункт «ціна позову потребує ручного
розрахунку».

### Як саме застосовувати 50%-floor

Це **довідкове значення для `review-card`**, не jest hard-валідація вхідних даних (бо абсолютна
сума при `requested_alimony.type == "percent"` залежить від доходу платника, якого немає у вхідній
схемі):

- `requested_alimony.type == "fixed"`: якщо `requested_alimony.value` для дитини цього віку
  **менше** за floor — додати до `flags` запис `below_default_floor: <value> < <floor> (50% ПМ
  для дитини <вікова група>)`. Це не блокує генерацію — лише сигнал юристу (приклад: §7,
  Приклад 2).
- `requested_alimony.type == "percent"`: floor виводиться в `review-card` як довідка (юрист має
  співставити з фактичним доходом платника).
- Для кількох дітей floor рахується **окремо для кожної дитини** за її віковою групою.

## 5. Генеративний абзац (L3) + перевірки (L4)

Застосовується **тільки** на маршруті `PROCEED` (після L0.5).

### 5.1 Вхід для генерації

- `changed_facts[]` (як прийшли, без фільтрації — фільтрація вже зроблена на рівні L0.5);
- набір `article_id` з §2, релевантних цим `changed_facts` (за таблицею в §1 — це твій «retrieval»,
  можна жорстко закодувати відповідність як словник, можна зробити справжній retrieval — не
  важливо для цілей вправи);
- самі вхідні факти (числа, вік дітей, суми) — єдине джерело чисел/дат для тексту.

### 5.2 Вихід

1–3 речення українською мовою, які:
- посилаються **тільки** на `article_id`, що входять у наданий для цього кейсу набір з §2
  (у людиночитаній формі, наприклад «ст.192 СК України»);
- згадують **тільки** числа/вік/факти, присутні у вхідних даних — ніяких нових сум, дат, імен.

**Особливий випадок (R3 із §3):** якщо після фільтрації єдиний факт — `cost_of_living_up`, а
`prior_alimony.type == "percent"`, абзац **не повинен** стверджувати «підвищення прожиткового
мінімуму — само по собі підстава для зміни» (за A1 це не так — потрібна зміна становища сторони).
Critic має зловити це як AMBER.

### 5.3 Критики (L4)

- **Critic 1 (детермінований, без LLM):** кожен `article_id`, згаданий у тексті, ∈ наданий набір з
  §2; кожне число/дата/факт у тексті ∈ вхідні дані. Це просто regex/парсинг — без моделі.
- **Critic 2 (будь-який спосіб — LLM-суддя, евристика, що завгодно):** оцінка groundedness — чи
  справді речення підтверджується контекстом, а не просто формально проходить Critic 1.

### 5.4 Abstention для reasoning (`ABSTAIN_REASONING`)

Якщо будь-який critic не проходить → абзац **замінюється** на статичний fallback (наприклад,
загальна фраза з посиланням лише на A1), документ все одно складається і віддається. Це **не** те
саме, що `ABSTAIN_EXTRAORDINARY`/`ABSTAIN_INDEXATION` із §3 — там документа немає взагалі, тут
документ є, просто без персонального абзацу.

## 6. Підсумковий вихід (L5)

Два артефакти на виході конвеєра:

1. **Текст документа** — шаблон (L1) із підставленим абзацом (L3) або з fallback-абзацем (якщо
   `ABSTAIN_REASONING`), або `redirect_message` без документа (якщо `ABSTAIN_EXTRAORDINARY` /
   `ABSTAIN_INDEXATION`).
2. **review-card** — JSON-зведення для перевіряючого:

```jsonc
{
  "route": "proceed" | "abstain_extraordinary" | "abstain_indexation",

  // лише якщо route == "proceed":
  "jurisdiction_basis": "A10 — за вибором позивача" | "A9 — за місцем проживання відповідача",
  "court_fee": {
    "exempt": true | false,
    "price_of_claim": number | null,
    "fee_amount": number | "manual" | null,
    "fee_basis": "A13" | "A11+A12" | null
  },
  "reasoning_status": "generated" | "abstained_generic",
  "citations_used": ["A1", "A2"],   // порожньо, якщо abstained_generic
  "flags": ["below_default_floor: ..."],  // опційно, може бути []

  // лише якщо route != "proceed":
  "abstention_reason": "...",
  "redirect_message": "...",

  "questions_for_lawyer": ["..."]
}
```

### Тексти для `redirect_message`

**`ABSTAIN_EXTRAORDINARY`:**
> «Ваш запит стосується конкретної додаткової витрати на дитину з визначеною вартістю (лікування,
> навчання тощо). Це інший вид позову — "стягнення додаткових витрат на дитину" (ст.181, 185 СК
> України), а не "зміна розміру аліментів" (ст.192). Цей сервіс поки не підтримує такий позов —
> рекомендуємо звернутись до юриста.»

**`ABSTAIN_INDEXATION`:**
> «Аліменти присуджені у твердій сумі, і єдина названа причина — зростання вартості життя. Такий
> розмір індексується автоматично, без суду (ст.184 СК України). Позов про "зміну розміру" (ст.192)
> тут не є належним способом захисту — якщо є й інші причини, оберіть їх у формі.»

## 7. Приклади виходу (worked examples)

### Приклад 1 — `increase`, звичний `PROCEED` (відповідає TC1 у §8)

**Вхід:**
```json
{
  "change_direction": "increase",
  "prior_alimony": {
    "type": "percent", "value": 25,
    "basis": "court_decision", "agreement_own_procedure": null
  },
  "requested_alimony": { "type": "percent", "value": 50 },
  "changed_facts": ["child_needs_up_general", "payer_income_up"],
  "children": [ { "age_years": 10 } ],
  "existing_debt": null,
  "evidence_list": ["довідка про доходи відповідача", "довідка про витрати на навчання дитини"]
}
```

**L0.5:** `route = PROCEED` (R5 — звичний випадок).

**L1 (детермінований скелет):**
- `jurisdiction_basis`: A10 (за вибором позивача)
- `court_fee`: `exempt = true` (A13)
- «ПРОШУ» — дія: «Збільшити розмір аліментів, що стягуються на утримання [дитина], з 25% до 50%
  доходу відповідача»
- «ПРОШУ» — момент дії: «з дня набрання рішенням суду законної сили» (A7)
- floor (довідково): дитина 10 років (група 6–18) → 1756 грн

**L3 (приклад згенерованого абзацу):**
> «Після ухвалення попереднього рішення суду дохід відповідача істотно зріс, а потреби дитини на

## 9. Критерії успіху

1. **Маршрутизація (R1–R5):** 100% збіг по всіх тест-кейсах. Це чиста логіка, без LLM — не повинно
   бути жодного промаху.
2. **Детермінований скелет (§4):** 100% збіг — підсудність, розрахунок збору (включно з floor),
   формулювання «ПРОШУ», floor-довідка по кожній дитині.
3. **Grounding генеративного абзацу (§5):** по всіх PROCEED-кейсах — **0%** посилань на
   `article_id`, що не входять у наданий набір, і **0%** чисел/фактів, відсутніх у вхідних даних.
   Оскільки вивід LLM недетермінований — вимірюй на N прогонах (наприклад, N=10 на кейс).
4. **Адекватний abstention (§5.4):** якщо штучно зіпсувати контекст (наприклад, дати L3 порожній
   набір `article_id`) — конвеєр має коректно перейти в `ABSTAIN_REASONING`, а не видати текст із
   посиланнями «з голови» моделі і не зависнути/впасти.
5. **review-card** завжди валідний за схемою §6, для кожного маршруту (включно з ABSTAIN_*).

## 10. Що НЕ задано — твій вибір

- Модель/провайдер (локальна модель, будь-яке API, що завгодно)
- Спосіб retrieval на L2 (жорсткий словник `changed_fact → article_id[]` цілком ОК для такого
  обсягу; справжній векторний пошук — опційно, можна «попрактикувати» окремо)
- Архітектура і бібліотеки на .NET (Semantic Kernel, Microsoft.Extensions.AI, прямі HTTP-виклики —
  що завгодно)
- Промпт-стратегія для L3 і для Critic 2
- Як саме реалізований Critic 2 (LLM-суддя, евристика, ансамбль — твій вибір)
- Формат зберігання/передачі L2-бази (захардкоджений масив, JSON-файл, БД — не важливо)

Успіхів! Якщо щось в умові незрозуміле або здається недо-специфікованим — це нормально для Tier 2:
частина твого завдання — помітити такі місця і явно вирішити, як їх закрити.
