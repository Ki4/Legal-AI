# Практическая задача: Tier 2 — гибридная генерация юридического документа

> Это самодостаточный документ (не требует доступа к репозиторию-источнику). Основан на реальной задаче
> юридического SaaS (Украина): генерация исковых заявлений. Все формулировки норм закона ниже —
> **пересказ для целей упражнения**, не юридическая консультация и не цитата для прода.

## 0. Идея задачи

Есть сервис, который по структурированным фактам собирает **исковое заявление об изменении размера
алиментов**. Почти весь документ — детерминированный шаблон с условной логикой (если/то по входным
полям). Но **один абзац** — это "обоснование" причин изменения, которое должно:
- быть сгенерировано (LLM или любым другим способом),
- ссылаться **только** на нормы закона из предоставленного тебе небольшого набора (никаких "статья 256
  Гражданского кодекса" от себя),
- упоминать **только** факты/числа/даты, которые есть во входных данных (никаких выдуманных сумм).

Это и есть "Tier 2" в нашей внутренней классификации:

- **Tier 0/1** — чистая комбинаторика шаблонов, без генерации вообще.
- **Tier 2 = Tier 1 + ровно один генеративный фрагмент**, обвязанный: маршрутизация → retrieval →
  constrained generation → grounding-проверка → abstention-fallback.
- **Tier 3** — свободный диалог/триаж (не в этой задаче).

**Твоя задача** — реализовать весь конвейер end-to-end на .NET. Модель, RAG-подход, библиотеки,
архитектура, стратегия промптов, как именно мерить "достаточно ли заземлён (grounded) текст" — всё
твой выбор. Этот документ описывает **WHAT** (вход, правила, ожидаемый выход, тест-кейсы, критерии
успеха). **HOW** — целиком твоя зона, в этом и смысл практики.

## 1. Входные данные (JSON)

```jsonc
{
  "change_direction": "increase" | "decrease",   // увеличить или уменьшить размер алиментов

  "prior_alimony": {
    "type": "percent" | "fixed",                  // текущий способ: % от дохода или твёрдая сумма
    "value": number,                              // percent: 0-100; fixed: грн/мес
    "basis": "court_decision" | "agreement",      // текущий размер установлен судом или договором
    "agreement_own_procedure": "yes" | "no" | "unknown" | null
    // ^ только если basis == "agreement": стороны уже пытались изменить договор сами?
  },

  "requested_alimony": {
    "type": "percent" | "fixed",
    "value": number
  },

  "changed_facts": ["..."],   // подмножество 9-значного enum, см. таблицу ниже

  "children": [ { "age_years": number } ],   // 1..N детей

  "existing_debt": "yes" | "no" | null,
  // ^ только если change_direction == "decrease": есть ли непогашенная задолженность по текущим алиментам?

  "evidence_list": ["..."]   // может быть пустым []
}
```

### `monthly_delta` (производное поле)

Нужно для расчёта цены иска (см. §4). Вычисляется **только если** `prior_alimony.type == "fixed"`
**и** `requested_alimony.type == "fixed"`:

```
monthly_delta = abs(requested_alimony.value - prior_alimony.value)
```

Если хотя бы одна сторона — `"percent"`, `monthly_delta = "unknown"` (нельзя вычислить долю от
неизвестного дохода). Это **не ошибка** — просто отдельная ветка в выходе (см. §6, TC4).

### `changed_facts` — enum (9 значений)

| Значение | Доступно при | Куда смотреть в базе знаний (§2) | Маршрут (§3) |
|---|---|---|---|
| `payer_income_up` | `increase` | A1, A2 | `PROCEED` |
| `payer_income_down` | `decrease` | A1, A2 | `PROCEED` |
| `payer_new_dependents` | `decrease` | A1, A2 | `PROCEED` |
| `payer_health_down` | `decrease` | A1, A2 | `PROCEED` |
| `child_needs_up_general` | `increase` | A1, A2 | `PROCEED` |
| `child_needs_up_extraordinary` | `increase` | A5 | **`ABSTAIN_EXTRAORDINARY`** |
| `child_health_down` | `increase` | A1, A2 | `PROCEED` |
| `recipient_income_down` | `increase` | A1, A2 | `PROCEED` |
| `cost_of_living_up` | оба направления | A1 (⚠️ слабое основание) | `PROCEED`*, кроме одного случая — см. R2 в §3 |

Валидный вход содержит **непустое** и **непротиворечивое** подмножество (нельзя одновременно
`payer_income_up` и `payer_income_down` — это противоречие, см. R4 в §3).

## 2. База знаний (L2) — фиксированный набор "статей закона"

Это весь набор источников, который доступен генератору. **Любая ссылка на статью закона в
сгенерированном тексте должна быть из этого списка** (по `id`), иначе это hallucination.

| id | Источник (для контекста) | Пересказ — что это означает (для grounding) |
|---|---|---|
| A1 | СК України, ст.192 | Основание для изменения размера алиментов — существенное изменение материального/семейного положения одной из сторон или состояния здоровья |
| A2 | СК України, ст.182 ч.2 | Перечень обстоятельств, которые суд учитывает при определении размера: состояние здоровья и материальное положение ребёнка и плательщика, наличие у плательщика других детей/лиц на содержании, доходы каждого из родителей и т.п. |
| A3 | СК України, ст.183 | Алименты могут присуждаться в доле от дохода плательщика |
| A4 | СК України, ст.184 | Алименты могут присуждаться в твёрдой денежной сумме; такая сумма подлежит автоматической индексации без отдельного решения суда |
| A5 | СК України, ст.181, ст.185 | Дополнительные расходы на ребёнка с определённой стоимостью (лечение, образование и т.п.) взыскиваются отдельным иском, отличным от "изменения размера алиментов" |
| A6 | СК України, ст.189 | Размер алиментов по договору можно изменить по соглашению сторон; в суд — если согласие не достигнуто |
| A7 | СК України, ст.191 / постанова ВСУ №3/2006 п.23 | Новый размер алиментов применяется со дня вступления решения суда в законную силу |
| A8 | СК України, ст.197 | Задолженность по алиментам взыскивается отдельно и не погашается автоматически изменением размера на будущее |
| A9 | ЦПК України, ст.27 | Общее правило подсудности — по месту проживания ответчика |
| A10 | ЦПК України, ст.28 ч.1 | Иски о взыскании алиментов можно подавать также по месту проживания истца |
| A11 | ЦПК України, ст.176 | Цена иска по требованиям о взыскании периодических платежей — совокупная сумма платежей за один год |
| A12 | ЗУ «Про судовий збір», ст.4 | Ставка судебного сбора — процент от цены иска, но не менее установленной доли прожиточного минимума |
| A13 | ЗУ «Про судовий збір», ст.5 ч.1 п.3 | Истцы освобождаются от уплаты судебного сбора по искам о взыскании алиментов |

## 3. Маршрутизация (L0.5) — детерминированный гейт ДО любой генерации

Чистая функция `route(changed_facts, prior_alimony.type)`, без LLM. Применяется **первой**, до
шаблона и до retrieval.

| # | Условие | → Маршрут | Что на выходе |
|---|---|---|---|
| R1 | `child_needs_up_extraordinary ∈ changed_facts` | `ABSTAIN_EXTRAORDINARY` | §5.1 — документ НЕ создаётся |
| R2 | `prior_alimony.type == "fixed"` И `changed_facts == {cost_of_living_up}` (ровно один элемент) | `ABSTAIN_INDEXATION` | §5.2 — документ НЕ создаётся |
| R3 | `prior_alimony.type == "percent"` И `changed_facts == {cost_of_living_up}` (ровно один элемент) | `PROCEED` | документ создаётся, но critic должен пометить абзац как слабо обоснованный (AMBER) |
| R4 | `changed_facts` пуст или противоречив (например, содержит и `payer_income_up`, и `payer_income_down`) | — | невалидный вход — отклоняется до маршрутизации (валидация формы) |
| R5 | всё остальное | `PROCEED` | обычный документ |

Порядок проверки: **R4 → R1 → R2/R3 → R5**. R1 и R2 не могут совпасть одновременно (R2 требует, чтобы
`changed_facts` состоял **ровно** из одного элемента `cost_of_living_up`).

> 🔑 **Важное различие на будущее (§5):** `ABSTAIN_EXTRAORDINARY` / `ABSTAIN_INDEXATION` — это решение
> "вообще не генерировать документ" (принимается **до** L1/L3). Это другая категория, чем
> `ABSTAIN_REASONING` из §5 — там документ генерируется, просто без персонализированного абзаца.

## 4. Детерминированный скелет (L1) — должно совпадать всегда, без LLM

| | `increase` (истец = получатель алиментов) | `decrease` (истец = плательщик) |
|---|---|---|
| Подсудность (шапка документа) | по выбору истца — место истца **или** ответчика (A10) | только место проживания ответчика (A9) |
| Судебный сбор | освобождение (A13), `court_fee.exempt = true` | расчёт: цена иска = `monthly_delta × 12` (A11); сбор = `max(1% от цены иска, 0.4 × 3328)` (A12) |
| "ПРОШУ" — действие | "Увеличить размер алиментов ... с X до Y" | "Уменьшить размер алиментов ... с X до Y" |
| "ПРОШУ" — момент действия | "со дня вступления решения суда в законную силу" (A7) — **одинаково для обоих направлений** | то же самое |
| 50%-floor (только если `requested_alimony.type == "percent"`) | применяется к `requested_alimony.value` **отдельно для каждого ребёнка** по возрасту (registry ниже) | то же самое |

### Registry-значения (на 2026 год, зашить как константы)

| Возраст ребёнка | Прожиточный минимум | 50% (floor) |
|---|---|---|
| < 6 лет | 2817 грн | **1408.50 грн** |
| 6–18 лет | 3512 грн | **1756 грн** |
| Прожиточный минимум для трудоспособных (для сбора, A12) | 3328 грн | floor сбора = **1331.20 грн** (0.4 × 3328) |

Если `monthly_delta == "unknown"` (см. §1) — `court_fee` не считается, в выходе ставится
`"court_fee": "manual"` и в `questions_for_lawyer` добавляется пункт "цена иска требует ручного расчёта".

## 5. Генеративный абзац (L3) + проверки (L4)

Применяется **только** на маршруте `PROCEED` (после L0.5).

### 5.1 Вход для генерации

- `changed_facts[]` (как пришли, без фильтрации — фильтрация уже сделана на уровне L0.5)
- набор `article_id` из §2, релевантных этим `changed_facts` (по таблице в §1 — это твой "retrieval",
  можно жёстко закодировать соответствие как словарь, можно сделать настоящий retrieval — не важно
  для целей упражнения)
- сами входные факты (числа, возраст детей, суммы) — единственный источник чисел/дат для текста

### 5.2 Выход

1–3 предложения на украинском языке, которые:
- ссылаются **только** на `article_id`, входящие в предоставленный для этого кейса набор из §2
  (в человекочитаемой форме, например "ст.192 СК України");
- упоминают **только** числа/возраста/факты, присутствующие во входных данных — никаких новых сумм,
  дат, имён.

**Особый случай (R3 из §3):** если после фильтрации единственный факт — `cost_of_living_up`, а
`prior_alimony.type == "percent"`, абзац **не должен** утверждать "повышение прожиточного минимума —
само по себе основание для изменения" (по A1 это не так — нужно изменение положения стороны).
Критик должен поймать это как AMBER.

### 5.3 Критики (L4)

- **Critic 1 (детерминированный, без LLM):** каждый `article_id`, упомянутый в тексте, ∈
  предоставленный набор из §2; каждое число/дата/факт в тексте ∈ входные данные. Это просто
  regex/парсинг — без модели.
- **Critic 2 (любой способ — LLM-судья, эвристика, что угодно):** оценка groundedness — действительно
  ли предложение подтверждается контекстом, а не просто формально проходит Critic 1.

### 5.4 Abstention для reasoning (`ABSTAIN_REASONING`)

Если любой критик не проходит → абзац **заменяется** на статический fallback (например, общая фраза
со ссылкой только на A1), документ всё равно собирается и отдаётся. Это **не** то же самое, что
`ABSTAIN_EXTRAORDINARY`/`ABSTAIN_INDEXATION` из §3 — там документа нет вообще, здесь документ есть,
просто без персонального абзаца.

## 6. Итоговый выход (L5)

Два артефакта на выходе пайплайна:

1. **Текст документа** — шаблон (L1) с подставленным абзацем (L3) или с fallback-абзацем (если
   `ABSTAIN_REASONING`), либо `redirect_message` без документа (если `ABSTAIN_EXTRAORDINARY` /
   `ABSTAIN_INDEXATION`).
2. **review-card** — JSON-сводка для проверяющего:

```jsonc
{
  "route": "proceed" | "abstain_extraordinary" | "abstain_indexation",

  // только если route == "proceed":
  "jurisdiction_basis": "A10 — за вибором позивача" | "A9 — за місцем проживання відповідача",
  "court_fee": {
    "exempt": true | false,
    "price_of_claim": number | null,
    "fee_amount": number | "manual" | null,
    "fee_basis": "A13" | "A11+A12" | null
  },
  "reasoning_status": "generated" | "abstained_generic",
  "citations_used": ["A1", "A2"],   // пусто, если abstained_generic
  "flags": ["AMBER: weak_basis_percent_cost_of_living"],  // опционально, может быть []

  // только если route != "proceed":
  "abstention_reason": "...",
  "redirect_message": "...",

  "questions_for_lawyer": ["..."]
}
```

### Тексты для `redirect_message`

**`ABSTAIN_EXTRAORDINARY`:**
> «Ваш запит стосується конкретної додаткової витрати на дитину з визначеною вартістю (лікування,
> навчання тощо). Це інший вид позову — "стягнення додаткових витрат на дитину" (ст.181, 185 СК
> України), а не "зміна розміру аліментів" (ст.192). Цей сервіс поки не підтримує такий позов —
> рекомендуємо звернутись до юриста.»

**`ABSTAIN_INDEXATION`:**
> «Аліменти присуджені у твердій сумі, і єдина названа причина — зростання вартості життя. Такий
> розмір індексується автоматично, без суду (ст.184 СК України). Позов про "зміну розміру" (ст.192)
> тут не є належним способом захисту — якщо є й інші причини, оберіть їх у формі.»

## 7. Тест-кейсы (acceptance suite)

Прогони каждый кейс через свой пайплайн целиком — от входного JSON до текста документа + review-card.

| № | `change_direction` | prior→requested type | `prior_alimony.basis` (+доп.поле) | `changed_facts` | children | `existing_debt` | Ожидаемый route | Что проверяем |
|---|---|---|---|---|---|---|---|---|
| TC1 | increase | percent→percent | court_decision | `[child_needs_up_general, payer_income_up]` | 1×(6-18) | — | PROCEED | подсудность=A10, fee.exempt=true, "ПРОШУ"="...набрання законної сили", floor=1756 |
| TC2 | decrease | fixed→fixed (Δ=небольшая) | court_decision | `[payer_income_down]` | 1×(<6) | no | PROCEED | подсудность=A9, fee = 1% цены иска (выше floor) |
| TC3 | decrease | fixed→fixed (Δ=100) | court_decision | `[payer_health_down]` | 1×(6-18) | no | PROCEED | цена иска=1200, 1%=12 < floor → fee=**1331.20** (floor сработал) |
| TC4 | decrease | percent→fixed | court_decision | `[payer_income_down]` | 1×(<6) | no | PROCEED | `monthly_delta="unknown"` → `court_fee="manual"`, вопрос юристу |
| TC5 | increase | percent→percent | court_decision | `[child_needs_up_extraordinary]` | 1×(6-18) | — | **ABSTAIN_EXTRAORDINARY** | без документа, redirect §6 |
| TC6 | decrease | fixed→fixed | court_decision | `[cost_of_living_up]` (ровно один) | 1×(<6) | no | **ABSTAIN_INDEXATION** | без документа, redirect §6 |
| TC7 | increase | percent→percent | court_decision | `[cost_of_living_up]` (ровно один) | 1×(6-18) | — | PROCEED (R3) | документ создаётся, но `flags` содержит AMBER про слабое основание |
| TC8 | increase | agreement→percent | agreement, `agreement_own_procedure=yes` | `[recipient_income_down]` | 1×(<6) | — | PROCEED | `questions_for_lawyer` упоминает проверку собственного порядка изменения договора (A6) |
| TC9 | decrease | fixed→fixed | court_decision | `[payer_new_dependents]` | 1×(6-18) | **yes** | PROCEED | документ + предупреждение: уменьшение не покрывает задолженность (A8) |
| TC10 | increase | percent→percent | court_decision | `[child_needs_up_general, child_health_down]` | 2× (1×<6, 1×6-18) | — | PROCEED | 50%-floor считается **отдельно по каждому ребёнку**: 1408.50 и 1756 |
| TC11 | increase | percent→percent | court_decision | `[recipient_income_down]` | 1×(6-18) | — | PROCEED, но **ABSTAIN_REASONING** | смоделируй отказ критика → документ создаётся, но абзац = generic fallback (НЕ ABSTAIN_EXTRAORDINARY/INDEXATION — документ есть) |
| TC12 | любой | — | — | `[payer_income_up, payer_income_down]` (противоречие) | — | — | вход отклонён (R4) | пайплайн вообще не запускается — ошибка валидации входа |

## 8. Критерии успеха

1. **Маршрутизация (R1–R5):** 100% совпадение по всем тест-кейсам. Это чистая логика, без LLM — не
   должно быть ни одного промаха.
2. **Детерминированный скелет (§4):** 100% совпадение — подсудность, расчёт сбора (включая floor),
   формулировка "ПРОШУ", 50%-floor по каждому ребёнку.
3. **Grounding генеративного абзаца (§5):** по всем PROCEED-кейсам — **0%** ссылок на `article_id`,
   не входящих в предоставленный набор, и **0%** чисел/фактов, не входящих во входные данные.
   Поскольку вывод LLM недетерминирован — измеряй на N прогонах (например, N=10 на кейс).
4. **Adequate abstention (§5.4):** если искусственно испортить контекст (например, дать L3 пустой
   набор `article_id`) — пайплайн должен корректно откатиться на `ABSTAIN_REASONING`, а не выдать
   текст с ссылками "из головы" модели и не зависнуть/упасть.
5. **review-card** всегда валиден по схеме §6, для каждого маршрута (включая ABSTAIN_*).
