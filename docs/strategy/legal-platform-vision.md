# Видение платформы: движок юридического комплаенса для юристов (взгляд разработки)

**Дата:** 2026-07-14 · **Тип:** стратегическое видение (продукт + бизнес-модель + что строить)
**Опирается на:** `med-fop-platform-vision.md` (первая вертикаль), `service-builder-vision.md`
(движок «услуга = данные»), `docs/research/*` (верифицированная бизнес-модель и конкуренты).

---

## 1. Видение одним абзацем

Мы строим не один продукт для одной ниши, а **платформу-движок**, на которой юрист конфигурирует
compliance-услуги (без кода), подключает мониторинг изменений законодательства и получает готовый
клиентский кабинет с подпиской. Медицина — **первая вертикаль и эталонная реализация**, а не потолок.
Платформа монетизирует юристов (supply) и через них — клиентов (demand). Наше преимущество как
разработки: движок генерации документов **service-agnostic**, поэтому добавление новой ниши = создание
и валидация данных, а не написание кода. Это делает мультинишевую платформу подъёмной для малой команды.

## 2. Ключевой инсайт, на котором всё держится

**Услуга — это данные, а не код.** Строка в таблице услуг = форма (`form_config`) + шаблон документа
(DSL) + режим генерации (`template`/`hybrid`/`ai`) + отслеживаемые законы + чек-лист обязательных
пунктов. Движок собирает документ, ничего не зная о конкретной услуге. Значит:

- **Новая услуга/ниша = новая конфигурация, не новый релиз.** Юрист-эксперт вносит знание домена;
  разработка не участвует в каждой услуге.
- **Одна кодовая база обслуживает все ниши.** Медицина, ветеринария, IT-ФОП различаются данными
  (формы, шаблоны, законы), но исполняются одним движком.
- Это структурное преимущество перед ручными юрфирмами (каждая услуга = ручной труд) и перед
  вертикальными SaaS (каждая ниша = отдельная разработка).

## 3. Двусторонняя модель

### Supply — что получает юрист (за что платит платформе)
- **Service Builder** — конструктор услуги через интерфейс: форма + шаблон + законы + чек-лист +
  панель готовности (preflight-«светофор»), которая не даёт опубликовать услугу с дырами в документе.
  ~80% read-only части уже существует (каталог, анатомия услуги, health-статусы, layout-preview).
- **Law-monitor** — автоматический мониторинг изменений в отслеживаемых законах → триггер на пересмотр
  услуги и обновление шаблонов у всех клиентов сразу.
- **Кабинет клиентов** — CRM: кто подписан, статусы, история, эскалации.
- **Экономика** — платформа снижает себестоимость обслуживания клиента на порядок → юрист рентабельно
  ведёт сегмент, недоступный ручной модели (соло-клиенты за низкий чек).

### Demand — что получает клиент (за что платит подписку)
- **Личный кабинет** (Telegram Mini App для алертов/статусов/быстрых действий + десктоп-веб для работы
  с документами).
- **Персональный регуляторный календарь** — триггерные алерты «изменение X касается тебя, дедлайн Y,
  вот готовый документ».
- **Автообновляемый пакет документов** — юрист правит шаблон один раз, у всех подписчиков актуально.
- **Доступ к юристу** — лимитированный форматом, с AI-черновиком под апрув; сложное — платная эскалация.
- **Плюшки** (perks) — бесплатный слой алертов как воронка, чек-листы, шаблоны, «оплата после результата»
  на разовых услугах, статус «ты в порядке».

## 4. Бизнес-модель платформы (как зарабатываем мы)

Мы монетизируем **supply-сторону** (юристов) — это масштабируется лучше, чем прямые продажи клиентам.
Гибрид из трёх потоков (бенчмарки верифицированы в `docs/research/`):

| Поток | Механика | Бенчмарк-ориентир |
|---|---|---|
| **Платформенная подписка (SaaS)** | Юрист платит фикс/мес за консоль + движок + law-monitor (тарифы по числу услуг/клиентов) | инфо-правовые системы 3 300–9 000 грн/мес |
| **Revenue share** | Платформа удерживает % с клиентских подписок, которые юрист ведёт | LawDepot white-label: партнёру 75%, платформе 25%; LegalZoom: recurring net of payments to law firms |
| **Транзакционные** | Комиссия/наценка на разовые услуги (лицензия «под ключ» как воронка) | лицензия 6–8 тыс. грн, себестоимость через автоматизацию кратно ниже |

Логика выравнивания интересов: платформа зарабатывает **больше, когда у юриста больше клиентов** —
поэтому мы вкладываемся в инструменты его роста, а не конкурируем с ним за клиента. Это прямой ответ
на риск «зачем юристу платформа»: мы — его инфраструктура и рычаг, а не соперник.

## 5. Что мы должны построить (разработка: есть / gap)

Против того, к чему уже пришли — честный аудит:

| Компонент | Статус | Что доделать |
|---|---|---|
| Doc-engine (детерминированная генерация, LLM не пишет юртекст) | ✅ есть | — эталон, переиспользуется всеми нишами |
| `form_config`-driven UI (форма из данных) | ✅ есть | — |
| Режимы генерации `template/hybrid/ai` | ✅ есть | диспетчер под сложность документа (см. §7) |
| Service-console (каталог, анатомия, health, layout) | ✅ ~80% read-only | собрать разрозненные экраны в единый UX |
| MCP-интервьюер (сбор данных клиента) | ✅ PoC | продуктизация |
| Law-monitor | ⚠️ частично | **OCR-слой** (МОЗ и др. публикуют сканы PDF) + LLM-структуризация + привязка изменения к услугам |
| **Service Builder (запись)** — «добавь услугу без разработчика» | 📋 gap | пошагово: редактор шаблона → конструктор полей → мастер услуги + preflight |
| **Мультитенантность** | 📋 gap (критично) | у каждого юриста свои услуги/шаблоны/клиенты/бренд; изоляция данных; RLS |
| **Биллинг** | 📋 gap | подписки клиентов + платформенная подписка + rev-share + разовые (платёжный провайдер UA) |
| **Клиентский кабинет** (календарь + алерты + документы) | 📋 gap | десктоп-веб + TMA; движок нотификаций |
| Слой ответственности/оферта | 📋 gap | «инструмент содействия, не страховой полис» |

**Порядок разработки** (снизу вверх, каждый слой опирается на готовый фундамент):
1. Собрать существующие экраны в единую Консоль услуг + завершить preflight-панель.
2. Мультитенантность (без неё нет ни второго юриста, ни white-label).
3. Клиентский кабинет + движок алертов (это то, за что платит клиент).
4. Law-monitor: OCR + структуризация + связка «изменение → услуга → обновлённый документ».
5. Биллинг (клиентские подписки → rev-share).
6. Service Builder (запись) — редактор шаблона → конструктор полей → мастер услуги.
7. Позже: RAG/GraphRAG как capability-toggles, каждый со своей панелью верификации.

## 6. Ниши помимо медицины (карта, ✅¹ разведка)

Две оси захода: **вертикали** (лицензируемые профессии — переиспользуют med-плейбук) и **горизонтальные
пакеты** (нужны всем, продаются add-on поверх любой ниши). Размеры рынка — ориентир, часть (не подтверждено).

### 6.1. Вертикали (лицензия на деятельность)

| Ниша | Рынок | Регуляторные события | Сложность док-в | Fit |
|---|---|---|---|---|
| **Ветеринария** | ~2–4 тыс. *(н/п)* | Лицензия Держпродспоживслужби, квалификация раз в 5 лет, проверки, требования к помещению | MEDIUM-HIGH | 🟢 **лучший** — почти копия медФОП, макс. переиспользование |
| **Охранная деятельность** | ~5–6 тыс. *(н/п)* | Лицензия МВД, частые апдейты лицусловий (2025→2026 с дедлайнами), штатный спец, проверки объектов | MEDIUM-HIGH | 🟢 **лучший по ARR** — «держим лицензию чистой», платёжеспособны |
| **Перевозчики (авто)** | ~11,5 тыс. лиц./год | Лицензия Укртрансбезпеки, приведение к новым лицусловиям, проверки безопасности | MEDIUM | 🟢 **объём** — стандартные документы, высокий self-serve |
| **Аптеки/фармация** | 18 115 точек | Лицензия Держлікслужби, апдейты лицусловий, фарм-надзор | HIGH | 🟡 консолидирован (сети со своими юристами), узкая ЦА |
| **Частное образование** | сотни-тыс. *(н/п)* | Лицензия МОН, кадры/помещение/программы | HIGH | 🟡 события редкие; репетиторы без лицензии отпадают |
| **Алкоголь/табак розница** | десятки тыс. *(н/п)* | Лицензия бессрочная, оплата поквартально, частые изменения закона | LOW-MEDIUM | 🔴 бухгалтерская, не юр-боль → дешёвый self-serve модуль |
| Строительство, туризм, ломбарды | малые/переходные | режимы нестабильны/зарегулированы | HIGH | 🔴 плохой fit на старте |

### 6.2. Вертикали (по типу бизнеса)

| Ниша | Рынок | Юр-потребности | Сложность | Fit |
|---|---|---|---|---|
| **IT-ФОП / фрилансеры** | ~148 тыс. | ЗЕД-контракты, валютный контроль, инвойсы, IP, NDA (под каждый контракт) | HIGH | 🟢 платёжеспособны, digital-native, высокочастотно. Риск: отток в Дія.City |
| **E-commerce ФОП** | 77 тыс., +21%/год | Оферта, права потребителей, ПРРО, ПДн; «пакет запуска + ежегодная актуализация» | MEDIUM | 🟢 быстрорастущий, чистая подписочная механика |
| **Бьюти-мастера ФОП** | массовый *(н/п)* | Договор аренды рабочего места (killer-SKU), санитария, оферта, ПДн-согласие | MEDIUM | 🟢 огромный объём однотипных, низкий порог, дешевле разового юриста |
| HoReCa | высокая плотность | HACCP, санитария, алкоголь, кадры | HIGH | 🟡 много офлайн-процедур вне авто-генерации |
| Аренда/риелторы | массовый | Договоры аренды, отчётность риелторов | MEDIUM | 🟡 низкая «липкость» (разовая сделка ≠ подписка) |
| Общий юр-ретейнер СМБ | 1,77 млн ФОП | Абонентское обслуживание | MEDIUM | 🟡 прямой конкурент по цене; держать как верхний тариф |

### 6.3. Горизонтальные пакеты (add-on поверх любой вертикали)

- **Кадры + охрана труда** — трудовые договоры, приказы, ПВТР, инструктажи; высокие штрафы = сильный
  триггер. ⚠️ военучёт для ФОП НЕ обязателен — не продавать как «страшилку» (частый миф).
- **Персональные данные / GDPR** — политика ПДн, согласия, ответственный; закон №8153 (штрафы до
  десятков млн грн) на подходе. Кросс-ниш SKU для всех, кто собирает данные клиентов.
- **Оферта + права потребителей** — для всех, кто продаёт онлайн/офлайн.
- **ЗЕД-пакет (валютный контроль)** — ядро для IT, нужен любому экспортёру.

## 7. Пакетирование по сложности (ответ «сопровождение в разных пакетах»)

Одна платформа обслуживает весь спектр через связку `generation_mode` × интенсивность сопровождения.
Сложность документа и интенсивность юрсопровождения задают тариф — не наоборот:

| Уровень | Сложность док-в | Режим генерации | Роль юриста | Пакет | Пример ниш |
|---|---|---|---|---|---|
| **Автопілот** | LOW | `template` | минимум, шаблон подписан заранее | дёшево, высокая маржа, self-serve | алкоголь/табак, транспорт, простые формы |
| **Стандарт** | MEDIUM | `template`/`hybrid` | периодический пересмотр + N вопросов | средний чек | ветеринария, e-commerce, бьюти |
| **Супровід** | HIGH | `hybrid` + обяз. HITL | обязательная подпись + эскалация | премиум, высокий чек | медицина, охрана, IT-ЗЕД, HoReCa |

Тот же принцип внутри ниши: базовая подписка (календарь + типовые документы) → апсейл «сопровождение»
(проверки, эскалации, сложные кейсы). Ёмкость юриста защищается конструкцией: формат вопросов +
AI-черновик под апрув + платная эскалация (не оптимистичным бенчмарком).

## 8. Последовательность вертикалей

1. **Медицина** — эталон, движок и плейбук.
2. **Ветеринария** — максимальный переиспользование med-плейбука, доказывает тезис «новая ниша = данные».
3. **Охрана / перевозчики** — доказывают масштаб и разный профиль (ARR vs объём).
4. **Горизонтальные пакеты (кадры/ПДн)** — растят чек внутри уже привлечённых клиентов, ниша-агностичны.
5. IT-ФОП / e-commerce / бьюти — вторая волна, другой тип боли (контракты/оферта, не лицензия).

Каждая новая вертикаль после медицины должна **закрываться конфигурацией, а не разработкой** — если
для ниши N требуется код, значит движку не хватает обобщения, и это баг платформы, а не задача ниши.

## 9. Ограничения и зависимости

- **Юрист-эксперт на нишу** — движок исполняет знание, но не создаёт его. Каждая вертикаль требует
  юриста-методолога (медицина ≠ охрана ≠ IT). Это supply-ограничение, не техническое.
- **Мультитенантность и биллинг — до второго юриста.** Без них платформа = один вертикальный продукт.
- **Law-monitor honesty** — OCR/AI-шаги не детерминированы на 100% → human sign-off обязателен,
  каждая AI-способность приходит со своей панелью верификации.
- **Валидация спроса** остаётся гейтом на каждую нишу (интервью по Mom Test), не только на медицину.
- **Ответственность** — оферта с разделением на каждую услугу.

## Резюме

Медицина — не продукт, а **первая услуга на движке**. Настоящий актив разработки — платформа, где
«услуга = данные», поэтому малая команда покрывает много ниш одной кодовой базой. Юрист получает
конструктор + мониторинг + кабинет клиентов; клиент — подписку на состояние комплаенса; мы зарабатываем
на supply-стороне (SaaS + rev-share + транзакции), выравнивая интересы с юристом. Что строить: собрать
консоль, мультитенантность, клиентский кабинет с алертами, law-monitor с OCR, биллинг, затем Service
Builder. Следующие ниши — ветеринария (копия плейбука), охрана и перевозчики (ARR и объём), плюс
горизонтальные пакеты (кадры, ПДн), которые растят чек в любой нише. Проверка зрелости движка: новая
ниша должна закрываться конфигурацией, а не кодом.
