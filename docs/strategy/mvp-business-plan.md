# Бизнес-план MVP: соло-ФОП (взгляд разработки)

**Дата:** 2026-07-14 · **Тип:** план исполнения (сегмент + скоуп + масштабирование)
**Связано:** `mvp-pmf-plan.md` (что такое MVP), `med-fop-platform-vision.md` (модель),
`legal-platform-vision.md` (платформа), `docs/research/interview-script-solo-fop.md` (валидация).

## 1. Тезис: почему мы в это идём

Пять причин, каждая проверяемая:

1. **Ниша пустая и это верифицировано.** Соло-медФОП за 1.5–2.5 тыс. грн/мес не обслуживает никто:
   юрфирмы начинаются от 5–10 тыс. (ручная себестоимость), tech-продукты либо без медправа (54–295 грн),
   либо для учреждений (3.3–9 тыс.). Между ними — пусто.
2. **Себестоимость — наше структурное преимущество, а не цена.** Конкурент не может спуститься к нам,
   не разрушив свою экономику. Мы не воюем ценой — мы обслуживаем сегмент, недоступный ручной модели.
3. **Движок уже построен.** Маржинальная стоимость попытки — недели, не годы (см. §3–4). Мы не строим
   платформу «чтобы проверить» — мы проверяем тем, что уже есть.
4. **Опциональность.** Если медицина не пойдёт — тот же движок закрывает ветеринарию, охрану,
   перевозчиков. Проверяется гипотеза сегмента, не выбрасывается актив.
5. **Ограниченный минус.** Провал PMF-гейта стоит недель и даёт: валидированный движок,
   переиспользуемый паттерн самоаудита и карту рынка. Это не ноль.

**Принцип плюшек:** ничего не добавляем «на всякий случай». Каждая функция появляется как **ответ на
задачу, которая уже повторилась** у реальных клиентов. Пока задача не повторилась — её нет.

## 2. Сегмент: зафиксирован — соло-ФОП

**Кто:** лікар-ФОП з чинною ліцензією на медпрактику, практикует сам, 0–3 наёмных.
Приоритет — стоматологи, косметологи с медлицензией, узкие специалисты с кабинетом (больше документов
на пациента → выше риск).

**Почему именно они:**
- Конкурентов нет (верифицировано negative search).
- **Ролей нет** — один человек = все роли → продукт проще на порядок (ноль мультитенантности в MVP).
- Короткий цикл продажи: решение принимает тот же, кто чувствует боль.
- Рынок ~35 тыс. лицензиатов.

**Кто НЕ наш клиент в MVP:** клиники/ТОВ (поле LicenseOffice и Medcraft, нужны роли и долгий цикл),
наёмные врачи (боль не у них), КНП.

## 3. Механизм масштабирования (ядро для разработки)

### Принцип: услуга — это данные, а не код
```
услуга = form_config (форма/интервью)
       + document_template (DSL-шаблон)
       + generation_mode (template / hybrid)
       + checklist (обязательные юр-пункты)
       + watched_laws (мониторинг)
       + skill (как агенту вести интервью по этой услуге)
```
Движок `render-document.js` **service-agnostic** — собирает документ, ничего не зная о конкретной услуге.

### Две оси автоматизации — обе читают одну строку `services`

| Ось | Что масштабирует | Чем |
|---|---|---|
| **doc-engine** | *производство* документа — детерминированно, без юриста, стоимость ≈ 0 | шаблон + движок |
| **MCP + skills** | *приём* — интервью с клиентом, то есть **тот самый час юриста, который стоит денег** | tool авто-генерится из `form_config`; skill = сценарий опроса |

**Уточнение к тезису «MCP позволяет масштабировать»:** масштабирует не MCP сам по себе, а
принцип «услуга = данные». MCP — адаптер агентной поверхности, **но именно он закрывает самую дорогую
человеческую операцию** (сбор данных). Telegram-бот, админка и MCP — три потребителя одной абстракции.

### Следствие для MVP: самоаудит — это тоже `form_config`
84 вопроса проверяющих с ветвлением = ровно то, что движок уже умеет (`tabs` + `show_if`).
Отчёт «готовность 62%, 3 критичных» = документ, который рендерит doc-engine.
**Значит MVP — это преимущественно конфигурация + тонкий слой скоринга, а не новая система.**

### Тест зрелости движка
Новая услуга/ниша должна закрываться **конфигурацией, а не кодом**. Если для услуги N нужен код —
это баг платформы, а не задача услуги.

## 4. Скоуп работ MVP

### 4.1. Строим

| # | Что | Оценка | Основание |
|---|---|---|---|
| 1 | **Аудит как услуга**: `form_config` на 84 вопроса + ветвление по типу практики | конфигурация | движок есть |
| 2 | **Слой скоринга**: правило «ответ → пробел → вес/критичность» → % готовности + список пробелов | **новое, малое** | единственный реально новый код |
| 3 | **Маппинг «пробел → услуга»**: какой документ закрывает какой пробел | данные | — |
| 4 | **Отчёт аудита** как `document_template` → PDF | конфигурация | doc-engine есть |
| 5 | **Доставка в Telegram** + бот-опросник | есть/доработка | бот есть |
| 6 | **Генерация закрывающих документов** | есть | doc-engine |
| 7 | **Инструменты юриста**: редактор шаблона + preflight + kill-switch | есть ~80% | service-console |
| 8 | **Эскалация**: структурированный вопрос → юристу | **новое, малое** | на MVP — Telegram-канал |
| 9 | **Оплата** | **ручная** | счёт/перевод, биллинг НЕ строим |

### 4.2. НЕ строим в MVP (осознанно)

Роли и мультитенантность · полный кабинет · автоматический law-monitor (юрист следит вручную, мы шлём) ·
OCR · RAG/GraphRAG · биллинг · аналитика · финансы · интеграции ЕСОЗ/МІС · база НПА · мобильное
приложение вне Telegram.

**Правило:** всё, что можно на MVP сделать руками — делаем руками. Автоматизируем **только то, что уже
повторилось** и болит.

## 5. Подключение юриста (критический путь)

Юрист — не пользователь системы, а **соавтор услуги**. Если ему неудобно — партнёрства нет, и весь план
мёртв. Его работа сведена к пяти операциям, всё остальное — наше.

| Задача юриста | Инструмент | Статус |
|---|---|---|
| Утвердить вопросы аудита (его экспертиза) | документ/таблица → мы вносим | ручное, ок |
| Автор/ревью шаблонов документов | редактор шаблона + предпросмотр + preflight | ✅ есть |
| Подпись под услугой (`disabled → active`) | kill-switch | ✅ есть |
| Отвечать на эскалации | структурированный вопрос + AI-черновик | 📋 малое |
| Видеть свой заработок | простой реестр | 📋 таблица на MVP |

### Что убивает юриста (проектируем против этого)
- **Свободные вопросы в 23:00** → формат ограничен: вопрос только по пробелу из аудита, с контекстом.
- **Одинаковые вопросы по кругу** → повторившийся вопрос становится FAQ/скиллом и больше до юриста
  не доходит. Ёмкость защищена конструкцией, а не обещаниями.
- **Обучение сложному инструменту** → юрист трогает **только шаблоны**. Всё остальное — наша зона.
- **Непонятно, что он заработал** → реестр «клиенты × месяц × доля» с первого дня.

### Онбординг юриста = 3 артефакта, а не обучение
1. Список вопросов аудита на утверждение.
2. Список шаблонов на ревью (мы готовим черновики — он правит).
3. Договорённость о доле и SLA эскалаций (сколько вопросов/срок ответа).

## 6. UX-принципы: безболезненно для обеих сторон

### Для врача
- **Ноль регистрации** — Telegram, он уже залогинен.
- **Ценность до оплаты** — самоаудит бесплатен и даёт результат сразу. Пустого экрана не существует.
- **Никогда не показывать форму на 84 поля** — агент спрашивает по одному, как разговор.
  Это и есть MCP+skills в проде.
- **Мгновенно** — детерминированная генерация, никаких «документ формируется…».
- **Одна цифра вместо меню** — «готовность 78%» и что горит. Не список модулей.
- Десктоп-веб — когда дойдём до работы с большими документами (заполнение ведомостей со смартфона —
  мучение); в MVP хватает Telegram.

### Для юриста
- **Он правит текст, а не заполняет систему.** Редактор шаблона + предпросмотр.
- **Preflight-светофор** — не даёт опубликовать шаблон с дырами. Его репутация защищена машиной.
- **Один вход для эскалаций**, не пять чатов.
- **Человеческий контроль — фича, а не ограничение.** Финальную кнопку «active» жмёт он.

## 7. Экономика (модель, не факт — цифры валидируем интервью)

**Допущения к проверке:**
- Подписка 1 500–2 500 грн/мес · доля юриста ~70–75% (бенчмарк white-label) · наша доля 25–30%
- Себестоимость обслуживания клиента ≈ 0 (генерация детерминирована) + доля эскалаций
- Utilization эскалаций ~25% (бенчмарк ABA) — то есть 3 из 4 клиентов в месяц юриста не трогают

**Что делает модель жизнеспособной:** не цена, а то, что **один юрист ведёт сотни клиентов**, потому
что рутина снята. Ключевая метрика юнит-экономики — **часы юриста на клиента в месяц**. Если она не
падает с ростом базы — модель не работает, и это надо увидеть на первых 10 клиентах, а не на 500.

**Ценовые якоря (верифицированы):** штраф за неоформленного сотрудника 86 470 грн = 3–4 года подписки;
учреждения платят 3.3–9 тыс./мес за инфо-системы; врачи уже платят ~300 грн бухгалтерии ежемесячно.

## 8. Фазы

| Фаза | Что | Гейт перехода |
|---|---|---|
| **0. Валидация** | 5–10 интервью по скрипту | ≥3 готовы пройти аудит, ≥1 сам спросил цену |
| **1. MVP (Wizard of Oz)** | самоаудит + ручное закрытие пробелов + ручная оплата | **≥5 платящих** |
| **2. Автоматизация повторов** | то, что руками делали 10 раз: кабинет, алерты, биллинг | retention ≥ 3 мес |
| **3. Вторая ниша** | ветеринария (копия плейбука) — проверка тезиса «ниша = конфигурация» | ниша закрыта без нового кода |
| **4. Мультитенант / white-label** | второй юрист, роли, клиники (ТОВ) | 2-й юрист-партнёр найден |

## 9. Риски и честные гейты

| Риск | Гейт / митигация |
|---|---|
| **WTP не подтверждена** | фаза 0 — до строительства. ≥5 платящих или стоп |
| **Юрист-партнёр не найден** | без него фаза 1 не стартует. Это supply-ограничение, не техническое |
| **Ёмкость юриста захлёбывается** | метрика «часы юриста на клиента» с первого клиента; формат вопросов + FAQ + платная эскалация |
| **Зависимость от одного лица** | второй юрист-методолог до фазы 4; бренд продукта растёт рядом с лицом |
| **Переоценка обещаний** | никаких «100% защиты» (DoNotPay-прецедент). Оферта: инструмент содействия, не страховой полис |
| **Скоуп поплыл** | правило: новая функция = ответ на повторившуюся задачу. Не «на всякий случай» |

## Резюме

Сегмент зафиксирован: **соло-ФОП** — там верифицированная пустая ниша и ролей нет вовсе, что делает
продукт на порядок проще. Масштабирование обеспечивает принцип «услуга = данные»: doc-engine снимает
производство документа, MCP+skills снимает интервью (самую дорогую часть юриста), обе оси читают одну
строку `services`. Отсюда MVP: **самоаудит — это тоже `form_config`**, поэтому строим конфигурацию +
тонкий слой скоринга, а не новую систему; всё остальное — вручную. Юрист трогает только шаблоны и
эскалации, его ёмкость защищена конструкцией продукта. Плюшки добавляем по мере повторения реальных
задач, не заранее. Гейт: ≥5 платящих на фазе 1 — иначе меняем сегмент, а не добавляем модули.
