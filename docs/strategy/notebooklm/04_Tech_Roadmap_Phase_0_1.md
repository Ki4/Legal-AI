# Технический roadmap — Phase 0 и Phase 1

**Горизонт планирования:** 8 недель (Phase 0 PoC) + 8 недель (Phase 1 Lawyer Beta)
**Обновляется:** еженедельно на основе ретроспективы

---

## Phase 0 — Hardcoded PoC (недели 1-8)

### Цель фазы

Доказать, что платформа может генерировать юридические документы уровня «готово к суду» в трёх разных уровнях сложности. Критерий успеха: Ольга подтверждает, что документы не требуют серьёзных правок перед подачей.

### Состав команды

- **Сергей** — ежедневная разработка, 4-6 часов в день
- **Claude (AI-ассистент)** — парное программирование, исполнение рутины
- **Ольга** — юридическая валидация, ~5 часов в неделю
- **Дядя** — read-only наблюдение, периодические архитектурные замечания

### Критерии готовности PoC

- [ ] 5 услуг реализованы и работают end-to-end
- [ ] Из них минимум 3 Tier 1 (шаблон + склонения) и 1 Tier 2 (гибрид)
- [ ] Ольга лично проверила минимум 5 документов каждой услуги и подтвердила качество
- [ ] Все критические security-уязвимости закрыты (секреты не в Git, RLS работает, PII зашифрованы)
- [ ] Базовая защита от злоупотреблений (rate limit, проверка Telegram initData)
- [ ] Audit log всех сгенерированных документов работает

### Неделя 1 — Стабилизация текущей базы

**Фокус:** закрыть накопленный технический долг и security-риски, подготовить репозиторий к работе с партнёрами.

**Задачи:**

1. **Инвентаризация незакоммиченных изменений**
   - Проверить все modified и untracked файлы
   - Разбить на логические коммиты с внятными сообщениями
   - Ввести правило документирования изменений через `.claude/changelog.md`

2. **Security — вынести секреты из n8n workflow JSON**
   - SUPABASE_SERVICE_KEY и ENCRYPTION_KEY сейчас хранятся в коммитах Git — это критическая уязвимость
   - Ротировать ключи
   - Перенести в переменные окружения n8n или в отдельный .env файл вне Git
   - Удалить из Git-истории (git filter-branch или BFG)

3. **Обновление стратегических документов**
   - `project_strategy_v2.md` — канонический источник стратегии (✅ сделано)
   - Перевод материалов для NotebookLM для встречи с Ольгой (✅ сделано)

**Deliverable:** чистый репозиторий, отсутствие секретов в истории, документированная стратегия.

### Неделя 2 — Услуга №2 «Алименты» (Tier 1)

**Фокус:** повторить успех Услуги №1 «Развод» на второй услуге того же уровня сложности. Цель — выявить переиспользуемые паттерны.

**Задачи:**

1. **Сбор требований от Ольги**
   - Эталонный документ (как она сейчас пишет заявление о взыскании алиментов)
   - Список обязательных полей формы
   - Ссылки на статьи СК Украины
   - Типичные edge cases и грабли

2. **Реализация**
   - Form config (JSON) с условной логикой
   - JavaScript шаблон документа
   - Integration с n8n для генерации
   - Подключение AI для склонения имён

3. **Валидация Ольгой**
   - Генерация 10 тестовых документов с разными входными данными
   - Ольга проверяет каждый
   - Исправления на основе замечаний

**Deliverable:** работающая услуга «Алименты», готовая к demo.

### Неделя 3 — Услуга №3 «Претензия о возврате товара» (Tier 1)

**Фокус:** третья услуга того же tier. **После неё — первая ретроспектива паттернов.**

**Задачи:**

1. Сбор требований от Ольги (аналогично неделе 2)
2. Реализация с максимальным переиспользованием из услуг 1-2
3. Валидация Ольгой
4. **Ретроспектива паттернов:**
   - Что в шаблонах повторяется между услугами 1, 2, 3?
   - Какие поля формы типовые, какие уникальные?
   - Какие promt'ы для AI похожи?
   - Что можно вынести в общие утилиты?

**Deliverable:** 3 работающие услуги Tier 1 + документ с выявленными паттернами.

### Неделя 4 — Рефакторинг на основе паттернов

**Фокус:** применить выводы из ретроспективы к кодовой базе. Не добавляем функциональность, улучшаем архитектуру.

**Задачи:**

1. **Общие утилиты:**
   - Функция склонения имён (единая для всех услуг)
   - Генератор шапки документа (ФИО истца, суд, дата)
   - Валидатор обязательных полей
   - Утилиты для работы с датами в украинском формате

2. **Унификация form_config:**
   - Общие типы полей (ФИО, паспорт, адрес, телефон)
   - Общие условные правила (show_if patterns)

3. **Ревью дяди:**
   - Показать ему архитектуру после рефакторинга
   - Получить замечания и зафиксировать

**Deliverable:** более чистая и переиспользуемая кодовая база.

### Неделя 5 — Услуга №4 «Заявление в ЖЭК/ОСББ» (Tier 1)

**Фокус:** проверить, насколько быстрее создаётся новая услуга после рефакторинга. Цель — реализовать за 3 дня вместо 7.

**Задачи:**

1. Сбор требований от Ольги
2. Максимально быстрая реализация с использованием утилит из недели 4
3. Валидация

**Deliverable:** 4-я услуга Tier 1, измеренное время разработки.

---

### Неделя 6 — Услуга №5 «Возражения на иск» (Tier 2 — ПИЛОТ)

**Фокус:** первая услуга уровня Tier 2 (гибрид). Это самая важная неделя в Phase 0 — проверяем, работает ли подход с AI-вставками в production-качестве.

**Задачи:**

1. **Архитектура промпта для AI:**
   - Какие данные AI получает на вход
   - Какой объём текста AI должен сгенерировать
   - Какие ограничения (не использовать статьи, которых нет в списке; не придумывать факты)

2. **Валидация вывода AI:**
   - Схема для проверки структуры
   - Список запрещённых паттернов
   - Fallback: если AI-вывод невалидный → показать юристу-партнёру для ручного дописывания

3. **Escalation rules:**
   - Первая реализация массива условий, при которых случай **не генерируется**, а передаётся живому юристу
   - Базовый UX для экрана эскалации

4. **Интенсивная валидация Ольгой:**
   - Минимум 15 тестовых кейсов с разным уровнем сложности
   - Ольга оценивает не только корректность, но и **стиль юридического текста**

**Deliverable:** 5-я услуга работает в Tier 2, escalation rules реализованы, Ольга подтверждает качество.

### Неделя 7 — Security, защита от злоупотреблений, тестирование

**Фокус:** подготовка продукта к показу внешним юристам.

**Задачи:**

1. **Проверка подписи Telegram initData** — защита от подделки запросов к webhook
2. **Rate limiting** — ограничение числа запросов на одного пользователя (например, 5 документов в час)
3. **Auto-create user flow** — корректная обработка сценария, когда пользователь открывает форму по прямой ссылке, никогда не нажимая /start
4. **Error UX** — понятные сообщения об ошибках вместо «что-то пошло не так»
5. **n8n Error Handler** — глобальный обработчик ошибок workflow, который уведомляет Сергея

**Deliverable:** продукт готов к внешнему demo, без стыдных багов.

---

### Неделя 8 — Полировка, документация, первое внутреннее demo

**Фокус:** подготовиться к Phase 1 (Lawyer Beta).

**Задачи:**

1. **Полировка UX:**
   - Анимации и переходы
   - Проверка на разных устройствах (iOS, Android, старые телефоны)
   - Проверка Telegram WebApp API во всех edge cases

2. **Документация для юристов-партнёров:**
   - Гайд «Как использовать платформу» (1 страница, картинки)
   - Гайд «Что происходит с моими клиентами» (юридические аспекты, ответственность)
   - FAQ

3. **Внутреннее demo:**
   - Сергей + Ольга проходят все 5 услуг «глазами клиента»
   - Фиксируются последние замечания
   - Создаётся список «что исправить перед внешним показом»

**Deliverable:** PoC готов к Phase 1. Можно показывать первым внешним юристам.

## Phase 1 — Lawyer Beta (недели 9-16)

### Цель фазы

Найти product-market fit с юристами как первыми платящими пользователями. Критерий: минимум 3 юриста регулярно используют продукт и платят без напоминаний.

### Неделя 9-10 — Первый внешний юрист

**Задачи:**
- Ольга представляет платформу 2-3 своим доверенным коллегам
- Выбираем одного для пилота
- Даём доступ, учим пользоваться
- Наблюдаем, фиксируем все трения

**Ключевые вопросы:**
- Понял ли юрист за 15 минут, как это работает?
- Сгенерировал ли он хотя бы один документ без нашей помощи?
- Готов ли он использовать это в работе с реальными клиентами?

---

### Неделя 11-12 — Обратная связь и исправления

**Задачи:**
- Еженедельная встреча с пилотным юристом (30-60 минут)
- Список фидбека → приоритизация → реализация критических правок
- Документация всех выявленных edge cases

**Критические метрики:**
- Сколько документов сгенерировал юрист за неделю
- Сколько из них он отдал клиентам
- Сколько потребовало правок и каких
- Готов ли он платить за продукт

---

### Неделя 13-14 — Подключение юристов №2 и №3

**Задачи:**
- Расширение круга тестирования
- Проверка: работают ли улучшения, сделанные на основе фидбека №1, для новых юристов?
- Первые платежи (даже символические — 100-500 грн)

---

### Неделя 15-16 — Ретроспектива Phase 1 и решение о Phase 2

**Задачи:**
- Анализ всех данных: usage, retention, payments, feedback
- Решение: готовы ли мы к Phase 2 (инфлюенсеры)?
- Если **да** — подключаем дядю в активную роль, начинаем планировать scaling
- Если **нет** — возвращаемся к PoC, исправляем критические проблемы, повторяем Phase 1

## Данные, которые мы собираем на каждой фазе

### На PoC (Phase 0)
- Время разработки каждой услуги
- Количество итераций правок после ревью Ольги
- Паттерны, которые повторяются
- Edge cases, которые мы не предусмотрели

### На Lawyer Beta (Phase 1)
- Количество сгенерированных документов по каждой услуге
- % документов, которые юрист отдал клиентам без правок
- % документов, которые потребовали ручного вмешательства
- Количество случаев эскалации (Tier 2)
- Время, которое юрист экономит на каждом документе (по его оценке)
- Готовность платить (в цифрах)

Эти данные — основа для решений о Phase 2 и для pitch'а потенциальным инфлюенсерам.

## Что НЕ делаем в Phase 0 и Phase 1 (осознанные отказы)

- ❌ **Не строим service builder** — преждевременно
- ❌ **Не ищем инвестиции** — преждевременно, уничтожит долю
- ❌ **Не делаем мобильное приложение** — Telegram WebApp достаточно
- ❌ **Не добавляем 10 новых услуг одним махом** — нужна валидация паттернов
- ❌ **Не нанимаем людей** — команды (Сергей + Ольга + Claude + дядя в read-only) хватает для PoC
- ❌ **Не запускаем публичный маркетинг** — сначала доказываем продукт на юристах
- ❌ **Не делаем Tier 3 (полностью AI)** — слишком рискованно для PoC
