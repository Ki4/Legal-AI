# Legal AI — Презентація продукту для юриста

> Дата: березень 2026
> Версія: MVP (перша послуга — розлучення)
> Мета зустрічі: показати продукт, отримати фідбек по якості документа, обговорити нову послугу

## 1. ЗАГАЛЬНА ІДЕЯ

### Що це?
Платформа, яка автоматично генерує юридичні документи (позовні заяви, заяви на аліменти тощо) через Telegram-бота. Клієнт заповнює форму — отримує готовий документ для подачі до суду.

### Для кого?
- **Клієнти (B2C):** люди, яким потрібен юридичний документ, але немає грошей/часу на повноцінну консультацію юриста
- **Юристи-партнери:** отримують "теплі ліди" — клієнтів, які вже заповнили дані і можуть потребувати подальшої допомоги

### Бізнес-модель
```
Клієнт платить за документ (50-200 грн)
  ├── Платформа забирає комісію
  └── Юрист-партнер отримує свою частку + контакт клієнта
```

## 2. TELEGRAM — ЧОМУ САМЕ ВІН

### Переваги Telegram як каналу
| Перевага | Деталі |
|----------|--------|
| **Нульовий бар'єр входу** | Клієнт вже в Telegram — не треба встановлювати додаток, реєструватись |
| **Автоматична ідентифікація** | Telegram передає `user_id` автоматично — без логіну/паролю |
| **Push-сповіщення безкоштовно** | Бот надсилає повідомлення напряму, без SMS/email |
| **Мобільний UX** | 90%+ користувачів з телефону — Telegram Mini App оптимізований під це |
| **Довіра** | Люди довіряють Telegram більше, ніж невідомому сайту |

### Як працює Telegram Mini App (TWA)

**Що це:** Міні-додаток (веб-сторінка), який відкривається прямо всередині Telegram. Виглядає як нативний додаток, але це наш React-сайт.

**Чому не звичайний сайт:**
- TWA отримує дані користувача (id, ім'я) автоматично від Telegram
- Не потрібна окрема реєстрація
- Форма відкривається в контексті чату з ботом

**Важливо щодо безпеки даних:**
- Дані НЕ зберігаються в Telegram Cloud — вони відправляються напряму на наш сервер
- Telegram не має доступу до персональних даних клієнта (ПІБ, ІПН, адреси)
- Telegram бачить тільки факт відкриття Mini App, але не зміст форми

### Перший контакт з ботом — як це виглядає

```
Крок 1: Клієнт знаходить бота (@Test_legal_AI_bot)
         або отримує посилання від юриста/реклами

Крок 2: Натискає /start → бот відповідає привітанням:
         "Вітаю! Я допоможу підготувати юридичні документи."

Крок 3: Клієнт пише "розлучення" або обирає послугу з меню
         → Бот відповідає описом послуги + кнопкою:

         📄 *Розірвання шлюбу*
         Підготовка позовної заяви про розірвання шлюбу.
         Натисніть кнопку нижче, щоб заповнити форму:

         [ 📝 Заповнити форму ]  ← Inline кнопка з web_app URL

Крок 4: Натискання кнопки → відкривається Mini App з формою
```

### Що передається між компонентами

```
Telegram → Mini App:
  - user_id (числовий ID в Telegram)
  - first_name (ім'я користувача)
  - service slug (яку послугу обрав — "divorce", "alimony" тощо)

Mini App → наш сервер (n8n):
  - service_slug: "divorce"
  - user_id: "236581343"
  - consented_at: "2026-03-27T19:40:00Z"  ← коли погодився на обробку даних
  - answers: { all 53 form fields }

Наш сервер → Telegram:
  - Повідомлення з посиланням на готовий Google Doc
```

## 3. ЗБІР ДАНИХ — УНІВЕРСАЛЬНА ФОРМА

### Принцип: одна форма для будь-якої послуги

Форма **не захардкоджена** під розлучення. Вона генерується динамічно з JSON-конфігу, який зберігається в базі даних. Це означає:

- Нова послуга = новий JSON-конфіг → нова форма автоматично
- Юрист може редагувати форму через адмін-панель (Service Builder)
- Один і той же React-компонент рендерить будь-яку форму

### Структура форми (на прикладі розлучення)

**4 вкладки (таби):**
```
1. Позивач      — ПІБ, дата народження, ІПН, адреса, телефон, email
2. Відповідач   — ПІБ, дата народження, ІПН, адреса (аналогічно)
3. Шлюб і сім'я — дата шлюбу, місце реєстрації, діти, майно, борги
4. Провадження  — тип, судові витрати, аліменти, оригінали документів
```

**53 поля, з яких:**
- ~25 обов'язкових (позначені зірочкою)
- ~28 умовних (з'являються залежно від відповідей)

### Типи полів
| Тип | Приклад | Як виглядає |
|-----|---------|-------------|
| `text` | Прізвище, Місто | Звичайне текстове поле |
| `textarea` | Опис майна | Багаторядкове поле |
| `date` | Дата народження | Нативний datepicker (з урахуванням bottom bar) |
| `boolean` | Є діти? | Дві кнопки "Так" / "Ні" |
| `choice` | Тип провадження | Radio-кнопки з описом |
| `multicheck` | Документи | Чекбокси (можна обрати кілька) |
| `phone` | Телефон | Поле з маскою +380 |

### Умовна логіка (show_if)

Поля з'являються/зникають залежно від відповідей:

```
Приклад 1:
  "Є діти?" = Так → з'являється поле "Дані дітей"
  "Є діти?" = Ні → поле дітей приховане

Приклад 2:
  "Немає ІПН (з релігійних переконань)" = Так → ховається поле ІПН
  → з'являється поле "Серія/номер паспорту"

Приклад 3:
  "Чи є спір щодо майна?" = "Окреме провадження"
  → ховаються поля з описом майна
```

**Технічна деталь:** Коли поле ховається, його відповідь автоматично очищається. Це запобігає відправці некоректних даних.

### Прогрес і валідація

- **Прогрес-бар** зверху показує % заповнення
- **Галочка на табі** з'являється коли всі обов'язкові поля заповнені
- **Підказки (tooltip)** біля складних полів — натисни на "?" щоб прочитати
- **Пояснення (explanation)** — блоки з корисною інформацією між полями
- **Валідація при відправці** — список незаповнених обов'язкових полів

### Consent-екран (GDPR)

**Перед** заповненням форми клієнт бачить екран-дисклеймер:

```
📄 Розлучення
   Підготовка юридичного документа

┌────────────────────────────────┐
│ 📄 Що буде далі               │
│ Ви заповните форму з даними.   │
│ AI-система підготує документ.  │
├────────────────────────────────┤
│ 🛡 Захист даних                │
│ Дані шифруються (AES-256)      │
│ відповідно до Закону «Про      │
│ захист персональних даних».    │
├────────────────────────────────┤
│ 🕐 Строк зберігання            │
│ Дані видаляються через 90 днів.│
│ Можна запросити раніше.        │
└────────────────────────────────┘

Детальніше: Політика конфіденційності

[ Погоджуюсь, перейти до форми ]
```

Тільки після натискання кнопки — відкривається форма. Час згоди (`consented_at`) зберігається в базі разом з кейсом.

## 4. ЯК ЗБЕРІГАЄМО ДАНІ — ДЕ, ЧОМ І ЯК ЗАХИЩАЄМО

### Архітектура зберігання

```
┌─────────────────────────┐      ┌──────────────────────────┐
│   n8n (оркестрація)     │      │   Supabase (база даних)  │
│                         │      │                          │
│  ENCRYPTION_KEY ──────────────→│  cases.encrypted_data    │
│  (64-символьний ключ)   │      │  (зашифрований рядок)    │
│                         │      │                          │
│  Ключ тут ↑             │      │  Дані тут ↑              │
└─────────────────────────┘      └──────────────────────────┘
         ↑                                    ↑
    Компрометація                      Компрометація
    одного НЕ розкриває               одного НЕ розкриває
    дані іншого                       дані іншого
```

### Що зберігається

| Дані | Де | Шифрування | Строк |
|------|----|-----------|-------|
| ПІБ, ІПН, адреси, телефони | Supabase `cases.encrypted_data` | AES-256-GCM | 90 днів |
| Telegram user_id | Supabase `identities` | Ні (не є PII) | Безстроково |
| Готовий документ | Google Docs | Google encryption | Безстроково* |
| Форма (UI стан) | Браузер клієнта | — | До закриття вкладки |

*Документ в Google Docs — окреме питання. Поки що залишається. Можна додати auto-delete пізніше.

### Формат шифрування

```
v1:805ce86755f132a6d531efa7:d27410e0051b8b7e1d29cc:a3f2...

Версія ↑     IV (12 байт) ↑         Auth Tag ↑        Зашифровані дані ↑
```

- **v1** — версія формату (для майбутньої ротації ключів)
- **AES-256-GCM** — стандарт шифрування (використовується у банківських системах)
- **Кожен запис** має унікальний IV (initialization vector) — навіть однакові дані виглядають по-різному

### GDPR / Закон «Про захист персональних даних»

| Вимога | Статус | Деталі |
|--------|--------|--------|
| Згода на обробку | ✅ Зроблено | Consent-екран з timestamp |
| Шифрування | ✅ Зроблено | AES-256-GCM |
| Право на доступ | ✅ Зроблено | `scripts/decrypt-case.mjs` |
| Строк зберігання | ✅ Зроблено | 90 днів, auto-delete |
| Право на видалення | ⬜ В розробці | Через бота (поки вручну) |
| Мінімізація даних | ⬜ Планується | Не зберігати зайві поля |

## 5. ГЕНЕРАЦІЯ ДОКУМЕНТА — ГІБРИДНИЙ ПІДХІД

### Проблема: чому не 100% AI?

Перші версії використовували повну AI-генерацію (GPT/Gemini). Проблеми:
1. **Галюцінації** — AI вигадував номери статей, дати, адреси
2. **Нестабільність** — той самий промпт давав різні результати
3. **Юридична відповідальність** — неправильна стаття = документ не приймуть у суді

### Рішення: 95% JS шаблон + 5% AI

```
┌──────────────────────────────────────────────────────┐
│                    JS ШАБЛОН (95%)                     │
│                                                       │
│  ✅ Всі дати — конвертуються програмно               │
│  ✅ Всі адреси — підставляються з форми              │
│  ✅ Всі статті закону — захардкоджені                │
│  ✅ Умовна логіка — if/else в JavaScript             │
│  ✅ Структура документа — детермінована              │
│                                                       │
│  0% галюцінацій — все перевірено тестами              │
└──────────────────────────────────────────────────────┘
                         +
┌──────────────────────────────────────────────────────┐
│                    AI (5%)                             │
│                                                       │
│  🤖 Тільки відмінювання ПІБ:                         │
│     "Шевченко Наталія Петрівна"                      │
│     → "Шевченко Наталією Петрівною" (орудний)        │
│     → "Шевченко Наталії Петрівни" (родовий)          │
│                                                       │
│  🤖 Відмінювання назв установ:                       │
│     "Центральний РАЦС м. Харкова"                    │
│     → "Центральному РАЦСі м. Харкова" (місцевий)    │
│                                                       │
│  6 полів JSON, ~200 токенів, температура = 0          │
└──────────────────────────────────────────────────────┘
```

### Чому це краще

| Аспект | Повна AI-генерація | Наш гібрид |
|--------|-------------------|------------|
| Галюцінації | Можливі завжди | Неможливі (дані з форми) |
| Статті закону | AI може вигадати | Захардкоджені, перевірені |
| Дати | AI може переплутати | Конвертуються програмно |
| Тестування | Складно (недетерміновано) | 4 сценарії, 17 перевірок, golden files |
| Вартість AI | ~1000 токенів/документ | ~200 токенів/документ |
| Швидкість | 5-15 сек | 2-3 сек |

### Які закони захардкоджені (для розлучення)

| Закон | Статті | Остання редакція |
|-------|--------|-----------------|
| Сімейний кодекс України | ст. 105, 110, 183 | 04.03.2026 |
| ЦПК України | ст. 175 | 17.07.2025 |
| Закон «Про судовий збір» | ст. 4, 5 | 10.03.2026 |

**Важливо:** Дати редакцій перевірені на zakon.rada.gov.ua і збережені в базі. Планується автоматичний моніторинг змін (щотижневий CRON).

### Тестування документів

```
4 тестові сценарії:
┌────────────────────────────────────────────────────┐
│ Сценарій 1: Просте розлучення без дітей           │ ✅ 17/17
│ Сценарій 2: Діти + аліменти (2 дітей, % доходу)   │ ✅ 17/17
│ Сценарій 3: Майно + борги + звільнення від збору   │ ✅ 17/17
│ Сценарій 4: Мінімум (тільки обов'язкові поля)      │ ✅ 17/17
└────────────────────────────────────────────────────┘

17 структурних перевірок включають:
- Наявність "ПОЗОВНА ЗАЯВА" в тексті
- Правильні номери статей СК, ЦПК
- Наявність блоків: вступ, суть, прохальна частина, додатки
- Дата та підпис
```

## 6. ДОСТАВКА ДОКУМЕНТА

### Поточний процес

```
1. JS шаблон генерує текст документа (~3000 символів)
2. Google Docs API:
   a) Копіює шаблон-документ (з правильним форматуванням)
   b) Замінює {{DOCUMENT_CONTENT}} на згенерований текст
   c) Встановлює дозвіл "anyone with link can view"
3. Бот надсилає клієнту в Telegram:
   "📄 Ваша позовна заява готова!
    👇 Відкрийте: [посилання на Google Docs]
    💡 Файл → Завантажити → PDF для друку"
```

### Чому Google Docs, а не PDF

| Google Docs | PDF |
|-------------|-----|
| Клієнт може редагувати | Тільки читання |
| Відкривається в браузері | Потрібен PDF-viewer |
| Автоматична історія версій | Немає |
| Просте API для заповнення | Складніша генерація |

### Що можна покращити (для юриста)

1. **Красивий шаблон Google Docs** — зараз plain text, можна зробити з форматуванням (жирний заголовок, абзаци, відступи)
2. **Множинні плейсхолдери** — замість одного `{{DOCUMENT_CONTENT}}`, юрист створює шаблон з `{{PLAINTIFF_NAME}}`, `{{COURT_NAME}}` тощо
3. **Юрист контролює зовнішній вигляд** — редагує шаблон в Google Docs, не в коді


### Конструктор форм — можливості

- **Автоматичний slug:** "Стягнення аліментів" → `styagnennya_alimentiv`

- **Клонування поля** — копіює з новим ID
- **Переміщення між табами** — dropdown з вибором таба

- **Live preview** — зміни одразу видно без перезавантаження
- **Індикатор змін** — "● Незбережено" з попередженням при закритті

## 8. МОНІТОРИНГ ЗАКОНІВ

### Проблема

Закони в Україні змінюються часто. Наприклад, Сімейний кодекс мав **80+ редакцій**. Якщо стаття змінилась, а шаблон документа — ні, клієнт отримає неправильний документ.

### Рішення: автоматичний моніторинг

```
Кожна послуга прив'язана до конкретних законів:

Розлучення:
  ├── СК України, ст. 105, 110, 183
  │   URL: zakon.rada.gov.ua/laws/show/2947-14
  │   Остання перевірена редакція: 04.03.2026
  │
  ├── ЦПК України, ст. 175
  │   URL: zakon.rada.gov.ua/laws/show/1618-15
  │   Остання перевірена редакція: 17.07.2025
  │
  └── Про судовий збір, ст. 4, 5
      URL: zakon.rada.gov.ua/laws/show/3674-17
      Остання перевірена редакція: 10.03.2026
```

### Як це працюватиме (планується)

```
Щотижня (понеділок 09:00):
  1. Система заходить на zakon.rada.gov.ua
  2. Парсить "Редакція від ДД.ММ.РРРР"
  3. Порівнює з збереженою датою
  4. Якщо змінилось → надсилає alert в Telegram:
     "⚠️ СК України змінився! 04.03.2026 → 15.04.2026
      Перевірте послугу: Розлучення"
  5. В адмін-панелі з'являється жовтий банер
```

### Що потрібно від юриста

При створенні кожної нової послуги юрист вказує:
1. Які закони використовуються (URL на zakon.rada.gov.ua)
2. Які конкретні статті
3. Чому кожна стаття важлива

Це дозволяє системі моніторити тільки релевантні зміни.

## 10. ЩО ПОКРАЩИТИ — ПЛАН РОЗВИТКУ

### Короткострокове (1-2 тижні)

1. **Друга послуга** — юрист заповнює чеклист → розробник будує за 1 сесію
2. **Красивий шаблон Google Docs** — замість plain text, з форматуванням
3. **Моніторинг законів** — підключити CRON, щоб автоматично перевіряти зміни

### Середньострокове (1-2 місяці)

4. **Платежі** — інтеграція з LiqPay/Monobank, revenue share для юристів
5. **AI-критик** — автоматична перевірка документа перед відправкою
6. **Множинні плейсхолдери** — юрист створює шаблон в Google Docs
7. **Self-service** — клієнт сам видаляє/завантажує свої дані

### Довгострокове (3-6 місяців)

8. **Admin Dashboard** — метрики, всі юристи, всі кейси
9. **Invite-система для юристів** — юристи запрошують інших юристів
10. **Мобільний додаток** — якщо потрібно вийти за межі Telegram
11. **CI/CD** — автоматичні тести і деплой при пуші коду

## 11. ПРОЦЕС ДОДАВАННЯ НОВОЇ ПОСЛУГИ

### Що потрібно від юриста (1-2 години)

Юрист заповнює чеклист (`docs/service-builder-checklist.md`):

```
1. БАЗОВА ІНФОРМАЦІЯ
   - Назва послуги: "Стягнення аліментів"
   - Опис для клієнта (1-2 речення)
   - Цільова аудиторія

2. ПИТАННЯ ДО КЛІЄНТА
   - Які дані потрібні? (ПІБ, дати, адреси...)
   - Які поля обов'язкові?
   - Які поля умовні? (якщо X, то показати Y)
   - Підказки до складних полів

3. ШАБЛОН ДОКУМЕНТА
   - Текст документа з плейсхолдерами
   - Або: готовий Google Docs шаблон

4. НОРМАТИВНА БАЗА
   - Які закони використовуються?
   - Які конкретні статті?
   - URL на zakon.rada.gov.ua

5. ТЕСТОВІ СЦЕНАРІЇ
   - 2-4 приклади заповнення форми
   - Очікуваний результат для кожного
```

### Що робить розробник (1 сесія = 3-4 години)

```
1. node scripts/scaffold-service.mjs alimony "Аліменти"
   → генерує каркас файлів

2. Заповнює form_config через Service Builder в адмін-панелі
   (або вручну в JSON)

3. Пише {service}-document.js по чеклисту юриста

4. Додає тестові fixtures і golden files

5. npm run test:docs -- alimony
   → перевіряє всі сценарії

6. End-to-end тест через Telegram
```
