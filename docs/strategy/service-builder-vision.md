## §0. Бачення одним абзацом

Єдина **консоль послуг** в адмінці, де юрист явно бачить: **які послуги є → з чого кожна складається →
як відображається документ → може підключати/відключати їх**, а в майбутньому — **сам додає нову послугу
через інтерфейс (Service Builder)**, включно з можливістю підключати RAG / GraphRAG тощо. І головне —
**через інтерфейс переконується, що все коректно** (панель готовності / preflight), бо для юридичних
документів довіра = продукт.

## §1. Чому це реально (ключовий інсайт)

**Послуга — це дані, а не код.** Рядок у таблиці `services`:

```
послуга = form_config (форма)
        + document_template (DSL-шаблон + keep-block розмітка)
        + generation_mode (template / hybrid / ai_generate)
        + citations (статті) + watched_laws (моніторинг)
        + checklist (обов'язкові юр-пункти)
```

Рушій (`render-document.js`, n8n `form-submit`) **уже service-agnostic** — збирає документ, нічого не
знаючи про конкретну послугу. Тому «додати послугу» = **зробити й перевірити ці дані**. Зараз це роблять
руками/скриптами. **Service Builder = UI, що виробляє ті самі дані + валідує їх.** Магії нема.

## §2. Твоя ідея → що вже живе (звірено в коді, session 60)

| Частина ідеї | Де це вже є | Статус |
|---|---|---|
| **Які послуги є** | `DashboardPage` — список карток послуг (`ServiceCard`) зі статусом, ціною, режимом | ✅ |
| **З чого складаються** | `ServiceViewPage` → `ServiceAnatomy`: вкладки Документ · Розкладка (нова, #84) · Анатомія · Граф зв'язків · Алгоритм форми + health 🟢/🟡/🔴 + закони/цитати | ✅ |
| **Як відображаються документи** | `DocumentPreview` (готовий приклад / порожній шаблон) + `DocumentLayoutPreview` (#84 — розкладка по A4) | ✅ |
| **Підключати / відключати** | Kill-switch статусу `active / needs_review / disabled`: тумблер прямо в `DashboardPage`, `<select>` у `ServiceEditPage`, + `scripts/service-lifecycle.mjs` | ✅ |
| **Білдер послуг (майбутнє)** | Форму вже можна редагувати (`FormBuilder`/`ServiceEditPage`); повного «додай послугу без розробника» — ще нема | 📋 |

**Висновок:** «каталог + з чого складається + як виглядає документ + увімк/вимк» — **вже працює**, лише

## §3. Як через інтерфейс переконуватись, що «все нормально» (preflight-панель)

Ядро для юр-продукту. **Не окрема велика робота, а збірка вже наявних детермінованих перевірок** в один
«світлофор готовності». Червоний → кнопка «Активувати» заблокована.

| Перевірка | Що вже є | Що показує юристу |
|---|---|---|
| Покриття полів (форма↔шаблон) | service-mirror health 🟢/🟡/🔴 ✅ | кожне поле використане, нема дір `________` |
| Обов'язкові пункти | checklist validator (regex) ✅ | шапка / ПРОШУ / дата+підпис / реквізити на місці |
| Цитати законів | citations golden ↔ watched_laws ✅ | статті не «дрейфують», закони під моніторингом |
| Розкладка | `DocumentLayoutPreview` (#84) ✅ | підпис не осиротів, блоки цілісні на A4 |
| Пробний прогін | `DocumentPreview` на sampleAnswers ✅ | готовий документ на тестових даних |
| Стабільність (template) | parity/golden тести ✅ | байт-у-байт, без сюрпризів |
| Людина | статус стартує `disabled` → Оля тисне active | юр-підпис = обов'язковий гейт |

Філософія проекту: **людський контроль — це feature, а не обмеження.**

## §4. Як лягають RAG / GraphRAG у майбутньому

Архітектура `generation_mode`-dispatch **уже це допускає** — RAG/GraphRAG це не новий рантайм, а
**додаткове джерело контексту** для AI-кроку. **Принцип: кожна нова AI-здатність приходить ЗІ СВОЄЮ
панеллю верифікації.** Не додаємо capability без способу перевірити її в UI.

- **RAG** (`law_chunks` + pgvector вже є): у білдері toggle «використати RAG-пошук» + привʼязка до корпусу.
  Verification-панель показує *які чанки знайшлись* + **groundedness** (цитата ∈ базі) — той самий
  детермінований anti-hallucination підхід, що вже в `preview-excerpt` / `law-change-groundedness`.
- **GraphRAG** (roadmap 2.1, `law_relations`): білдер показує *які звʼязки законів використані*; кожен
  проходить HITL-підтвердження (roadmap: «жоден звʼязок не в граф без підтвердження юриста»).
  Verification = карта звʼязків + confirm/reject.

## §5. Пошарова траєкторія (знизу вгору, не стрибати одразу в білдер)

```
✅ Перегляд послуги (service-mirror + #84)             ← ми тут
📋 #101 Редактор розкладки (клік-розмітка keep-together)
📋 #51  Редактор шаблону документа
📋 #10  Конструктор полів (drag&drop) + preflight-панель «Готовність»
📋 #18/#20 Повний Service Builder (майстер: форма+шаблон+закони+чекліст)
      └── пізніше: RAG / GraphRAG як capability-toggles, кожен зі своєю verification-вкладкою
```

Кожен шар = окрема Tier-2 фіча, кожен спирається на вже побудований фундамент (реєстр блоків #84,
doc-engine SSoT, lifecycle-статуси).

## §6. Чесні обмеження

1. **AI-кроки не перевіряються детерміновано на 100%** (hybrid/ai_generate/RAG) → потрібні **evals**
   (#93, відкладено) + human sign-off лишається обовʼязковим для легалки.
2. **Складність росте нелінійно:** білдер для `template`-послуги простий; для GraphRAG — потрібен граф +
   ревʼю звʼязків. Будувати пошарово.
3. **Це великий продукт сам по собі** → кожен шар з власним ТЗ, не все одразу.
