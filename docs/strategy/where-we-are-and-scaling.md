# Где мы на самом деле и как масштабируемся

> Честная оценка состояния продукта на 2026-06-26 (перед демо Ольге 1 липня) + теория масштабирования.
> Контекст: 2 живые услуги (divorce, alimony), фаза презентации/доказательства, не масштабированный продукт.

---

## 1. Режим работы этой фазы: self-determine + post-hoc review

Точка проверки качества — **встреча с Ольгой 1 липня**, а это **до** реального масштаба. Сейчас услуги
крутятся на маленьком объёме (демо + единичные живые тесты). Поэтому режим:

> делаем по своему исследованию → Ольга ловит расхождения по факту → составляем список → идём по списку

имеет **маленький радиус поражения**. Ошиблись в формулировке — поправили шаблон за минуту, никто не
пострадал. Это **корректный режим для фазы презентации**, но не навсегда: когда пойдёт реальный объём,
каждая *новая* услуга всё равно должна получить sign-off до выхода в прод на массу.

**Метод честного self-determine:**
- Стандартные иски (divorce/alimony) — типовые; формулировки есть в СК/ЦПК, судебной практике, публичных
  образцах. Research-based best-effort попадает в ~80–90%.
- Чего мы НЕ знаем сами — свежая практика конкретных судов и нюансы в голове практикующего юриста.
- Поэтому: делаем по исследованию **+ ведём явный список «тут не уверены»** → этот список на встречу 1-го.
- Формула: не «мы как юрист», а «мы сделали обоснованно и честно отметили дыры».

**Единственный настоящий «нельзя без неё»** — флип `alimony-change` (hybrid) в прод: новый сервис,
эмитящий судебный документ через менее детерминированный путь. Он сознательно отложен (hybrid не приоритет),
поэтому все остальные таски — в зелёной зоне «можно самим».

## 2. Где мы на самом деле

**2 услуги — это не продукт. Это доказательство, что пайплайн работает, и витрина для презентации.**

Живой конвейер (реальный и хороший):

```
Telegram → форма (form_config) → n8n → детерминированный шаблон (doc-engine) → PDF/DOCX → приватная доставка
```

263 parity-теста, court-ready вывод, PII закрыта. Но:

- Обе услуги — **руками написанные шаблоны** в git + CLI. Добавить услугу = разработчик пишет
  template-DSL + `form_config` + citations + деплоит.
- Юрист **не может** сам создать услугу — админка её только **показывает** (service-mirror), не редактирует.
- Sign-off Ольги — неформальный, не часть продукта.

> **Продукт — это не divorce и alimony. Продукт — это машина, которая производит услуги.**
> Машина есть, но «оператор машины» пока разработчик, а не юрист.

## 3. Узкое место масштабирования: авторинг, а не генерация

Генерация **решена** — детерминированные шаблоны работают. Бутылочное горлышко — *как быстро появляется
новая проверенная услуга*. Сегодня это «разработчик строит каждую вручную» → не масштабируется дальше
горстки.

Три рычага, превращающие 2 → 20 → 100:

### Рычаг 1 — Service Builder (авторинг для юриста)
Самый главный разрыв продукта. Юрист сам собирает услугу (форма + блоки документа) без git/CLI. Множитель:
«разработчик строит каждую» → «юрист сам себя обслуживает». Без этого Сергей — узкое место на каждой услуге.

### Рычаг 2 — Блочная модель A/B/C/D (теория безопасного масштаба)
- **A** — детерминированная подстановка (большинство документа).
- **B** — абзацы по правилу (DSL `{{#if}}` уже умеет, `divorce.document.txt`).
- **C** — LLM-черновик + ревью (редко).
- **D** — эскалация к живому юристу (сложные кейсы; часто лучше, чем C).

Дешёвые услуги добавляются как детерминированные шаблоны пачками; тяжёлый LLM-стек **не строим**, пока
конкретная услуга его не потребует. (Поэтому hybrid сознательно отложен.)

### Рычаг 3 — Мониторинг законов (CRON + impact-агент)
Держит N услуг живыми без N× ручного слежения. Закон поменялся → монитор флипает услугу в `needs_review`
→ агент драфтит «что изменилось + влияние по услугам» для подписи юриста. Без этого на 20 услугах —
утонуть в ручной сверке СК/ЦПК.

---

## 4. Честный итог и последовательность

- **К 1 липня:** 2 услуги доказывают пайплайн и принципы (детерминизм, человек-в-петле, эскалация). Это
  витрина, а не масштаб.
- **Реальный рост 2→20** начинается с **Service Builder** + формального sign-off как **состояния продукта**
  (roadmap v2.2 «панель рецензування»).
- **Hybrid/LLM-стек** — потом, под конкретную услугу, которую нельзя сделать чистым шаблоном.

Последовательность правильная: сначала доказать пайплайн (сделано) → дать юристу авторинг → формализовать
ревью → и только потом, по необходимости, LLM-рассуждение для редких сложных услуг.
