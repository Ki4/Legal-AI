# doc-engine — Requirements

> Tier 2 spec. Сервіс-агностична генерація документів: декларативний шаблон у БД + спільний движок рендерингу.
> Мета: нова проста послуга = form_config + текст шаблону, **0 рядків коду**. Юрист редагує текст документа, не код.

---

## 1. Проблема (стан зараз)

- Нода **Build Document** (form-submit) = 45K символів: JS-білдери divorce (32K) + alimony (27K) вшиті інлайн.
- Dispatch захардкоджено: `{ divorce: buildDivorceDocument, alimony: buildAlimonyDocument }` — третя послуга не запрацює без сесії розробки.
- `services.ai_prompt` для тіла документа декоративний (реально використовується лише declension-промпт).
- Юридичний контент (текст позовної заяви) живе в програмному коді — Ольга не може ні додати послугу, ні поправити формулювання.

Дзеркальна аналогія, яка ВЖЕ працює в проєкті: `DynamicLegalFormBuilder` (код, 1 раз) + `form_config` (дані, на послугу). Робимо те саме для документів.

## 2. Архітектура

```
services (Supabase)                    n8n Build Document (Code node)
┌──────────────────────────┐           ┌─────────────────────────────────┐
│ generation_mode:         │  ───────► │ dispatch по generation_mode:    │
│   'js' | 'template'      │           │  'template' → renderDocument(   │
│ document_template: TEXT  │  ───────► │     document_template, context) │
└──────────────────────────┘           │  'js'       → legacy builders   │
                                       └─────────────────────────────────┘
SSoT шаблону в git:                    Движок (SSoT в git, тести):
n8n/templates/services/<slug>.document.txt   n8n/templates/render-document.js
```

- **Движок** — чистий JS без залежностей (працює в n8n Code node і в vitest). Парсер, НЕ `eval` — шаблон, відредагований юристом, не може виконати код.
- **Шаблон** — текст документа з конструкціями DSL. SSoT — файл у git; у БД — runtime-копія (як form_config), завантажується скриптом.
- **Режим — властивість послуги** (`generation_mode`): прості послуги — `template`; майбутні `hybrid` / `ai_generate` — розширення цього ж dispatch (поза scope цієї фічі).

## 3. Контракт DSL (фіксується цією спекою)

### 3.1 Підстановка
- `{{field}}` — значення відповіді форми. Порожнє (`null`/`undefined`/`''`) → fallback `________` (поточна семантика `val()`).
- `{{helper arg1 arg2}}` — виклик хелпера. Аргументи: шлях до поля, `'литерал'`, або вкладене значення контексту.
- `{{field|raw}}` — без fallback (порожній рядок як є) — для випадків, де прочерк недоречний.

### 3.2 Умови
```
{{#if expr}} ... {{else if expr}} ... {{else}} ... {{/if}}
```
- `expr`: правдивість поля (семантика `has()`: не null/undefined/''/false; рядок `'false'` = false),
  порівняння `field == 'literal'`, `field != 'literal'`, числові `>`, `<`, `>=`, `<=`.
- Логічні `and` / `or` / `not` (без дужок — пласкі ланцюжки; складніше → computed-значення в движку).

### 3.3 Цикли
```
{{#each children}}{{@index1}}) {{name}}, {{birthDate}} року народження{{/each}}
```
- `{{@index1}}` — 1-based лічильник; `{{@first}}` / `{{@last}}` — булеві для роздільників.
- Усередині блоку шляхи резолвляться відносно елемента, зовнішній контекст доступний.

### 3.4 Пробіли та переноси (критично для byte-identical)
- Блокові теги (`{{#if}}`, `{{else}}`, `{{/if}}`, `{{#each}}`, `{{/each}}`), що стоять на окремому рядку, **поглинають свій рядок** (не лишають порожніх рядків). Інлайн-використання — не поглинають.

### 3.5 Коментарі та директиви стилю (зарезервовано під фазу 2)
- `{{! коментар }}` — не потрапляє у вихід.
- `{{!style: ...}}` — **директива стилю абзаца**, що йде після неї. У фазі 1 рендерер директиви **ігнорує** (вихід — той самий плоский текст); у фазі 2 вони рендеряться в Google Docs `updateParagraphStyle`. Зарезервовані значення:
  - `right` / `center` — вирівнювання (шапка праворуч, заголовок по центру);
  - `bold` — накреслення;
  - `indent` — абзацний відступ першого рядка;
  - `keep-with-next` — не відривати від наступного абзацу (заголовок «ПРОШУ СУД:» не повисне останнім рядком сторінки);
  - `keep-together` — не розривати блок усередині (блок підпису: дата+підпис+ПІБ переїжджають на нову сторінку цілком);
  - `page-break-before` — завжди з нової сторінки.
- **Принцип розривів сторінок: правила, не позиції.** Довжина контенту невідома заздалегідь (кількість дітей, довжина адрес), тому шаблон декларує семантику блоків, а ДЕ саме впаде розрив — обчислює Google Docs при розкладці. Ручних «вставити розрив тут» у шаблонах немає.

### 3.6 Контекст рендерингу (3 шари)
1. **`answers`** — сирі відповіді форми (field_id → value).
2. **`ai.*`** — склонения від AI Declension **з fallback**: `{{ai.plaintiff_genitive}}` → якщо AI не дав, підставляється зібране ПІБ (поточна поведінка `(ai && ai.x) || name`).
3. **`computed`** — похідні значення, які движок обчислює ДО рендеру (спільна бібліотека для всіх послуг):
   - `plaintiff_name`, `defendant_name` — зібрані ПІБ (3 поля → рядок, пропуски відфільтровано);
   - `children[]` — розпарсений `children_details` (→ `{name, birthDate, certInfo, certInstrumental, gender}`), `n_children`;
   - `plaintiff_gender`, `defendant_gender` — за по батькові (`-івна/-ївна/-овна` → female).

### 3.7 Хелпери фази 1 (юридично-критична логіка — в движку, тестована 1 раз)
| Хелпер | Приклад | Дає |
|---|---|---|
| `formatDate` | `{{formatDate marriage_date}}` | `20 червня 2015` (ISO → укр.) |
| `formatDateQuoted` | | `«20» червня 2015` |
| `gender` | `{{gender plaintiff_gender 'уклав' 'уклала'}}` | словоформа за статтю |
| `plural` | `{{plural n_children 'дитина' 'діти'}}` | форма за кількістю (2 або 3 форми) |
| `alimonyFraction` | `{{alimonyFraction n_children}}` | `1/4` / `1/3` / `1/2` (ст. 183 СК) |
| `concat` | | склейка з пропуском порожніх |

Список розширюваний; нові хелпери — лише з тестами. Сервіс-специфічні словники (типу REASONS_MAP у divorce) — рішення на сесії портування divorce, НЕ в цій фічі.

## 4. Зміни Supabase

**Migration 014** (`014_doc_engine.sql`):
- `services.generation_mode TEXT NOT NULL DEFAULT 'js' CHECK (generation_mode IN ('js','template'))` — майбутні `hybrid`/`ai_generate` додаються окремою міграцією, коли будуть реалізовані;
- `services.document_template TEXT NULL`;
- backfill: усі поточні послуги → `'js'` (поведінка не змінюється від самої міграції);
- COMMENT на обидві колонки.

RLS не змінюється (services вже SELECT-public, write через service_role/authenticated — як є).

**Перемикання alimony на `'template'`** — НЕ в міграції, а окремою дією після live-перевірки (флип колонки = миттєвий rollback у `'js'` без деплою — той самий патерн, що status kill-switch).

## 5. Зміни n8n (form-submit)

- **Build Document** — єдина змінювана нода:
  - інлайн додається движок (дзеркало `n8n/templates/render-document.js`);
  - dispatch: `generation_mode === 'template' && document_template` → движок; інакше — legacy JS-білдери (divorce лишається на JS у цій фічі);
  - дані послуги вже доступні: `$('Get Service')` робить `getAll` без обмеження колонок.
- Prepare Declension / AI Declension — **не змінюються** (уніфіковані поля `defendant_*` вже спільні для divorce+alimony). Обмеження: нові послуги мають використовувати ту саму конвенцію імен полів для склонень → зафіксувати в IMPROVEMENTS як майбутню конфігурованість.
- Деплой — `scripts/deploy-workflow.mjs form-submit` (бекап + збереження credential-ID).

## 6. Скрипти

- `scripts/upload-document-template.mjs <slug>` — generic: читає `n8n/templates/services/<slug>.document.txt` → `UPDATE services SET document_template`. Ідемпотентний, `--dry-run`. (Патерн upload-alimony-config.mjs, але без one-off хардкоду.)

## 7. Пілот: alimony

- `n8n/templates/services/alimony.document.txt` — шаблон, що відтворює `buildAlimonyDocument` **байт-у-байт**.
- Чому байт-у-байт: на кроці міграції змінюється лише спосіб зберігання контенту → вихід зобовʼязаний бути ідентичним, інакше невідомо, що зламали. Покращення типографіки — окремий свідомий крок (фаза 2) зі своєю перегенерацією голденів.
- divorce НЕ портується в цій фічі (наступна сесія, після обкатки DSL на alimony).

## 8. PII / безпека

- Движок не змінює потік PII: документ так само збирається в памʼяті n8n і йде в Google Docs; шифрування кейса (AES-256-GCM) не торкається.
- Шаблон НЕ містить PII і НЕ містить секретів — лише плейсхолдери.
- Парсер без `eval`/`Function` — шаблон з БД не може виконати довільний код у n8n.

## 9. Поза scope (свідомо)

- Портування divorce (наступна сесія).
- Admin-UI редактор шаблону для Ольги (окрема фіча; поки що — файл у git + upload-скрипт).
- Режими `hybrid` / `ai_generate` (розширення dispatch, після появи ревʼюера).
- Типографіка Google Docs — **фаза 2**: рендер `{{!style:}}` директив у styled `batchUpdate` requests (вирівнювання, відступи, keep-with-next/keep-together для контролю розривів сторінок). У цій фічі — лише зарезервований синтаксис, який фаза 1 ігнорує.
- Конфігурованість полів declension під нові послуги (→ IMPROVEMENTS).
