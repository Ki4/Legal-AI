## §0. Намір (одним абзацом)

Юрист відкриває послугу в адмінці й **бачить**, як документ розкладається по сторінках A4 та які
частини тримаються разом, щоб розуміти й контролювати цілісність (напр. що підпис не лишиться сам).
«Розташування частин» НЕ редагується вільно — скелет позову фіксований ст.175 ЦПК; важіль юриста =
**цілісність** (тримати-разом / з-нової-сторінки). Ця ітерація закладає **модель** (іменовані блоки +
зв'язки + гайд) і **візуалізацію** (read-only); інтерактивне редагування — окрема майбутня ітерація.

## §1. Модель authoring (іменовані блоки + зв'язки)

### §1.1 Блок документа
- **Гібрид:** фіксований канонічний набір блоків позову + опційні під-блоки.
- Канонічні блоки (v1, для divorce/alimony): `court_header` (шапка суду), `parties` (сторони),
  `doc_title` (назва документа), `circumstances` (обставини), `legal_basis` (правова основа / цитати
  статей), `petition` (ПРОШУ), `appendices` (Додатки), `signature` (дата+підпис).
- **Під-блок (опційний):** довільний іменований діапазон усередині канонічного (напр. окремий пункт
  ПРОШУ). Не обов'язковий для v1-візуалізації; модель має його ДОПУСКАТИ, UI може не вводити.
- Розпізнавання блоків у відрендереному документі — детерміноване, з маркерів/структури (див. §4).

### §1.2 Зв'язки цілісності (v1)
Рівно два, обидва вже мають примітив у рушії:
- **`тримати-разом`** (keep-together-як-юніт) → `keep-block` → ланцюг `keep-with-next`. Блок ніколи
  не розривається між сторінками.
- **`з-нової-сторінки`** (page-break-before) → блок починається з нової сторінки.
- **Поза скоупом v1:** міжблоковий явний клей (A↔B) і **widow/orphan** — останнє в Google Docs
  недосяжне → в IMPROVEMENTS #77 (export-only для docx/PDF-міграції). Не вводити «мертві» атрибути.

### §1.3 Реєстр (SSoT)
- **Код-модуль у репо** (TS у `apps/client/src/`, без БД, без міграцій). Структура запису:
  `{ id, label (укр.), primitives: string[], help_text (укр.), color }`.
  - `label` — людська назва блоку/зв'язку для UI.
  - `primitives` — на що мапиться (`['keep-block']`, `['page-break-before']`).
  - `help_text` — пояснення «навіщо» для гайду (§3).
  - `color` — колір підсвічування блоку в прев'ю + у легенді.
- **ОДИН реєстр** кормить три речі: (1) візуалізацію (підписи/кольори блоків), (2) розкривний гайд,
  (3) майбутній редактор. Дублювання заборонено.

## §2. Прев'ю — симуляція A4 (read-only)

### §2.1 Вхід
- Відрендерений документ + `styleHints` з рушія (`renderDocumentWithStyles`, уже у браузері як чистий
  JS) на **тестових даних** — реюз `apps/client/src/admin/lib/sampleAnswers.ts` (SSoT форм-ключів).
- Метрики сторінки (ДСТУ-орієнтир, конфіг-константи): A4, TNR ~14, інтервал ~1.5, поля ~30/15/20 мм.

### §2.2 Поведінка
- Рендерити документ у контейнері шириною A4; **JS-вимірювання** висот абзаців → призначення сторінок;
  малювати межі сторінок.
- **Honorувати зв'язки:** блок із `тримати-разом` НЕ розривається (переїжджає на наступну сторінку
  цілим); `з-нової-сторінки` форсує розрив перед блоком. Тобто прев'ю показує **ефект** зв'язків
  (з keep-block підпис уже їде разом з Додатками — і це видно).
- **Підсвічування:** кожен блок обведено/тоновано кольором свого типу зв'язку (легенда — §3).
- **Edge: блок вищий за сторінку** → показати попередження «⚠ цей блок вищий за сторінку — рушій
  розірве його» І все одно намалювати розрив (чесно показати межу рушія). Без тихого розриву.

### §2.3 Caveat (обов'язково в UI)
- Видимий напис «**Наближено** — точна пагінація залежить від рушія (Google Docs). Канонічний вигляд —
  згенерований документ.» Прев'ю — advisory, НЕ суд-точне.
- Точний PDF-preview (через docx+Gotenberg) — явно **поза скоупом**, занотувати в IMPROVEMENTS як
  наступний крок fidelity.

## §3. Вбудований гайд

- **Розкривний (collapsible) блок-легенда** під/поряд прев'ю: «Як це працює».
- Вміст із реєстру (§1.3): колір → `label` → `help_text` для кожного зв'язку та канонічного блоку.
- Реюз існуючого UI-патерну (напр. `Tooltip`/collapsible із session 56) — без нового дизайн-язика.
- Дефолт — згорнуто (не лякати, не засмічувати).

## §4. Розпізнавання блоків (детерміновано)

- Прев'ю мусить знати межі блоків. Джерело — **структура + маркери** відрендереного документа
  (`styleHints` дають keep-with-next-діапазони; заголовки/«ПРОШУ»/«Додатки:» — якірні рядки).
- Спиратися на той самий детермінований підхід, що `preview-excerpt.js`/`citations.mjs` (якірні
  патерни), а не на крихкі номери рядків.
- **Fail-closed:** якщо блок не розпізнано — показати документ без підсвічування цього сегмента +
  тихий сигнал у «технічні деталі», ніколи не падати й не вгадувати межі.

## §6. Інваріанти

1. **Read-only:** жодного запису в `services`/`cases`; жодного нового live-workflow. Чистий клієнт.
2. **Один SSoT реєстру** кормить прев'ю + гайд (+ майбутній редактор).
3. **Детермінований рушій прев'ю** (вимірювання/призначення сторінок) — тестований (не LLM).
4. **Чесність fidelity:** caveat «наближено» завжди видимий; overflow → попередження, не тихо.
5. **Реюз рушія:** пагінація споживає той самий `styleHints`, що й прод (keep-with-next), а не власну
   копію правил.
