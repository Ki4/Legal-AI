# service-mirror — Plan

> **SDD-Tier 2** спека. Адмінка стає **дзеркалом** (read-only огляд того, що вже є) + **каналом зворотного зв'язку** (коментарі юриста + запит нової послуги з прикладом документа).
> Контракт — `requirements.md`; перевірка — `validation.md`.
> Передісторія/рамка — обговорення сесії 41 (розворот «білдер → дзеркало»), memory `project-phase-foundation`, IMPROVEMENTS #12/#51.

## Навіщо (рамка)

Поточна адмінка — інструмент **редагування** (FormBuilder + декоративний таб «AI-промпт» + Налаштування). Проблеми, з'ясовані в коді:
1. **Петля «адмінка → документ» розірвана**: прод-генерація йде з `services.document_template` (DSL), а таб «AI-промпт» (`ai_prompt`) у генерації **не використовується** — юрист бачить поле, що ні на що не впливає.
2. **Білдер технічно ворожий не-юристу**: показує `field.id`, сирі `show_if` оператори, слаги, транслітерацію.
3. Юрист не має способу **побачити**, з чого складається послуга, на яких законах тримається і **чого бракує**.

**Розворот (рішення Сергія, сесія 41):** не чіпати редагування зараз. Спершу — **показати юристу те, що є, гарно й зрозуміло**. Юрист вчиться, як це працює → дає фідбек (коментар прямо в адмінці) → замовляє нову послугу (опис + закони + приклад документа, який сам завантажує). Ми (розробники) збираємо заявки/фідбек, знаходимо закономірності — і **звідси** проєктуємо майбутній білдер, не наосліп.

**Не-ціль цієї фічі:** редагування форм/шаблонів через UI, ролі/RLS, AI-генерація чернетки шаблону з прикладу. Усе це — пізніше (див. «Поза скоупом»).

## Підхід

- **Read-only насамперед.** Слайс 1 нічого не пише в `services` і не чіпає генерацію → ризик 🟢, рухаємось швидко.
- **Рахуємо «анатомію» в браузері з даних, що ВЖЕ є.** `form_config` (поля) і `document_template` (DSL-шаблон) обидва лежать у рядку `services`. Чиста функція парсить шаблон → список використаних `field_id`, плейсхолдерів і цитат; порівнює з полями форми → знаходить «дірки». Жодного нового AI, жодного бекенда.
- **Спрощуємо, де можемо переиспользувати.** Логіка парсингу шаблону вже існує в `n8n/templates/render-document.js`; екстрактор цитат — `scripts/lib/citations.mjs`. Виносимо потрібний мінімум у спільний **чистий TS-модуль** `apps/client/src/lib/serviceAnatomy.ts` з парасоль-тестом на паритет із regex-цитатником (SSoT не дублюємо змістовно — тест ловить дрейф).
- **Канал зв'язку — мінімальний CRM.** Дві таблиці (`service_notes`, `service_requests`), статуси лише `open|done`, без тредів/нотифікацій. Файл прикладу — Supabase Storage (приватний bucket).
- **Реверсивність.** Слайс 1 — лише читання. Слайси 2-3 додають таблиці (forward-only міграції) + сторінки; видаляються відкатом гілки.

## Слайси

### Слайс 1 — Дзеркало послуги (read-only) ← цей реліз
Нова сторінка `Перегляд послуги` (route `services/:id` → view; редагування переїжджає на `services/:id/edit`, лишається dev-інструментом). Секції:
1. **Форма як є** — таби → поля: підпис, тип (людською: «Текст», «Дата», «Так/Ні»…), обов'язковість, варіанти (для choice/multicheck), умова показу **природною мовою** («показується, якщо `Є діти` = Так»), без `id`/слагів на видноті.
2. **Анатомія документа** (поля in/out + health):
   - поля форми → **використовуються** шаблоном / **без мапи** (gap: форма питає, документ ігнорує);
   - плейсхолдери шаблону → **мають поле** / **без поля** (gap: документ чекає дані, форма не питає);
   - **health-світлофор** (правило — requirements §3): 🟢 / 🟡 / 🔴.
3. **Закони — списком** (граф пізніше, окремий слайс): цитовані статті з шаблону → лінк на джерело (zakon.rada / `law_chunks`) + badge «застаріло» (`is_stale`) / «змінено» (є pending у `law_change_log`).
4. **Каталог** (`DashboardPage`) — додати health-badge на картку, щоб стан було видно списком.

### Слайс 2 — Коментарі юриста (`service_notes`)
Панель на сторінці перегляду: юрист пише нотатку (що добре / погано / незручно), статус `open|done`. Dev бачить усі в одному інбоксі. RLS — як `law_change_log` (authenticated read/write; INSERT/DELETE контрольовано).

### Слайс 3 — Запит нової послуги (`service_requests` + Storage)
Форма заявки: назва, опис, потрібні закони (текст/лінки), **завантажити приклад документа** (DOCX/PDF → приватний Storage bucket). Інбокс заявок для dev. Приклад документа = фактичний бриф на шаблон.

## Групи задач (слайс 1)

### G1 — Спільна логіка анатомії (чиста, з тестами)
- `apps/client/src/lib/serviceAnatomy.ts` — чисті функції:
  - `analyzeTemplate(tpl: string) → { usedFieldIds: string[]; placeholders: string[]; citations: string[] }` — парсинг `{{field}}`, `{{#if cond}}`, цитат (regex з `citations.mjs`, портований).
  - `diffFormVsTemplate(formConfig, analysis) → { usedFields, unusedFields, unmatchedPlaceholders }`.
  - `serviceHealth(service, analysis, staleArticles) → { level: 'green'|'amber'|'red'; reasons: string[] }`.
- `apps/client/src/lib/__tests__/serviceAnatomy.test.ts` — unit-тести + **паритет-тест цитат** проти реального `divorce`/`alimony` шаблону (golden `<slug>.citations.json`).

### G2 — Сторінка перегляду
- `apps/client/src/admin/pages/ServiceViewPage.tsx` — read-only, 4 секції вище.
- Розвести роути: `services/:id` → view, `services/:id/edit` → існуючий `ServiceEditPage`. Картка в `DashboardPage` веде на view; кнопка ✏️ — на edit (dev).
- `STATUS_META`-стиль для health-badge (переиспользувати патерн).

### G3 — Каталог + закони
- Health-badge на картку послуги в `DashboardPage`.
- Секція «Закони»: статті → джерела; підтягнути `is_stale` з `law_chunks` за `law_code` + pending з `law_change_log` за `affected_services`.

### G4 — Доки + закриття
- `DECISIONS.md` — розворот «білдер → дзеркало»; чому read-only first; межа анатомії (парсинг, не рендер).
- `IMPROVEMENTS.md` — занести відкладене (граф-viz, коментарі-слайс2, заявки-слайс3, AI-чернетка з прикладу, ролі/RLS, редагування графа).
- `roadmap.md` — рядок про service-mirror.
- changelog + session-summary; `Closes #N` при merge.

## Поза скоупом (→ IMPROVEMENTS / roadmap)
- **Граф-візуалізація** law_relations (react-flow) — слайс після списку.
- **Живе превʼю реального документа** — потребує рендер-движка в браузері; слайс 1 показує лише поля in/out + health.
- **Редагування** форм/шаблонів через UI (білдер для юриста) — **головна майбутня фаза**, проєктуємо ПІСЛЯ фідбеку.
- **AI-чернетка `form_config` + шаблону з прикладу документа** («Legal Engineer агент») — north-star, після розбору 5-10 заявок руками.
- **Ролі + per-row RLS** — тригер: окремий логін Ольги.
- **Редагування/пропозиція зв'язків графа головним юристом** (HITL) — roadmap v2.2.
- **Email-сповіщення**, прикріплення кількох файлів, тред-коментарі, тести-в-адмінці.

## Стоп-умова
Якщо G1 покаже, що `render-document.js`-логіку парсингу не можна надійно відтворити в браузері (ESM/CJS-interop, приховані залежності) — **не тягнемо весь движок у бандл**. Виносимо лише потрібний токен-парсер як окремий чистий модуль (≈30 рядків) з тестом на паритет; повний рендер лишаємо на слайс «превʼю документа».
